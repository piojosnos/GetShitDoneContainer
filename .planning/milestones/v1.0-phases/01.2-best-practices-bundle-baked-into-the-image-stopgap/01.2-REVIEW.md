# Phase 01.2: Code Review Report

**Reviewed:** 2026-10-04
**Depth:** standard
**Files Reviewed:** 31
**Status:** issues_found

## Summary

The start hook, entrypoint hook loop, Dockerfile changes, managed settings and guard rules hold up under static tracing. I traced the hook against hostile list lines, a missing bundle, an interrupted sync and glob edge cases, and found no data-loss or injection path beyond what SANDBOX.md documents. I found no blocker.

The weaker areas are:

- The bundled skills, which carry logic gaps.
- A silent-skip path in the entrypoint that undercuts the "failing hook stops the start" guarantee.
- The H-18 test, which lacks a negative control and points its diagnostics at the wrong log.
- A few host-test details that depend on locale or timing.

Docker is not available here, so none of this was confirmed by running containers.

## Warnings

### WR-01: `merged` skill deletes a branch whose name it may never have recorded, and uses `-D`

**File:** `best-practices/skills/merged/SKILL.md:15-16, 22, 61-77`
**Issue:**
- Step 4 uses `$FEATURE_BRANCH`, which the skill sets only from `headRefName` in the auto-detect path (Step 1.2).
- On the `/merged <target-branch>` path (Step 1.1) detection is skipped, so nothing sets the variable.
- Step 3 then runs `git checkout "$TARGET"`, which leaves the feature branch and loses its name.
- The `git branch --merged "$TARGET" | grep -F "$FEATURE_BRANCH"` line with an empty variable matches every merged branch.
- A model improvising from that skill can delete the wrong branch, or run `git branch -D ""`.
- The text says to use `git branch -D` (force) and calls it "reversible and loses nothing". That is false if the local branch has commits made after the PR head was merged: squash/rebase merges make `--merged` useless, and `-D` discards those commits.

**Fix:** Record the branch before switching, and delete safely:
```bash
FEATURE_BRANCH=$(git rev-parse --abbrev-ref HEAD)   # before Step 3, in both paths
...
# Step 4: compare against the PR head sha, not the name
gh pr view "$FEATURE_BRANCH" --json headRefOid -q .headRefOid   # expected tip
[ "$(git rev-parse "$FEATURE_BRANCH")" = "$HEAD_OID" ] && git branch -D "$FEATURE_BRANCH"
```
Otherwise tell the model to stop and ask when the local tip differs from the merged head. Also require `FEATURE_BRANCH` to be non-empty and different from `TARGET`.

### WR-02: `pr-reply` skill omits `--paginate`, contradicting the rule the same bundle ships

**File:** `best-practices/skills/pr-reply/SKILL.md:162, 167, 168`
**Issue:**
- `best-practices/rules/git-workflow.md:39` says "Always pass `--paginate` to `gh api` when fetching `pulls/{n}/comments` and `pulls/{n}/reviews`".
- All three fetch commands in the skill (pulls comments, issue comments, reviews) omit it.
- Any PR with more than 30 comments silently drops the newest, which is the failure the rule exists to prevent.
- A model that follows the skill's literal commands reproduces the bug.

**Fix:** Add `--paginate` to all three `gh api` GET commands:
```bash
gh api --paginate repos/{owner}/{repo}/pulls/{n}/comments --jq '...'
```
Note that `--paginate` with `--jq` runs the filter per page, which is fine for these per-item filters.

### WR-03: `pr-reply` classifies threads by "who wrote the last comment", but its own replies post as the user

**File:** `best-practices/skills/pr-reply/SKILL.md:170-171, 199-215`
**Issue:**
- The agent posts replies with the user's `gh` token, so on GitHub the agent's replies and the user's replies have the same `user.login`.
- Steps 1b.1 to 1b.3 and the "never double-post" rule depend on telling "your reply" from "the user's response", and `in_reply_to_id` plus the login cannot do that.
- The skill gives no marker for the model to key on.
- A re-run can double-post, or treat its own reply as an "approval" from the user.

**Fix:** Have every posted reply start with a fixed marker line (for example `<!-- pr-reply -->` as an HTML comment, or a visible `[proposal]` prefix) and classify a comment as "mine" by that marker. Document it in Phase 1 step 4.

### WR-04: Entrypoint silently skips a start hook that is not executable

**File:** `base/sbx-entrypoint:47-50`
**Issue:**
- `if [ ! -f "$hook" ] || [ ! -x "$hook" ]; then continue`.
- SANDBOX.md says "A failing hook stops the start, so a sandbox never runs with a half-synced bundle".
- A hook that lost its exec bit is skipped with no message, and the sandbox starts with a stale or missing bundle.
- That is exactly the unprotected state the feature is meant to prevent.
- The Dockerfile `chmod 755` and the H-14 mode check make it unlikely today, but a future hook added in an image layer that forgets the chmod fails open.

**Fix:** Skip only non-regular files; fail on a non-executable regular file:
```bash
if [ ! -f "$hook" ]; then
  continue
fi

if [ ! -x "$hook" ]; then
  echo "[sbx] ERROR: start hook $hook is not executable; the container was not started." >&2
  exit 1
fi
```

### WR-05: H-18 has no negative control, so a refusal is not tied to the managed settings

**File:** `tests/host/h18-scope-and-deny.sh:69-71, 89-104` (and `tests/bundle-selftest.sh:503-510`)
**Issue:**
- The deny scenario passes when the synced rule is unchanged and the planted files are absent.
- Those outcomes also occur if the edit fails for any other reason:
  - `old_string` is not unique.
  - The tool sees a protected-path prompt, which `-p` auto-denies, for a config-dir location.
  - A future Claude version blocks writes under `CLAUDE_CONFIG_DIR` wholesale.
- The only positive control is a file in the project folder, which sits outside the config dir.
- SANDBOX.md also claims "Your own skills and `state/claude/CLAUDE.md` stay editable", and no automatic check proves it.
- The managed-settings protection could therefore be a no-op and H-18 would still print PASS.

**Fix:** Add two steps to the deny script that must succeed:
- A Write to an allowed path inside the config dir, for example `{configRoot}/skills/h18-user-skill/SKILL.md`.
- An Edit of `{configRoot}/CLAUDE.md`.

Assert both files changed. Do the same in `bundle-selftest.sh`, and fail H-18 with "the deny proves nothing" if the control did not run.

### WR-06: H-18 failure messages point at a log that is always empty

**File:** `tests/host/h18-scope-and-deny.sh:31-38, 80, 91`
**Issue:**
- In `run_scenario` the node server's output goes to `/dev/null`, and Claude's stdout and stderr go to `$containerRoot/logs/h18-$scenarioName-claude.log`.
- The `docker exec` output that is captured into `$RUN/logs/h18-$scenarioName-run.log` is therefore essentially empty.
- The failure messages print `head -c 300` of that `-run.log` as "run output".
- When Claude fails (bad API format, timeout, auth), the person reading the FAIL line sees an empty string and the real error sits in an unmentioned file.

**Fix:** Print `head -c 300 "$RUN/logs/h18-$scenario-claude.log"` instead (the host path is the same file, because `logs/` is inside the mount). Also keep the server's output instead of sending it to `/dev/null`.

## Info

### IN-01: Expected skill order depends on the host's glob collation, the real order on the container's

**File:** `tests/host/h15-bundle-synced-and-visible.sh:24-41`, `tests/host/h16-sync-refreshes-and-spares.sh:21-28, 76-80`
**Issue:**
- The hook writes `.best-practices-skills` in the container's glob order (`LANG=C.UTF-8`).
- H-15 and H-16 build the expected list from `"$bundleDir"/skills/*/` in the macOS shell's locale, then compare with `!=` on the whole text.
- With the current names (`merged`, `pr-reply`) the two orders agree.
- A later skill with an uppercase letter, `_` or digit prefix can collate differently on the Mac and produce a false FAIL.

**Fix:** Compare sorted lists on both sides (`sort` with `LC_ALL=C` on each), or have the hook `sort` its glob.

### IN-02: Hook wipes `rules/` without saying what it removed

**File:** `claude/start.d/10-best-practices:29-30`
**Issue:**
- `rm -rf "$configDir/rules"` destroys any rule the user wrote in `~/.claude/rules/`.
- That includes the rules of a sandbox migrated from the old layout.
- The behaviour is documented in SANDBOX.md and covered by the selftest, but the hook prints nothing, so the first start after migration deletes user files with no trace.

**Fix:** When `rules/` holds a file that is not in the bundle, print one line to stderr, for example `[sbx] note: removed rules/foo.md (not in the bundle)`. This is optional and cheap.

### IN-03: `fake-claude-api.js` crashes on a non-JSON body

**File:** `tests/host/support/fake-claude-api.js:62-65`
**Issue:**
- `JSON.parse(body)` is unguarded inside the `end` handler.
- A malformed or truncated request throws an uncaught exception that kills the server.
- Claude then sees ECONNREFUSED and the test reports "never reached the fake API", which is misleading.

**Fix:** Wrap the parse in try/catch, answer 400, and write the error to stderr.

### IN-04: Fixed `sleep 1` as the server readiness wait

**File:** `tests/host/h18-scope-and-deny.sh:33`, `tests/bundle-selftest.sh:459`
**Issue:**
- Both scripts start the Node server in the background and sleep one second before running Claude.
- On a slow Docker Desktop VM or a loaded machine that may not be enough.
- Claude retries connection errors, so it is usually forgiving, but the failure would be intermittent and look like an API wire-format regression.

**Fix:** Poll until the port accepts a connection (for example `node -e` connect, or a short loop over `/dev/tcp`) with an upper bound of about 10 s.

### IN-05: `bundle-selftest.sh` runs the `/context` probe without a timeout

**File:** `tests/bundle-selftest.sh:403-407`
**Issue:**
- The fake-API runs use `timeout 90`.
- The earlier offline `claude -p /context` probe does not.
- A hung Claude, for example one that waits on a network call before reaching the local command, would hang the selftest forever.

**Fix:** Prefix it with `timeout 60`, as is done at line 463.

### IN-06: Doc inconsistencies in H-19 and the always-on rules

**File:** `tests/host/manual/h19-bundle-behaviour.sh:6` versus `tests/host-checklist.md` (H-19 helper row); `best-practices/rules/coding-general.md:54-57, 63-66`
**Issue:**
- H-19's header says "six numbered steps", while the checklist row says "five steps" (step 6 is only `/exit`).
- `coding-general.md` is an always-on rule titled language-agnostic, but it carries project-specific examples: "card-* classes with --card-* tokens" and a static-site "serves each site at the base path". Those examples tokens spend context in every project and can confuse the model in unrelated repos.

**Fix:** Say "five steps" in both places. Replace the two examples with neutral ones, or move the rule to the project that needs it.

### IN-07: Managed settings are only syntax-checked at build time; an untracked export tarball sits in the repo root

**File:** `claude/Dockerfile:41, 48`; `claude-best-practices-export.tar.gz` (repo root, untracked)
**Issue:**
- The Dockerfile comment says invalid managed settings stop Claude from starting, so "the build parses the file". `JSON.parse` only catches syntax errors; a misspelled key or wrong rule shape is not caught at build time (only H-18 would notice).
- The untracked tarball is the export that `bundle_is_plain_files_only` warns about (memories, session ids). It is outside the build context (`.dockerignore`), but a stray `git add` of the root would commit it.

**Fix:**
- Reword the Dockerfile comment to "the build checks the JSON syntax".
- Delete the tarball, or add it to `.gitignore`.
