# Phase 01.2: Best-practices bundle baked into the image (stopgap) - Context

**Gathered:** 2026-10-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Every new sandbox starts with the user's best-practices bundle in place: general rules that apply everywhere, language rules that load when Claude touches matching files, and the `/pr-reply` and `/merged` skills. The bundle is committed in this repo as plain files under `best-practices/`, copied into the Claude image at `/opt/sbx/best-practices` (outside the mount), and synced into `state/claude` on every container start, with no network.

This is a stopgap. Phase 2.1 moves the bundle to its own git repo with a per-sandbox clone. The structure chosen here should point toward the long-term goal: a growing library of the user's preferences and practices (general coding, language-specific, testing, docs, git), each loaded in the situation where it applies.

</domain>

<decisions>
## Implementation Decisions

### Bundle contents and structure
- **D-01:** Restructure the tarball content now, organised by topic and situation, not by where it came from. This phase only moves and merges existing text; no new rules are written. Target shape:
  ```
  best-practices/            (repo root; Phase 2.1 moves it to its own repo)
    CLAUDE.md                only if research shows it is still needed (see D-05)
    rules/                   one folder; topic subfolders when it grows
      communication.md
      prose-style.md
      git-workflow.md
      coding-general.md
      documentation.md
      shell.md               (paths: *.sh)
      java.md                (paths: Java/FreeMarker files)
    skills/
      pr-reply/SKILL.md
      merged/SKILL.md
  ```
  **Reversibility:** costly. Why: Phase 2.1 seeds the bundle repo from this shape, and every sandbox's sync expects it.
- **D-02:** Each rule has one home. The source text maps to rule files like this (planner may adjust file names; no rule may end up in two files):

  | Rule file | Folds in |
  |---|---|
  | `communication.md` | `AGENTS.md` "Communication style"; memories `answer-concisely-with-pros-cons`, `decision-grounding-before-choosing`, `prefers-prose-over-askquestion-in-discuss` |
  | `prose-style.md` | `AGENTS.md` "Prose style"; `code-conventions.md` prose section; memory `no-dash-as-punctuation` |
  | `git-workflow.md` | `AGENTS.md` branch-and-PR protocol and push/merge gates; memories `branch-and-pr-protocol`, `engagement-commit-push-approach`, `confirm-before-pr-merges`, `gh-api-paginate-pr-comments` |
  | `coding-general.md` | `code-conventions.md` Part A; memories `symmetry-principle`, `use-first-party-tooling` |
  | `documentation.md` | `AGENTS.md` "Documentation style"; memory `documentation-writing-style` |
  | `shell.md` | memory `shell-scripts-must-be-bsd-macos-portable` |
  | `java.md` | `code-conventions.md` Part B |
  | `skills/pr-reply`, `skills/merged` | the two skills as-is; memory `merged-skill` is dropped (the skill's own description covers it) |

- **D-03:** Drop from the bundle: `README.md` (it only explained the export), `github-workflow-prompt.md` (a subset of `AGENTS.md` for agents without skills), and memory `pr-reply-skill-pending-commit` (stale: `pr-reply` is now committed in the bundle). Strip `originSessionId` from anything carried over. The tarball `claude-best-practices-export.tar.gz` is not committed.
- **D-04:** Rule scope lives in each file's frontmatter, not in the folder: no `paths:` means always on; `paths:` means loaded when Claude touches a matching file. Mapping:
  - Always on: rules a file path cannot predict (communication, prose, git, general coding, docs).
  - Path-scoped: language and file-type rules (`shell.md`, `java.md`).
  - Skills: activities (`/pr-reply`, `/merged`; later testing, docs).
- **D-05:** **Research must verify** how Claude Code (at the pinned 2.1.285) loads a user-level `rules/` folder under `CLAUDE_CONFIG_DIR`: do files without `paths:` load always and files with `paths:` load on match? Are subfolders scanned? If yes, the bundle ships no `CLAUDE.md` (no `@` imports needed). If not, `CLAUDE.md` imports the always-on files with `@`, and language rules fall back to skills. Note: `@` imports are eager (loaded every session), so the always-on set must stay small.

### Memories
- **D-06:** The bundle ships no memories and the sync never writes into any `projects/*/memory/` folder or `MEMORY.md`. Memories are per project and learned by the agent. The long-term flow is one-way: a memory that proves general is promoted into a bundle rule by PR, then deleted. This amends roadmap success criteria 3 and 4 and BP-02 (done in this discussion).

### Ownership of state/claude
- **D-07:** The image owns `state/claude/CLAUDE.md` (if the bundle ships one): it is overwritten on every start. Project rules belong in the project's own `CLAUDE.md`; general rules belong in the bundle. If research shows no `CLAUDE.md` is needed, the image ships none and the existing file is left untouched.
- **D-08:** Accidental edits to generated files are prevented in three layers:
  1. Self-healing: the next start overwrites them.
  2. A header in every synced file saying it is generated, edits are lost on restart, and naming the source to edit instead (`best-practices/` in this repo; in Phase 2.1, the sandbox's bundle clone). The header must not break skill or rule frontmatter (place it after the frontmatter, as a comment or short note).
  3. Managed settings baked into the image (expected path `/etc/claude-code/managed-settings.json`, outside the mount) with deny rules for Edit/Write on the synced `CLAUDE.md`, `rules/**` and the bundle's skills. **Research verifies** the path and deny-rule syntax for the pinned Claude version and how the deny paths resolve under `CLAUDE_CONFIG_DIR`.
- **D-09:** A deliberate change to a global rule is always made in the source, never in the generated copy. Phase 01.2: edit `best-practices/` here, PR, merge, rebuild, restart. Phase 2.1: same flow in the bundle clone.

### Sync behaviour
- **D-10:** `state/claude/rules/` is a full mirror: wiped and copied fresh from the image on every start. Nobody else writes there. A hand-placed file there is lost by design.
- **D-11:** `state/claude/skills/` uses a manifest (a small list file in `state/claude`, e.g. `.sbx-bundle-skills`) of the skill names the sync installed. Each start: remove every skill listed, copy the bundle's skills, rewrite the list. No diffing. GSD skills (`gsd-*`, from Phase 2) and the user's own skills are never touched. On a name clash the bundle skill wins. The user is wary of shell complexity: keep this the simple remove-listed-then-copy form (about 15 lines).
- **D-12:** If the sync fails, the container start fails with a clear `[sbx] ERROR: ...` message, the same style as the existing mount checks. No warn-and-continue.

### Where the sync lives
- **D-13:** Start hook folder. `base/sbx-entrypoint`, after its existing checks and before `exec "$@"`, runs every executable in `/etc/sbx/start.d/` in name order; any failure stops the start (D-12). The Claude image adds its sync as e.g. `/etc/sbx/start.d/10-best-practices`. Phase 2 adds GSD's sync the same way (`20-gsd`). The base stays agent-agnostic, same idea as `SBX_STATE_DIRS`. **Reversibility:** costly. Why: Phase 2's GSD sync and later agent images build on this hook contract.
- **D-14:** The bundle sits in the image at `/opt/sbx/best-practices`, root-owned, read-only to `sandbox`. Start needs no network.

### Claude's Discretion
- Exact rule file names and frontmatter globs (e.g. whether `java.md` also matches `*.ftl`, `pom.xml`).
- Wording of the generated-file header.
- Manifest file name and location inside `state/claude`.
- Whether `AGENTS.md`'s "GSD workflow" section goes into `git-workflow.md` or its own small rule.
- Verification split. Default agreed: new automated checks in `tests/host/`, wired into `run-all.sh` lists, covering: bundle present at `/opt/sbx/best-practices`; after start, `state/claude/rules` and bundle skills match the image; a rule or skill removed from the bundle disappears after rebuild and restart; non-bundle skills and memories survive; start works with networking disabled; the Phase 1 checks still pass. Manual pass (in `tests/host-checklist.md` or a helper under `tests/host/manual/`): `/pr-reply` and `/merged` appear in Claude, an always-on rule is visibly followed, a path-scoped rule loads on a matching file, and the deny rule refuses an edit to a generated file.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `base/sbx-entrypoint` `die()` helper: same `[sbx] ERROR` style the sync failure should use (D-12).
- `SBX_STATE_DIRS` pattern: precedent for the agent image extending the base without the base knowing the agent.
- `tests/host/lib.sh`: PASS/FAIL helpers and test sandbox setup for new checks.

### Established Patterns
- Image ENV (not entrypoint) for anything `docker exec` shells need; the entrypoint runs only at container start.
- Everything the image provides lives outside `/home/sandbox/workspace` so no mount hides it.
- Dockerfile comments: short bullet lists above each section explaining why.
- Shell: plain bash, `set -eu`, short, BSD/macOS-portable where it runs on the host (container scripts run on Linux).

### Integration Points
- Claude's project memory path: `state/claude/projects/-home-sandbox-workspace-<name>/memory/` (left untouched by the sync).
- `state/claude/skills/` will be shared with GSD's skills from Phase 2 (hence the manifest, D-11).

</code_context>

<specifics>
## Specific Ideas

- Long-term vision: a library of practices (general coding, per language, testing, docs, git) where each piece loads only in the situation it applies to. Always-on content must stay small because it costs context every session.
- Memories are the inbox; the bundle is the curated library.
- Symmetry: Claude's bundle sync and Phase 2's GSD sync use the same hook folder and the same "image wins" rules.

</specifics>
