## Summary

Claude Code 2.1.285 loads user-level rules from `$CLAUDE_CONFIG_DIR/rules/` exactly the way the discuss phase hoped. I ran the pinned binary (the dev sandbox has the same 2.1.285 installed) against scratch config dirs: a rule with no `paths:` loads at session start as memory type "User"; a rule in a subfolder loads too (recursive); a rule with `paths:` does not load at start and loads after Claude Reads a matching file. So **the bundle ships no `CLAUDE.md`** (D-05 answered, D-07 never triggers) and no `@` imports are needed. Block-level HTML comments in a rule file cost zero tokens (stripped), so the generated-file header should be an HTML comment placed after the frontmatter. One silent trap: an unquoted glob in `paths:` (`- **/*.sh`) is invalid YAML, and Claude then loads the rule as always-on without any error. Always quote the globs.

Managed settings work as the discuss phase expected: file `/etc/claude-code/managed-settings.json` on Linux (docs), `permissions.deny` entries `Edit(//abs/path/**)`, and deny rules block in every mode including `bypassPermissions`. I proved the deny syntax and the bypass behaviour with the pinned binary by putting the same rules in user settings (managed settings cannot be written without root here). With a symlinked `~/.claude` the absolute form `Edit(//home/sandbox/workspace/state/claude/rules/**)` blocked Edit through the symlink path, Edit through the real path, Write of a new file, `sed -i`, `>>` redirects and `cp`; an undenied control file stayed editable. The `~/.claude/rules/**` form works too, but only because Phase 1 made `~/.claude` a symlink to `state/claude`, so prefer the absolute form that mirrors the image's `CLAUDE_CONFIG_DIR`.

**One blocking finding for the planner:** the Claude image is built with `docker build -t sbx-claude:local claude/`, so its build context is `claude/`. `COPY` cannot reach `best-practices/` at the repo root, which D-01 locks. The fix is to build both images with the repo root as context (`-f <dir>/Dockerfile .`) plus a root `.dockerignore` allowlist; it touches `tests/host/lib.sh`, one regex in `tests/host-selftest.sh`, `SANDBOX.md` (two places) and a `compose.yml` comment. See Open Question 1; this needs the user's go because it changes the documented build command.

**Primary recommendation:** Ship `best-practices/rules/**` (always-on files without frontmatter, path-scoped files with quoted `paths:` lists) and `best-practices/skills/*`, copy them to `/opt/sbx/best-practices` with the repo root as build context, sync them with a `/etc/sbx/start.d/10-best-practices` script run by a plain-bash hook loop in `base/sbx-entrypoint`, lock the synced paths with a baked `/etc/claude-code/managed-settings.json`, and verify with new host checks H-14 to H-17 plus a Linux-runnable selftest of the sync script.

### Pattern 1: Always-on rule vs path-scoped rule

**What:** Scope lives in frontmatter only. No frontmatter means always on. A quoted YAML list under `paths:` means load when Claude Reads, Writes or Edits a matching file under the session's working directory.
**When to use:** every rule file in the bundle.
**Example:**
```markdown
---
paths:
  - "**/*.sh"
---
<!-- Generated from the sbx repo, best-practices/rules/shell.md. Edits here are lost on every container start; edit the source and rebuild. -->

# Shell scripts
...
```
Source: [CITED: code.claude.com/docs/en/memory#path-specific-rules]; behaviour [VERIFIED: ran 2.1.285, Evidence E1, E2, E7].

### Pattern 2: Hook folder with fail-fast loop (base entrypoint)

**What:** run every regular executable in `/etc/sbx/start.d` in name order; first failure ends the start. A missing or empty folder is fine (the unmatched glob is skipped by the `-f` test, so no `nullglob` is needed).
**When to use:** the single addition to `base/sbx-entrypoint`, placed after the existing checks and the `mkdir` loop, before `exec "$@"`.
**Example:** see Code Examples, "Hook loop".

### Pattern 3: Remove-listed-then-copy skill sync

**What:** the manifest `state/claude/.sbx-bundle-skills` lists the skill names the previous start installed. Each start removes exactly those, truncates the manifest, then appends a name and copies each bundle skill. Bundle wins on a name clash because the copy target is removed first.
**When to use:** the whole of the sync script. See Code Examples, "Sync script"; exercised against rename, removal, hand edits, GSD-style skills, user skills, a hostile manifest, a missing bundle and an unwritable config dir.

### Anti-Patterns to Avoid
- **Unquoted globs in `paths:`:** `- **/*.sh` is invalid YAML (a leading `*` starts an alias). Claude silently loads the rule as always-on (Evidence E7). Always write `- "**/*.sh"`.
- **Header before the frontmatter:** frontmatter must be the first line of `SKILL.md` or the whole file becomes skill content [CITED: code.claude.com/docs/en/skills]; put the header after the closing `---`.
- **Making the synced copies read-only (`chmod -R a-w`):** the printed host cleanup `rm -rf <run folder>` would then fail on the Mac (read-only directories cannot be emptied), and the next start's `rm -rf` needs a `chmod` first. The deny rule is the guard; leave modes alone.
- **Denying `skills/**` wholesale:** it would stop Claude editing the user's own and GSD skills. Deny per bundle skill name.
- **Using `Write(...)` or `NotebookEdit(...)` path rules:** Claude Code accepts but never consults them; use `Edit(path)` only [CITED: code.claude.com/docs/en/permissions#read-and-edit].
- **`run-parts` for the hook folder:** silently skips dotted names (see Alternatives).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Comparing repo bundle to image / state | checksum loops, `find` + `sha` pipelines | `docker cp sbx-hosttest:/opt/sbx/best-practices <dir>` then `diff -r` on the host | `diff -r` exists on macOS and Linux; reports exact differing files; the guard bans `sha256sum` on host code |
| Proving rules and skills are visible to Claude | log scraping, mocked loaders | `claude -p "/context"` with `ANTHROPIC_API_KEY=sk-ant-dummy ANTHROPIC_BASE_URL=http://127.0.0.1:1` | Prints "Memory Files" (path, type) and "Skills" (source) with no auth and no network |
| Directory mirror | custom walkers | `rm -rf` then `cp -R dir dst` (dst absent, so identical semantics on GNU and BSD) | Two commands, no edge cases |
| Frontmatter parsing in tests | awk/sed YAML parsing | a grep guard for unquoted glob starts, and `/context` as the behavioural check | Real parser (Claude's) is the oracle; the guard only catches the one known silent failure |
| JSON validity of managed settings | hand inspection | `node -e 'JSON.parse(...)'` in the image build | An unparseable managed file makes Claude refuse to start |

**Key insight:** every moving part here is already provided by Claude Code (loader, scoping, permission engine) or by coreutils. The phase's real work is file placement, one 6-line loop, one 25-line sync, and tests that observe the real Claude through `/context`.

## Common Pitfalls

### Pitfall 1: The bundle is outside the Claude image's build context
**What goes wrong:** `COPY best-practices /opt/sbx/best-practices` fails (`not found`) because the image is built with `docker build -t sbx-claude:local claude/`.
**Why it happens:** the build context is the directory argument. `base/` and `claude/` are separate contexts today [VERIFIED: compose.yml:15 `# Built on the Mac with: docker build -t sbx-claude:local claude/`, SANDBOX.md:24-25, tests/host/lib.sh `docker build -t "sbx-$imageName:local" "$REPO_DIR/$imageName"`].
**How to avoid:** build both images from the repo root with `-f` (Open Question 1 recommendation), add a root `.dockerignore` allowlist so the daemon never receives `.git`, `.planning`, the tarball or sandbox state, and update every build site (list in Code Examples). Do not use a BuildKit named context with `COPY --from=best-practices`: without the flag BuildKit treats the name as an image reference and tries to pull it from Docker Hub, which this project forbids (`pull_policy: never`).
**Warning signs:** build log says `"/best-practices": not found`; H-14 fails.

### Pitfall 2: Unquoted glob makes a language rule silently always-on
**What goes wrong:** `shell.md` loads into every session, costing context and breaking "load when relevant" (Evidence E7).
**Why it happens:** `- **/*.sh` is invalid YAML; Claude ignores the frontmatter and treats the rule as having no `paths`.
**How to avoid:** quote every glob; add guard rule `bundle_path_globs_are_quoted`; add the behavioural check that `/context` after start lists the always-on files and does NOT list `shell.md` or `java.md`.
**Warning signs:** `shell.md` appears in the "Memory Files" table of `/context` before any file was touched.

### Pitfall 3: A malformed `managed-settings.json` stops Claude from starting
**What goes wrong:** every `claude` run in the sandbox errors out.
**Why it happens:** a managed file that is present but not a JSON object makes Claude Code refuse to start [CITED: code.claude.com/docs/en/managed-settings, "Invalid entries" section]. A root-only (unreadable) file is the opposite failure: the policy is silently not applied [CITED: same page].
**How to avoid:** `RUN node -e 'JSON.parse(require("fs").readFileSync("/etc/claude-code/managed-settings.json","utf8"))'` in the Dockerfile; `chmod 644`; H-14 checks the file is root-owned, world-readable and parses.

### Pitfall 4: Managed deny list drifts from the bundle's skill list
**What goes wrong:** a skill added to the bundle later is not protected, or a removed skill leaves a stale deny.
**How to avoid:** a guard rule that every directory under `best-practices/skills/` has a matching `Edit(//home/sandbox/workspace/state/claude/skills/<name>/**)` entry, and that the `rules/**` entry exists.

### Pitfall 5: `100-` runs before `20-`
**What goes wrong:** hook order is text order, so `100-late` sorts before `20-gsd` [VERIFIED: ran the loop].
**How to avoid:** two-digit prefixes only (`10-`, `20-`, ...); say so in the entrypoint comment.

### Pitfall 6: `die()` prints a misleading hint for hook failures
**What goes wrong:** the existing `die()` appends "Start the sandbox with 'docker compose up' (see SANDBOX.md)", which is wrong when a start hook failed [VERIFIED: base/sbx-entrypoint:22-26, quoted in Code Examples].
**How to avoid:** the hook loop prints its own `[sbx] ERROR: start hook <path> failed; ...` line without the compose hint, then `exit 1`. The hook's own stderr (for example `cp: cannot stat ...`) appears above it.

### Pitfall 7: Words in the entrypoint trip a guard rule
**What goes wrong:** `tests/guard.sh` rule `no_installs_at_container_start` greps `base/sbx-entrypoint` for `\b(npm|npx|bunx|pip|apt-get|apt|curl|wget)\b`, comments included [VERIFIED: tests/guard.sh:99-101]. `no_floating_latest_versions` greps all sandbox files for `:latest|@latest`.
**How to avoid:** keep new comments free of those words; run `bash tests/guard.sh` after each edit. The proposed loop text was checked against both regexes. Extend the first rule's file list to include `claude/start.d/*` so the sync script is held to the same rule.

### Pitfall 8: Path-scoped user rules anchor under the working directory
**What goes wrong:** editing a `.sh` file outside the session's cwd does not load `shell.md`.
**Evidence:** a `.sh` outside cwd did not load the rules; one inside cwd, two levels down, did (Evidence E2). Compose sets `working_dir` to the project folder, so project scripts are covered; files under `state/` are not, which is fine.

### Pitfall 9: Selftest counts and the fake docker are hard-coded
**What goes wrong:** adding checks breaks `tests/host-selftest.sh`: it asserts "14 PASS lines" (line 490), "Summary: 14 passed, 0 failed, 0 not run" (line 493) and "13 passed, 1 failed" (line 523), and the fake `docker` handles only the verbs it already knows (`run` has two branches; no `cp`; `exec` has a closed list).
**How to avoid:** budget a selftest task: update the counts, add fake handlers for `docker cp`, `docker run --network none`, and the new `exec` forms, and add per-check cases (pass, fail) the way existing checks have them. Line 516 also matches `^build -t sbx-claude:local .*/claude$`, which changes if the build command changes.

### Pitfall 10: `claude -p` probes write `state/claude/.claude.json`
**What goes wrong:** H-15 and H-17 run Claude (no login needed) and Claude records first-start data in `.claude.json` [VERIFIED: ran; file contains cached feature flags, `userID`, no onboarding flag, no credentials]. The manual `h07-login.sh` then finds `.claude.json` already present, so its `.claude.json` half stops being a login signal; its `.credentials.json` half still is.
**How to avoid:** accept and note it in `tests/host-checklist.md`, or have the probes run after the manual login. Do not point the probes at a scratch config dir: the point is the real synced folder.

### Pitfall 11: Migrated sandboxes load old rules twice
**What goes wrong:** a sandbox whose migrated `state/claude` still has `CLAUDE.md` with `@AGENTS.md` and `@code-conventions.md` (this very sandbox does) gets the same text from the old imports and from the new rules.
**How to avoid:** nothing to do in this phase (D-07 leaves the existing `CLAUDE.md` alone); add one line to the Phase 5 migration notes (DOC-02): remove those imports once the bundle is in the image.

### Pitfall 12: Hook failures are invisible without a log
**What goes wrong:** `docker compose up -d --wait` only says the container exited; the reason is in `docker logs sbx-<name>`.
**How to avoid:** the error text already goes to stderr (visible in `docker logs`); mention `docker logs` in the `SANDBOX.md` troubleshooting section.

### Hook loop (insert into `base/sbx-entrypoint` before `exec "$@"`)

Existing lines for orientation [VERIFIED: base/sbx-entrypoint:22-26 and :40]: `die() { echo "[sbx] ERROR: $1" >&2; echo "[sbx]        Start the sandbox with 'docker compose up' (see SANDBOX.md)." >&2; exit 1; }` (multi-line in the file) and the final line `exec "$@"`.

```bash
# Start hooks: every executable in /etc/sbx/start.d runs in name order, after the checks above
# and before the command. The first failure stops the start. Names sort as text, so use
# two-digit prefixes (10-, 20-).
hookDir=/etc/sbx/start.d

for hook in "$hookDir"/*; do
  if [ ! -f "$hook" ] || [ ! -x "$hook" ]; then
    continue
  fi

  "$hook" || { echo "[sbx] ERROR: start hook $hook failed; the container was not started." >&2; exit 1; }
done

exec "$@"
```
Behaviour [VERIFIED: ran]: missing folder and empty folder both fall through to the command; order `10-`, `100-`, `20-`; a failing hook prints the error and exits 1 before the command; a non-executable file is skipped. Also update the header comment of the script (it currently lists what the entrypoint does).

### Sync script (`claude/start.d/10-best-practices`, mode 755 in git)

```bash
#!/usr/bin/env bash
set -eu

# Syncs the image's best-practices bundle into the Claude config folder.
# - Runs at every container start, as sandbox, with no network.
# - rules/: full mirror; wiped, then copied fresh from the image.
# - skills/: names installed last time are listed in $manifest. Those are removed, then the
#   bundle's skills are copied and listed again. Other skills are never touched.
# - Never touches CLAUDE.md or projects/*/memory/.
# - SBX_BUNDLE_DIR exists so the script can be tested outside the image.

bundleDir=${SBX_BUNDLE_DIR:-/opt/sbx/best-practices}
configDir=${CLAUDE_CONFIG_DIR:?CLAUDE_CONFIG_DIR is not set}
manifest=$configDir/.sbx-bundle-skills

mkdir -p "$configDir/skills"
rm -rf "$configDir/rules"
cp -R "$bundleDir/rules" "$configDir/rules"

if [ -f "$manifest" ]; then
  while IFS= read -r oldName; do
    case "$oldName" in
      ""|*/*|.*) continue ;;
    esac

    rm -rf "$configDir/skills/$oldName"
  done <"$manifest"
fi

: >"$manifest"

for skillDir in "$bundleDir"/skills/*/; do
  skillName=$(basename "$skillDir")
  echo "$skillName" >>"$manifest"
  rm -rf "$configDir/skills/$skillName"
  cp -R "$skillDir" "$configDir/skills/$skillName"
done
```
Scenarios [VERIFIED: ran in a scratch dir, all as expected]: first start; rename of a rule (old name gone, new present); removal of a skill (listed, so removed); user skill and a GSD-named skill untouched; `projects/*/memory/note.md` and `CLAUDE.md` untouched; hand edit of a synced rule and a synced skill undone; hand-placed rule file wiped; second run idempotent; hostile manifest lines (`../projects`, `.hidden`, blank, `/etc`) ignored by the `case` guard while a legitimate listed name is removed; missing bundle exits 1; unwritable config dir exits 1. The `case` guard is 3 lines; drop it only if the user insists on the shortest form (the manifest is in a folder the agent can write). Order matters: the manifest is truncated after the old entries are removed and each name is appended before its copy, so a mid-run failure never leaves an unlisted orphan.

### Claude image: bundle, hook and managed settings (while `USER root`, before the final `USER sandbox`)

```dockerfile
# --- Best-practices bundle ---
# - Copied from best-practices/ in the repo (the build context is the repo root).
# - Lives in /opt/sbx, outside the mounted folder; root-owned, read-only to sandbox.
# - The start hook copies it into CLAUDE_CONFIG_DIR on every start, so the image version wins.
# - Managed settings deny Claude's own Edit tool on the synced copies. A guard against
#   accidents, not a security boundary: a script the agent runs can still write there.
# - Invalid managed settings stop Claude from starting, so the build parses the file.
COPY best-practices /opt/sbx/best-practices
COPY claude/start.d/10-best-practices /etc/sbx/start.d/10-best-practices
COPY claude/managed-settings.json /etc/claude-code/managed-settings.json
RUN chmod -R u=rwX,go=rX /opt/sbx/best-practices \
    && chmod 755 /etc/sbx/start.d/10-best-practices \
    && chmod 644 /etc/claude-code/managed-settings.json \
    && node -e 'JSON.parse(require("fs").readFileSync("/etc/claude-code/managed-settings.json", "utf8"))'
```
`COPY` of a directory copies its contents and files default to UID/GID 0 [CITED: docs.docker.com/reference/dockerfile]. Constraints from the guard: the last `USER` line of `claude/Dockerfile` must stay `USER sandbox`; `claude/Dockerfile` must keep exactly one `FROM ${BASE_IMAGE}` (H-02), so no multi-stage trick.

### `claude/managed-settings.json`

```json
{
  "permissions": {
    "deny": [
      "Edit(//home/sandbox/workspace/state/claude/rules/**)",
      "Edit(//home/sandbox/workspace/state/claude/skills/pr-reply/**)",
      "Edit(//home/sandbox/workspace/state/claude/skills/merged/**)"

```
- Path is the literal value of the image ENV `CLAUDE_CONFIG_DIR=/home/sandbox/workspace/state/claude` [VERIFIED: claude/Dockerfile:28]. `//` anchors at the filesystem root, so `//home/...` is `/home/...` [CITED: code.claude.com/docs/en/permissions#read-and-edit].
- No `CLAUDE.md` entry: the bundle ships none, so the user's own `state/claude/CLAUDE.md` stays editable (D-07).
- Syntax and effect [VERIFIED: ran 2.1.285 with the same rules in user settings, `--permission-mode bypassPermissions`, `~/.claude` symlinked to the config dir, Evidence E6]: Edit via symlink path, Edit via real path, Write of a new file in `rules/`, `sed -i`, `>>` redirect and `cp` into a denied path were all refused; a control file in the config dir stayed editable. The managed location itself is [CITED: code.claude.com/docs/en/managed-settings: "Linux and WSL: /etc/claude-code/managed-settings.json"]; it could not be exercised here (needs root), so H-18 or the manual pass proves it on the Mac.
- Deny rules block in every mode including `bypassPermissions` [CITED: code.claude.com/docs/en/permission-modes]; managed settings rank above user, project, local and `--settings` [CITED: code.claude.com/docs/en/settings]. The docs state that Edit rules cover Bash file commands Claude recognises (`sed`, `tee`, redirects) but not arbitrary subprocesses (a Python script that opens the file), so say "guard, not boundary" in the SANDBOX.md text.

### Optional stretch: fake Anthropic API for an automated path-scope and deny proof

A 30-line Node script served inside the container proves, with no login and no network, that a path-scoped rule loads after a Read of a matching file and that the managed deny refuses an Edit under bypass. It was run locally against 2.1.285 (Evidence E2, E6). Core:

```js
// tests/host/support/fake-claude-api.js  (served by node inside the test container)
const http = require("http");
const script = JSON.parse(process.env.SCRIPT || "[]");  // [{name, input}, ...] one tool call per step
const send = (res, ev, data) => res.write("event: " + ev + "\ndata: " + JSON.stringify(data) + "\n\n");
http.createServer((req, res) => {
  let body = "";
  req.on("data", (chunk) => { body += chunk; });
  req.on("end", () => {
    const parsed = body ? JSON.parse(body) : {};
    if (!req.url.startsWith("/v1/messages") || req.url.includes("count_tokens") || !parsed.stream) {
      res.writeHead(200, { "content-type": "application/json" });
      res.end(JSON.stringify({ input_tokens: 10, id: "m", type: "message", role: "assistant", model: "m",
        content: [{ type: "text", text: "ok" }], stop_reason: "end_turn", usage: { input_tokens: 5, output_tokens: 1 } }));
      return;
    }
    let step = 0;
    for (const message of parsed.messages || []) {
      for (const block of Array.isArray(message.content) ? message.content : []) {
        if (block.type === "tool_result") { step += 1; }
      }
    }
    const tool = (parsed.tools || []).length > 3 ? script[step] : undefined;
    res.writeHead(200, { "content-type": "text/event-stream" });
    send(res, "message_start", { type: "message_start", message: { id: "m" + step, type: "message", role: "assistant",
      model: parsed.model, content: [], stop_reason: null, usage: { input_tokens: 10, output_tokens: 1 } } });
    if (tool) {
      send(res, "content_block_start", { type: "content_block_start", index: 0, content_block: { type: "tool_use", id: "t" + step, name: tool.name, input: {} } });
      send(res, "content_block_delta", { type: "content_block_delta", index: 0, delta: { type: "input_json_delta", partial_json: JSON.stringify(tool.input) } });
    } else {
      send(res, "content_block_start", { type: "content_block_start", index: 0, content_block: { type: "text", text: "" } });
      send(res, "content_block_delta", { type: "content_block_delta", index: 0, delta: { type: "text_delta", text: "done" } });
    }
    send(res, "content_block_stop", { type: "content_block_stop", index: 0 });
    send(res, "message_delta", { type: "message_delta", delta: { stop_reason: tool ? "tool_use" : "end_turn", stop_sequence: null }, usage: { output_tokens: 5 } });
    send(res, "message_stop", { type: "message_stop" });
    res.end();
  });
}).listen(8799, "127.0.0.1");
```
Drive it with `ANTHROPIC_BASE_URL=http://127.0.0.1:8799 ANTHROPIC_API_KEY=sk-ant-dummy claude -p go --permission-mode bypassPermissions`; assert on the tool results Claude posts back (a denied Edit returns "Permission to edit ... denied" or "File is in a directory that is denied by your permission settings") and on file bytes before and after. This relies on the streaming wire format of the pinned version, so treat it as MEDIUM confidence and keep the manual fallback.
