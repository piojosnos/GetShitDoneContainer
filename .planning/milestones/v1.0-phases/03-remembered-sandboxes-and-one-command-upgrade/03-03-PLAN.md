## Phase Goal

ROADMAP.md Phase 3 goal (verbatim): "The user registers each sandbox once, then starts, stops, and upgrades it by name alone. One command rebuilds the images and recreates the sandbox, and login and history survive."

Not in user-story form; quoted verbatim as in earlier phases.

This plan makes the tool versions visible at a glance: written once into the images at build time, printed by every interactive shell and as the last line of `sbx-upgrade`. Then the docs pass: SANDBOX.md trades the paste-by-hand flow for the scripts, and the test docs and counts catch up with the three plans.

Planning notes:
- D-15 to D-17 and D-22 (` | ` separator, full Python version) are implemented here. The line, for the current pins: `claude 2.1.285 | gsd 1.15.0 | ccusage 20.0.26 | node 24.21.0 | jdk 21.0.12 | mvn 3.9.11 | python 3.12.3`.
- Planner choices (Claude's discretion): the file is `/etc/sbx/tool-versions`, next to the existing pin record `/etc/sbx/versions.env`; the shell hook is one line appended to `/etc/bash.bashrc`, which Ubuntu reads only in interactive shells (its first line returns when PS1 is empty), so no `.bashrc` in the image changes; `sbx-upgrade` reads the file with `docker exec` from the recreated container, so the line shows what the sandbox now runs; each Dockerfile checks the line's shape with a grep, so an empty tool answer stops the build.
- JDK and Python have no version pin of their own: the base asks `java -version` and `python3 --version` once, at build time. H-30 compares the jdk field with the TEMURIN_IMAGE tag and the python field with the container's python3.
- The SANDBOX.md sections that describe the manual flow ("Create a sandbox folder", "Start, enter, stop", "Rebuild without losing login", "Before every start: check the sandbox folder") become the script flow; the raw Compose commands stay as one short "What the scripts run" block. README.md stays untouched (guard rule old_layout_untouched).
- Reversibility: reversible (an image file, one bashrc line, docs).
