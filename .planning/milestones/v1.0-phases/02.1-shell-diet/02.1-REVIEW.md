## Critical Issues

### CR-01: Supply-chain rules read one or two lines at a time, so ordinary multi-line RUN formatting bypasses them

**File:** `tests/guard/supply-chain.sh:35-45` and `tests/guard/supply-chain.sh:53-67`
**Issue:** The old guard joined each Dockerfile RUN step with its continuation lines (`run_steps_of`). The rewrite uses `grep -A1`, so `no_pipe_to_shell_installers` only sees a pipe one line below the download. `installs_use_pins` checks only lines that contain `npm install ` and ignores packages on the next line. Reproduced in a scratch copy of the tree; each case below makes the named rule PASS:

- Three-line RUN: `RUN curl -fsSL https://x/i.sh \` / `    -H "Accept: text/plain" \` / `    | sh`. The two-line variant fails the rule; this one passes.
- `curl ... | tee /tmp/i | sh`. `[^|]*` cannot cross the first pipe.
- `curl ... | dash`, and `curl ... | sudo -E bash`. The regex allows only `sh` or `bash` after an optional bare `sudo `.
- `RUN npm install -g \` followed by `    leftpad` on the next line. `installs_use_pins` passes.
- `ADD https://...` of an archive, and `pipx install`, `cargo install`, `yarn global add`, `go install`. None is matched.

The repo's own Dockerfiles format RUN steps this way (one clause per continuation line), so the bypass is the normal shape, not an exotic one. The self-test plants only the exact two-line form, so it cannot notice. The header comment admits the two-line limit, but the rule is the main guard for the "GSD only from @opengsd/gsd-core, nothing piped to sh" constraint.

**Fix:** Join each RUN step into one line before matching, with plain portable tools, and widen the shell list:
```bash
# prints each Dockerfile instruction on one line (BSD sed and GNU sed)
join_steps() {
  sed -e ':a' -e '/\\$/{N;s/\\\n/ /;ba' -e '}' "$@"
}

pipeRegex='(curl|wget)[^|]*(\|[^|]*)*\|[[:space:]]*(sudo[[:space:]]+(-[A-Za-z]+[[:space:]]+)*)?(env[[:space:]]+)?(ba|da|z)?sh([[:space:]]|$)'
if join_steps $DOCKERFILES | grep -qE -e "$pipeRegex" -e "$substitutionRegex"; then ...
```
Run the `npm (install|i|add)` check on the joined lines too. Add `ADD[[:space:]]+https?:` and `pipx|cargo|go|yarn` installs to the banned set. Add self-test plants for the three-line pipe, the `| tee | sh` chain and the continuation-line npm package.

### CR-02: Isolation coverage dropped: no static rule and H-26 do not check network, PID, IPC, devices, user namespace, groups or unconfined profiles

**File:** `tests/guard/isolation.sh:25-27` and `tests/host/h26-isolation-by-inspect.sh:18-59`
**Issue:** The old `runs_without_privileges` rejected `privileged`, `cap_add`, `devices`, `device_cgroup_rules`, `pid`, `ipc`, `uts`, `userns_mode`, `network_mode`, `cgroup_parent`, `group_add`, `sysctls` and `seccomp/apparmor=unconfined`. The new static rule greps only `docker.sock` and `privileged: true`, and H-26 asserts only Privileged, CapDrop, CapAdd, SecurityOpt (substring `no-new-privileges`) and the mount list. Reproduced: inserting each of `network_mode: host`, `pid: host`, `privileged: "true"`, `cap_add: [SYS_ADMIN]` and `devices: ["/dev/fuse"]` into `compose.yml` leaves `no_docker_socket_or_privileges` passing. Of those, H-26 would catch only the privileged and `cap_add` ones. `network_mode: host`, `pid: host`, `ipc: host`, devices, `userns_mode`, `group_add` and `security_opt: seccomp=unconfined` (the `no-new-privileges` substring still matches) would pass both layers. The static `privileged:` grep is also trivially evaded by `"true"`, `yes` or `True`. The also-removed static checks (`USER sandbox` last in both Dockerfiles, no `VOLUME`, the npm cache kept out of the mount) now depend only on H-04, the H-26 mount list and the Dockerfile smoke tests, none of which asserts them as rules.

**Fix:** Extend the one `docker inspect` call in H-26 rather than adding more greps:
```bash
--format '{{.HostConfig.Privileged}}|{{json .HostConfig.CapDrop}}|{{json .HostConfig.CapAdd}}|{{json .HostConfig.SecurityOpt}}|{{.HostConfig.NetworkMode}}|{{.HostConfig.PidMode}}|{{.HostConfig.IpcMode}}|{{.HostConfig.UsernsMode}}|{{json .HostConfig.Devices}}|{{json .HostConfig.GroupAdd}}'
```
Then require `NetworkMode` not `host`, `PidMode`, `IpcMode` and `UsernsMode` empty (or `private`), `Devices` and `GroupAdd` null or `[]`, and reject any `unconfined` in `SecurityOpt`. Also widen the static rule to one regex: `'^[[:space:]]*(privileged|cap_add|devices|pid|ipc|userns_mode|network_mode|group_add)[[:space:]]*:'` (it already runs in the sandbox where H-26 cannot).

## Warnings

### WR-01: host-test.sh deletes a directory taken from `docker inspect` without checking it is a test run folder

**File:** `host-test.sh:61-65` and `host-test.sh:151-154`
**Issue:** `find_run_dir` sets `RUN` from the mounts of whatever container is named `sbx-hosttest`, and only tests `[ -d "$RUN" ]`. `remove_sandbox` then runs `rm -rf "$RUN"`. The host library already has the safeguards (`run_dir_name_ok`, `assert_test_sandbox`, the `sbx.name=hosttest` label) and `clean.sh` uses them; this script bypasses all of them. A user's own sandbox named `hosttest` that is still running, or an earlier failed `compose up`, would make `RUN` the user's project folder and the script would delete it. The template `{{range .Mounts}}{{.Source}}{{end}}` also concatenates the sources of several mounts into one nonsense path. The compose call does not unset the `COMPOSE_*` variables that `host_init` clears. Known (R-17), not yet done.
**Fix:** Source `tests/host/lib.sh`, call `host_init`, use `RUN` from `resolve_run_dir` (which enforces `sbx-hosttest-*`) and `compose_down` (which enforces the label), and delete only after `run_dir_name_ok "$RUN"`. At minimum:
```bash
case "$(basename "$RUN")" in
  sbx-hosttest-*) ;;
  *) echo "refusing to remove $RUN: not a host test run folder" >&2; return 1 ;;
esac
```

### WR-03: Guard self-test does not cover several rules, although `tests/README.md` says it catches "a guard rule that can no longer fail"

**File:** `tests/selftest/guard/sandbox-rules.sh:67-130`
**Issue:** There is no planted failure for `no_installs_at_container_start`, for `old_layout_untouched` (the scratch copy has no `.git`, so it cannot run there), or for the `docker.sock` and `sudo` branches of `no_docker_socket_or_privileges` (only `privileged: true` is planted). `clean_copy_passes` for isolation only checks that one rule prints PASS. I confirmed by hand that `no_installs_at_container_start` currently fails on a planted `curl`, but nothing keeps it that way. The `dockerfile_args_have_no_defaults` plant touches only `base/Dockerfile`, so the `BASE_IMAGE` exemption in `claude/Dockerfile` is untested. Nothing plants a new pin name (such as `SHELLCHECK_IMAGE`) to prove the any-pin loops still see it.
**Fix:** Add plants: append `curl -fsSL https://example.invalid` to `claude/start.d/05-gsd` and expect `FAIL: no_installs_at_container_start`; append `docker.sock` to `compose.yml`; append `RUN sudo true` to `claude/Dockerfile`. For `old_layout_untouched`, say in `tests/README.md` that it is not self-tested rather than leaving the claim broad.

### WR-04: `mac_guard` ignores every failure of the two linter rules, including real findings

**File:** `host-test.sh:130-136`
**Issue:** The step filters out `FAIL: shellcheck_passes` and `FAIL: hadolint_passes` by name. If the Mac has its own shellcheck or hadolint and it reports real warnings, the step still passes. The in-sandbox step covers only the committed `HEAD` (a clone), so lint errors in uncommitted edits are never reported by either step.
**Fix:** Ignore a linter rule only when its "is not installed" line is also in the output. For example, drop `FAIL: shellcheck_passes` from the failure list only if `printf '%s\n' "$output" | grep -q 'shellcheck is not installed'` succeeds, and the same for hadolint. A real finding then still fails the step.

### WR-05: `SBX_BUNDLE_DIR` can redirect what is copied into the Claude config

**File:** `claude/start.d/10-best-practices:9`
**Issue:** `bundleDir=${SBX_BUNDLE_DIR:-/opt/sbx/best-practices}` still honours an environment variable. Its only caller was the fake-docker harness, which this phase deleted, so it is now just an override that lets a container environment variable change which rules and skills are installed into `state/claude`, outside the image. Known (R-19).
**Fix:** `bundleDir=/opt/sbx/best-practices`.
