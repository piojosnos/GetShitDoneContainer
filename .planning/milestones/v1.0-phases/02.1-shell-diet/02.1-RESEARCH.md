### Locked Decisions

**Linters (shellcheck, hadolint)**
- **D-01:** Both are installed in the `sbx-base` image, pinned in `versions.env` like every other tool (no `latest`, same pin style as the existing toolchain). The guard runs them directly. Every new-layout sandbox gets them.
- **D-02:** A missing linter is a guard failure, never a silent skip: the guard prints one `FAIL:` line naming the missing tool. A check that quietly skips almost never runs.
- **D-03:** Migrating the dev work to a new-layout sandbox is NOT required to finish this phase. While execution runs in the old sandbox, the guard reports exactly the "linter missing" failures from D-02 and nothing else; executors treat those as expected there. The full green guard run (linters included) is a Mac verification step: after `./build.sh`, run `bash tests/guard/run-all.sh` inside a new-layout sandbox via `docker exec`. Migrating is optional and can happen any time after that rebuild.

**Self-tests that stay or go**
- **D-04:** `tests/selftest/host/` and `tests/selftest/host/support/fake-docker` are deleted (roadmap criterion 2).
- **D-05:** `tests/selftest/bundle/` is deleted now: the bundle leaves this repo in Phase 2.2, so keeping it means maintaining it twice.
- **D-06:** `tests/selftest/entrypoint/` stays. It runs the real start code (`base/sbx-start-lib.sh`, `base/sbx-entrypoint`, `claude/start.d/05-gsd`) as plain bash in a temp folder, without Docker. The Mac checks H-16 and H-17 already cover the main paths.

- **D-10:** `tests/host-checklist.md` is trimmed to the host checks that remain, and gains the new `docker inspect` isolation check (from the approved cut of the mount and privilege rules).

**Comment format**
- **D-11:** Every commented block uses this shape; each rule line is exactly 80 characters including the leading `#`:

```bash
# ------------------------------------------------------------------------------
# run_groups SUITE_DIR GROUP...: runs each group and counts its FAIL lines
# ------------------------------------------------------------------------------
# A group that crashes without a FAIL line counts as one failure.
# So a crash is never silent.
# ------------------------------------------------------------------------------
run_groups() {
```

  - Title line: what the block does (not necessarily caps).
  - Comment block: at most two lines, only the "why".
  - When there is no "why", drop the second block: the title sits between two rules.

```bash
# ------------------------------------------------------------------------------
# print_summary: prints the summary and exits 0 only when every rule held
# ------------------------------------------------------------------------------
print_summary() {
```

- **D-12:** The file header at the top of each script uses the same shape: the purpose is the title, usage (and at most one other line) goes in the comment block. The long header bullet lists (for example `tests/guard/run-all.sh`) go away.
- **D-13:** The format applies to all shell in scope (shipped scripts, guard, host checks, entrypoint self-test). Dockerfiles and `compose.yml` follow the same banner shape where they have section comments.

## Summary

The phase is mostly deletion with one new capability. The new capability is two pinned linters in `sbx-base` plus a guard group that runs them. Everything else removes rules, self-tests and comment noise. Measured baseline this session: the guard has 45 rules in 9 group files (1762 lines in `tests/guard/`), all PASS, 1 second. `tests/selftest/guard/` is 766 lines (12 s). `tests/selftest/entrypoint/` is 736 lines, 73 PASS lines in 29 case groups, under 1 second. After the approved cuts 17 rules survive (exactly the roadmap's "about 17"), plus 2 new linter rules.

Linters: use the project's own image-pin pattern. `koalaman/shellcheck:v0.11.0` and `hadolint/hadolint:v2.15.1` are both multi-arch (linux/amd64 and linux/arm64) OCI indexes whose only payload is one static binary (`/bin/shellcheck`, `/bin/hadolint`). Adding them as `SHELLCHECK_IMAGE` and `HADOLINT_IMAGE` (tag plus index digest) and `COPY --from=` them into `/usr/local/bin` is the same mechanism already used for `UV_IMAGE` and `TEMURIN_IMAGE`: no per-arch asset names, no checksum parsing (shellcheck publishes no checksum file at all), digest verified by Docker, `build.sh` and the pin guard rules need no change. Both tools were downloaded and run in the dev sandbox (arm64) this session, so the cleanup effort is measured, not guessed: shipped scripts and Dockerfiles are nearly clean; at `-S warning` the surviving test scripts need one real fix.

Two real traps found while measuring: (1) `severity=` in `.shellcheckrc` is ignored by shellcheck 0.11.0, so `-S warning` must be on the command line; (2) `shellcheck -x -P SCRIPTDIR` hangs (30 s timeout reproduced) on `tests/selftest/entrypoint/*` with the current tree, so do not use `-x`; silence SC1090/SC1091 in `.shellcheckrc` instead. Also, the interactive tool shell here replaces `grep` with an embedded ugrep function whose handling of `\|` and multiple `-e` differs from GNU/BSD grep; verify every proposed grep form through a real `bash script` run, not ad hoc in the tool shell.

**Primary recommendation:** Tracer first: land the linter pins (after a human pin approval row), `base/Dockerfile` install, `.shellcheckrc`, `.hadolint.yaml` and `tests/guard/linters.sh` with the glob runner. Then do the cuts in dependency order (move `fake-gsd`, remove guard rules that name the doomed folders, delete folders, rewrite the surviving rules as plain greps, add H-26), then the entrypoint self-test diet, then the comment rewrite last (so only surviving code is rewritten), then the C13 re-scan as proposals only.


```dockerfile
COPY --from=shellcheck --chmod=755 /bin/shellcheck /usr/local/bin/shellcheck
COPY --from=hadolint --chmod=755 /bin/hadolint /usr/local/bin/hadolint
```
and add `&& shellcheck --version >/dev/null && hadolint --version >/dev/null` to the existing last-RUN smoke test (it already ends with the `test -z "$(ls -A /home/sandbox/workspace)"` check, which must stay last). `COPY --chmod` is already used in `claude/Dockerfile` (`COPY --chmod=644 versions.env /etc/sbx/versions.env`), so BuildKit support is proven on the Mac.

The guard rule `dockerfile_args_have_no_defaults` requires each `FROM` to match `^FROM \$\{[A-Z_]+\}( AS [a-z]+)?$` [VERIFIED: tests/guard/supply-chain.sh:203-223]; the two new FROM lines satisfy it. `pins_are_exact` image regex `^[A-Z_]+_IMAGE=[a-z0-9][a-z0-9./-]*:[A-Za-z0-9._-]+@sha256:[0-9a-f]{64}$` [VERIFIED: tests/guard/supply-chain.sh:184-198] accepts both new lines.

## Common Pitfalls

### P1: H-25 fails on the Mac because the bare-base-build regex does not know the new pins
**What goes wrong:** the bare `docker build base/Dockerfile` without `build.sh` stops at a blank `FROM`, and BuildKit may name `SHELLCHECK_IMAGE` or `HADOLINT_IMAGE` first.
**How to avoid:** extend the alternation in `h25-images-match-versions.sh:91`.
**Warning signs:** H-25 reports "did not stop naming a missing pin" with a log under `logs/h25-bare-base.log`.

### P2: a deleted folder leaves a literal glob in a guard scan
**What goes wrong:** `grep` is given the unmatched pattern, `nowhere_matches` returns 1, and a rule FAILs for no content reason (dependency 3).
**How to avoid:** change file lists in the same commit as the deletion; run the guard after every commit.

### P3: `shellcheck -x` hangs; `severity=` in `.shellcheckrc` does nothing
See Linters, pitfalls 1 and 2. Command-line `-S warning`; rc `disable=` list; no `-x`.

### P4: the tool shell's `grep` is not GNU grep
In this dev sandbox's interactive tool shell `grep` is a function that runs an embedded ugrep; the same ERE with several `-e` and `\|` gave different results there than in `bash script.sh` (GNU grep 3.12). Guard scripts run under real `bash`, so they use GNU grep here and BSD grep on the Mac. When prototyping greps, run them through `bash -c '...'` or `/usr/bin/grep`, and prove them with the self-test (planted violation), not by eye. Note the rule regexes use `\|` as a literal pipe, which GNU and BSD ERE both treat so; keep that.

### P5: Dockerfile parser directive pushed down by a banner
See Comment format: `# check=skip=InvalidDefaultArgInFrom` must stay line 1 of `base/Dockerfile`.

### P6: dropping the `Depends on:` header line leaves prose pointing at it
`tests/host/run-all.sh:21` says checks name what they need in a `# Depends on:` line. Edit the sentence with the header fold.

### P7: wholesale `skills/**` deny changes documented behavior
`SANDBOX.md:187` promises editable own skills. Either fix the sentence (recommended if the user keeps C6 as approved) or keep per-skill entries. See Open Question 1.

### P8: the old sandbox "expected failure" masks a real linter failure
D-03 says executors treat the two "missing" FAILs as expected. They must still check that those are the ONLY FAILs and that no other rule line is `FAIL:`. The self-test fake-linter cases (plan 01) prove the rule can fail for real when a tool exists.

```bash
  PATH="$WORK/emptybin" /bin/bash "$WORK/repo/tests/guard/linters.sh" >"$WORK/missing.out" 2>&1 </dev/null
  expect "linters: a missing shellcheck fails the rule" has_text "$WORK/missing.out" "FAIL: shellcheck_passes"
  expect "linters: the missing tool is named" has_text "$WORK/missing.out" "shellcheck is not installed"
}
```
(`/bin/bash` absolute so the empty `PATH` does not hide the shell; the group's own `grep`, `sed` are then not found, so give the case a `PATH` that holds symlinks to `grep` and `sed` only, or run the check function by sourcing the group.
