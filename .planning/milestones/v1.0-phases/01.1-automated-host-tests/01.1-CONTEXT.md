# Phase 1.1: Automated host tests - Context

**Gathered:** 2026-10-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Turn the manual Mac checklist (`tests/host-checklist.md`, H-00 to H-13 plus Coexistence) into scripts under `tests/host/`.

- `tests/host/run-all.sh` is fully unattended: it builds the images, creates a throwaway sandbox, runs every check that needs no human, prints a PASS/FAIL line per check and a summary, and exits non-zero on any failure.
- The steps that need a human (Claude login, `claude --continue`, `claude doctor`) stay in the checklist doc as a short manual pass, each driven by a small helper script.
- Passing both on the Mac closes Phase 1's deferred host verification (HT-05).

Not in scope: CI (Phase 6), new sandbox features, changes to the images or `compose.yml` beyond what a failing check proves is broken.

</domain>

<decisions>
## Implementation Decisions

### Unattended vs attended
- **D-01:** `run-all.sh` never waits for input. Nothing in it is interactive.
- **D-02:** Attended steps live in `tests/host-checklist.md` (shrunk) as a manual pass with clear instructions, run after `run-all.sh` against the same test sandbox. When a step needs more than a command or two, it gets its own helper script under `tests/host/manual/`, separate from the automated checks. Expected helpers:
  - login (H-07): opens `claude` in the test sandbox; after the user exits, checks automatically that `.claude.json`, `.credentials.json` and `projects/` are in `state/claude`, `claude auth status` shows logged in, and there is no `~/.claude.json` in the container home.
  - rebuild and resume (H-09 login part): rebuilds the images (optionally `--no-cache`), recreates the container, checks `claude auth status`, then opens `claude --continue` for the user to confirm the session resumes.
  - doctor (H-13 part): opens `claude doctor` for the user to confirm auto-updates are disabled.
- **D-03:** `run-all.sh` ends (pass or fail) by printing the manual-pass commands and the cleanup command, ready to copy and paste.
- **D-04:** This changes the earlier roadmap wording ("the runner pauses before H-07"). HT-02, HT-03 and Phase 1.1 success criteria 2 and 3 in `ROADMAP.md` / `REQUIREMENTS.md` were reworded to match on 2026-10-04.

### Throwaway sandbox
- **D-05:** The test folder comes from `mktemp -d` with a readable prefix plus a timestamp, for example `${TMPDIR:-/tmp}/sbx-hosttest-YYYYMMDD-HHMMSS.XXXXXX`. A fresh folder per run; never reused. (BSD `mktemp` needs an explicit template; the `X`s must be at the end.)
- **D-06:** The test sandbox has a fixed name (for example `SBX_NAME=hosttest`, container `sbx-hosttest`), so the manual helpers find it by name. A helper can read the test folder back from the container's mount (`docker inspect`), so no pointer file is needed.
- **D-07:** **Never delete anything on the filesystem.** No `rm` of the test folder, ever, pass or fail. The runner prints the exact `rm -rf <folder>` command for the user to run. This also covers anything H-10 might create: point H-10's nonexistent path inside the run folder so the same printed command cleans it up.
- **D-08:** Containers may be removed by the scripts. The runner removes a leftover `sbx-hosttest` container from an earlier run before starting (with `docker compose down`, never `-v`). At the end it leaves the test sandbox running, so the manual pass can use it; the printed cleanup includes stopping it. It must only ever touch the test container: match it by its exact name (and the `sbx.name=hosttest` label), never by pattern.
- **D-09:** Images use the real tags `sbx-base:local` and `sbx-claude:local`, because those are what is being verified. Running real sandboxes are not affected; they pick up a new image only when recreated. The scripts never delete these images.

### Shared library, order and failure handling
- **D-10:** A shared `tests/host/lib.sh` holds defaults, setup and teardown, the PASS/FAIL printing, and small helpers. Each check script sources it, so any check can run on its own against an existing test sandbox.
- **D-11:** Order: run the independent checks first, and keep going when one fails, so one run reports as much as possible. Chained checks (those that rely on an earlier step, such as recreate, rebuild, persistence after down/up) come after, and the chain stops at its first failure. A failed image build stops everything.
- **D-12:** Each check script states its dependencies explicitly in a header comment, `# Depends on: <check IDs or "nothing">`, and the order in `run-all.sh` follows those lines.

### Checks a script cannot see directly
- **D-13:** Interactive checks become manual steps (D-02). Non-interactive judgment checks get automated proxies:
  - H-02 "Claude image sits on the base": the base image's layer digests are a prefix of the Claude image's layers, and `claude/Dockerfile` has exactly one `FROM ${BASE_IMAGE}`.
  - Coexistence: snapshot the old-layout containers (`cc_*`) from `docker ps -a` before and after the run and compare; `git status` shows no change under `ClaudeCode/` or `OpenCode/`.
  - H-00: prints the Compose and Docker Desktop versions as info, passes if Compose is v2.

### Claude's Discretion
- Exact names: test sandbox name, folder prefix, helper script file names, `lib.sh` function names.
- Which of H-05 to H-13's sub-steps are automated vs manual, as long as everything that needs no human is in `run-all.sh`. In particular H-08 (history survives recreate): automate it if a faithful non-interactive way exists (for example a pty via `script`, or `bash -i`), otherwise make it a manual helper.
- Name of the optional variable for the slow `--no-cache` rebuild (roadmap already fixes that it is optional and off by default).
- Where build logs go (quiet into a log file inside the run folder, printed on failure, is a reasonable default).
- Whether `tests/guard.sh` gains a rule about the new scripts.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `tests/guard.sh`: header comment style, `set -u`, `cd "$(dirname "$0")/.."`, small named helper functions; a model for `lib.sh` and the check scripts.
- `tests/host-checklist.md`: every command and pass condition already written; each check maps to one script.

### Established Patterns
- Plain bash, short scripts, bash 3.2 and BSD tools on the Mac (no `declare -A`, no `mapfile`, no GNU-only `sed -i`/`stat -c` on the host side; `stat -c` inside the container is fine).
- Compose needs both `SBX_NAME` and `SBX_DIR` for every subcommand, including `down`.
- The container is named `sbx-<name>` and labelled `sbx.name=<name>`.

### Integration Points
- The scripts drive `docker build`, `docker compose` (from the repo root) and `docker exec` against `sbx-hosttest`.
- Phase 1.2 and later phases verify their image changes by running `tests/host/run-all.sh`.

</code_context>
