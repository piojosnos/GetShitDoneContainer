# Phase 01.3: Code Review Report

**Reviewed:** 2026-10-05
**Depth:** standard
**Files Reviewed:** 30
**Status:** issues_found

## Summary

The refactor is faithful. I diffed every converted script against `d375d39` and traced each old `set --` / `fail ... exit` path to its `add_problem` / `report_check` / `stop_check` equivalent. Message text, ordering of details, exit codes and PASS/FAIL line text are unchanged. This includes the manual helpers (the question prompts, the `answer: <none>` detail, and the leading newline before each y/N prompt). `tests/entrypoint-selftest.sh` (all cases), `tests/host-selftest.sh` and `tests/guard.sh` all pass in this sandbox, and `bash -n` is clean on every file. No security issues found.

The two real problems are:
1. The new "a hook is never skipped silently" guarantee has a hole: broken symlinks and other non-regular entries are still skipped silently, and SANDBOX.md states the stronger claim.
2. `run_timeout` (code moved into `lib-sandbox.sh` unchanged) does not kill the command it wraps when that command is a shell function, so a timed-out `compose up` keeps running.

## Warnings

### WR-01: A broken symlink (or fifo/socket) in the hook folder is still skipped silently, contradicting SANDBOX.md

**File:** `base/sbx-entrypoint:76`
**Issue:** `run_start_hooks` skips anything that fails `[ -f "$hook" ]` before it reaches the new "not executable" error. `-f` follows symlinks, so a dangling symlink, a fifo, a socket and a device node are all `continue`d without a message. I confirmed it:

```
ln -s /nonexistent h/10-dangling; mkfifo h/20-fifo
( . base/sbx-entrypoint; hookDir=h; run_start_hooks ); echo rc=$?   # rc=0, nothing printed
```

`SANDBOX.md:168` says "A hook is never skipped silently; only folders and names that start with a dot are ignored", and `base/Dockerfile:76` says the entrypoint "runs every file here". Both are false for these entries. A dangling hook link is exactly the "image lost its hook" failure this behaviour change exists to catch, and it is the one case that still starts a half-configured sandbox (for example without the bundle sync) with exit 0. The self-test covers a link to a non-executable file, but not a dangling link.

**Fix:** Skip only directories and the unmatched-glob literal; everything else must be an executable file.

```bash
for hook in "$hookDir"/*; do
  if [ ! -e "$hook" ] && [ ! -L "$hook" ]; then
    continue   # the glob matched nothing
  fi

  if [ -d "$hook" ]; then
    continue
  fi

  if [ ! -f "$hook" ] || [ ! -x "$hook" ]; then
    echo "[sbx] ERROR: start hook $hook is not executable; the container was not started." >&2
    exit 1
  fi
  ...
```

Then add a dangling-link case to `tests/entrypoint-selftest.sh`. If the permissive behaviour is intended instead, weaken the SANDBOX.md and Dockerfile wording to "regular files".

### WR-02: `run_timeout` leaves the timed-out command running when it wraps a shell function

**File:** `tests/host/lib-sandbox.sh:28-52`
**Issue:** `"$@" &` backgrounds a function in a subshell, and the watcher's `kill "$commandPid"` kills only that subshell, not the `docker compose` it spawned. I reproduced it with `slowcmd() { sleep 7; }; run_timeout 1 slowcmd`: it returns 143 but the `sleep 7` process is still alive afterwards. `compose_up` calls `run_timeout 120 compose_cmd up -d --wait`, and `compose_cmd` is a function, so after a 120 s timeout the orphaned `docker compose up --wait` keeps running while the next step (for example `compose_down` in `restart_test_sandbox`, or the H-10 restart) acts on the same project. This code predates the phase but was moved here unchanged; the layout phase now owns it.

**Fix:** Run the command in its own process group and signal the group, or make `compose_up` call an external command rather than a function, for example:

```bash
run_timeout 120 env SBX_NAME=hosttest SBX_DIR="$RUN" docker compose -f "$REPO_DIR/compose.yml" up -d --wait
```

(This is the form H-10 already uses.) For the general case, kill the children as well: `pkill -P "$commandPid"` before `kill "$commandPid"` (BSD `pkill -P` works on macOS).

## Info

### IN-01: Missing blank line before control flow, against the project's own convention

**File:** `tests/host/lib-report.sh:25`, `tests/host/lib-sandbox.sh:37,39,113,134`, `tests/host/lib-docker.sh:16`, `tests/host/lib.sh:83`, `tests/host/run-all.sh:47,60,120,188,214`, `tests/host/coexistence.sh:54`, `tests/host/h01-native-arch.sh:31,42,55`, `tests/host/h02-claude-on-base.sh:37,59`, `tests/host/h08-history-survives-recreate.sh:31`, `tests/host/manual/h09-rebuild-resume.sh:28`
**Issue:** Each `if` / `for` / `while` listed directly follows an assignment or command line with no blank line, but the conventions require a blank line before every control-flow statement. A layout phase is the place to apply it uniformly. Most are an assignment followed by the `if` that tests it.
**Fix:** Insert a blank line before each listed statement. Output is unaffected.

### IN-02: `stop_check` silently discards problems already collected

**File:** `tests/host/lib-report.sh:77-80`
**Issue:** `stop_check` calls `fail "$@"` and exits without looking at `problemList`. A check that calls `add_problem` and later reaches a `stop_check` would lose the earlier problems. No current check does this, but the new shared API makes it easy to hit as checks grow (for example a helper with a `stop_check` after an earlier `add_problem`).
**Fix:** Either document it in the lib header ("call stop_check before any add_problem"), or have `stop_check` append `"${problemList[@]}"` to the details when the list is non-empty (count tested first, for bash 3.2).

### IN-03: The entrypoint self-test never exercises the Main block's success path or its order

**File:** `tests/entrypoint-selftest.sh:187-205`
**Issue:** `case_direct_run_checks` only proves that a run with no mount stops at the first check. Nothing checks that, on success, the steps run in the order `check_workspace_mount`, `check_project_and_state_folders`, `create_state_dirs`, `run_start_hooks`, `exec "$@"`. A reordering (for example hooks before the folder checks, or creating state dirs before the project-folder check) would pass every case. Also, `case_folder_and_dotfile_skipped` writes `.hidden` but never asserts its marker was not created; it passes only because a 644 dotfile would have turned the exit code to 1.
**Fix:** Add a case that sources the script in a subshell, overrides `is_mount`, `ws`, `state` and `hookDir` to fixture folders, and runs the four steps in the Main order with a command that touches a marker. Or add an `SBX_*` test seam that lets a direct run use fixture paths. Assert `test ! -e "$WORK/skipped/hidden-ran"` as well.

### IN-04: Dockerfile hook comment is inaccurate and over-long

**File:** `base/Dockerfile:76`
**Issue:** "runs every file here" is not what the code does (folders and dotfiles are skipped, see WR-01), and the line is far longer than its neighbours, which wrap near 90 columns.
**Fix:**

```
# - The entrypoint runs every file here at container start, in name order.
#   A file that is not executable stops the start; folders and dotfiles are skipped.
```
