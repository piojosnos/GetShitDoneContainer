## User Constraints (from CONTEXT.md)

### Locked Decisions

**Splitting scripts into functions**
- **D-01:** Every script gets the layout: header comment, 80-column section banners, and a `Main / Entry Point` banner over the top-level flow.
- **D-02:** Split code into functions only where there are separate pieces that each get a clear name. A cohesive block stays whole, even in a short script; do not force a split where there are not two or more distinct things.
- **D-03:** When a piece also happens in other scripts, generalize it a little and move it to a library (see D-07 to D-09).

**Failure reporting in the checks**
- **D-04:** Find the best, cleanest way for a check to collect and report its result, and use it in every host check (symmetry). The starting point is the pattern H-14 to H-18 use today: `add_problem` while checking, `report_check` at the end. Single-assertion checks that call `pass`/`fail` directly today move to the same pattern.
- **D-05:** No `set -- "$@"` failure collection is left in any check.
- **D-06:** PASS and FAIL lines, their order and exit codes stay exactly as today.

**Library organisation**
- **D-07:** Split `tests/host/lib.sh` now into topic libraries. Each library file has one topic or purpose; its functions are cohesive with each other. From the file name a reader can infer what the functions do, and is never surprised to find a given function in a given library.
- **D-08:** A library is a set of reusable utilities. A function belongs in a library only when several scripts really use it; the more callers, the better. Do not move everything into libraries: hundreds of functions each used twice is a failure. One-script helpers stay in the script.
- **D-09:** Each library function has one well-defined behaviour and responsibility, and a short comment saying what it does. The goal is a small collection of libraries that make writing and reading the checks easier.

**Behaviour preservation**
- **D-10:** The phase is a pure restructure except for D-11. Proof: `tests/host-selftest.sh`, `tests/bundle-selftest.sh` and `tests/guard.sh` give identical output before and after (temp names stripped), and `tests/host/run-all.sh` passes on the Mac.
- **D-11:** WR-04 fix in `base/sbx-entrypoint`: a regular file in `/etc/sbx/start.d` that is not executable stops the start with an `[sbx] ERROR` line and a non-zero exit, like a failing hook. Folders and dotfiles stay ignored. Covered by a test case.

## Summary

The phase is a mechanical restructure of about 1,500 lines in 24 files plus one fail-closed behaviour change. The reference implementations already exist in the repo: `claude/start.d/10-best-practices` (layout) and `tests/host/h14` to `h18` plus `lib-bundle.sh` (reporting pattern, topic library). Three facts shape the plan more than any others: (1) `tests/host-selftest.sh` is frozen but sources only `tests/host/lib.sh` and calls `host_init`, `make_run_dir`, `claude_pin` and `expected_arch` through it, so those four must stay reachable from `lib.sh`; (2) the same selftest copies only the top-level `tests/host/*.sh` into a scratch repo, so libraries must be flat files next to `lib.sh`; (3) the three required proof scripts print only rule or case names, so they cannot prove that FAIL texts survived. A full-transcript harness (built and validated this session) closes that gap.

Library split (recommended): `lib.sh` keeps the run folder and environment functions and loads the other topic libraries; new flat siblings `lib-report.sh` (PASS/FAIL and result collection, text formatting), `lib-sandbox.sh` (guards and lifecycle of the test sandbox), `lib-docker.sh` (image builds and facts, old-container snapshot); `lib-bundle.sh` stays as is; a manual-only `tests/host/manual/lib-manual.sh` holds the prompt and terminal helpers (it must live under `manual/` because the guard bans `read` in `tests/host/*.sh`). Reporting pattern: keep `add_problem` and `report_check` unchanged, add `report_result` (non-exiting variant for helpers with several results), `stop_check` (print FAIL and exit 1 for a precondition or a decision-table outcome) and `pass_check`. Every check then ends in `report_check`, `stop_check` or `pass_check`, none uses `set --`.

WR-04 is a four-line change, but it cannot be tested on Linux today: the script hard-codes `/home/sandbox/workspace` (must be a mount) and `/etc/sbx/start.d`, and neither frozen selftest runs it. Recommended seam: move the hook loop into `run_start_hooks`, wrap the Main calls in `if [ "${BASH_SOURCE[0]}" = "$0" ]; then ... fi` so a test can source the script in a subshell, override `hookDir` and call the function. Put the cases in a new `tests/entrypoint-selftest.sh` (adding them to `bundle-selftest.sh` would change that script's output and break D-10).

**Primary recommendation:** Do the library split first as a pure move (proof: transcript diff empty), then convert checks in disjoint batches using the five-verb reporting API, then the entrypoint with its new selftest, then the Mac run as the final human checkpoint.

### Reporting pattern (D-04 to D-06)

Today's pattern [VERIFIED: tests/host/lib.sh:308-330]:
```bash
problemList=()
add_problem() { problemList+=("$1"); }
report_check() {  # ID FAIL_SUMMARY PASS_TEXT
  ...
  if [ "${#problemList[@]}" -gt 0 ]; then
    fail "$checkId" "$failSummary" "${problemList[@]}"
    exit 1
  fi
  pass "$checkId" "$passText"
  exit 0
}
```
H-14 to H-18 call `add_problem` in functions and end with one `report_check` (H-16 and H-17 also have 4 `fail`+`exit 1` precondition stops). The ten older checks use `set -- "$@"` (H-01, H-02, H-03, H-05, H-06, H-09, H-11, H-12, H-13, Coexistence; manual H-07 too) or call `pass`/`fail` directly (H-00, H-04, H-08, H-10, the manual helpers).

Recommended API (keeps `add_problem`/`report_check` signatures, so H-14 to H-18 and `lib-bundle.sh` need no change):

| Function | Use when | Behaviour |
|----------|----------|-----------|
| `add_problem MSG` | a failed assertion; the check goes on | appends to `problemList` (unchanged) |
| `report_check ID FAIL_SUMMARY PASS_TEXT` | the normal end of a check | `report_result`, then `exit` with its status (unchanged output and exit codes) |
| `report_result ID FAIL_SUMMARY PASS_TEXT` NEW | a helper prints several results (manual H-07, H-19) | prints FAIL with the collected problems or PASS, clears `problemList`, returns 1 or 0, does not exit |
| `stop_check ID SUMMARY [DETAIL...]` NEW | a precondition fails and the rest is meaningless, or a decision-table outcome (H-00, H-08, H-10, H-16, H-17, manual H-09) | `fail "$@"` then `exit 1` |
| `pass_check ID TEXT` NEW | a check that ends with an unconditional PASS after its `stop_check` steps (H-08, H-10) | `pass` then `exit 0` |

Exact-output rules, all derived from the current scripts:
- `fail` prints `FAIL: ID TEXT` then one indented line (6 spaces) per detail [VERIFIED: tests/host/lib.sh:100-110]. Each former `set -- "$@" "a" "b" "c"` with several args becomes that many `add_problem` calls in the same order (H-09 l.52-54, Coexistence l.27-30).
- One-assertion checks: H-04 becomes `add_problem "got: $output"` plus `report_check H-04 "expected uid=1000(sandbox) gid=1000(sandbox)" "container user is uid=1000(sandbox)"`.
- H-00 "older than v2": `add_problem "install Docker Desktop, which ships Compose v2"` then `report_check H-00 "Compose $composeVersion is older than v2" "Compose $composeVersion is v2 or newer"`.
- H-10: its three FAIL outcomes have different summaries and the third has no details, so they use `stop_check`; the final line is `pass_check`.
- Manual `ask_judgment ID QUESTION PASS_TEXT FAIL_TEXT` is `add_problem "answer: ${answer:-<none>}"` plus `report_result`; it prints `'%s [y/N] '`. Manual H-09 prints `'\nDid the earlier session resume? [y/N] '`, so pass the question as `$'\nDid the earlier session resume?'`.
- Output order is observable: `compose_up` prints failure hints to stdout when it fails, so in H-11 the `compose_up` call must stay after the sentinel checks and before `report_check`, as today.

### Anti-Patterns to Avoid
- **Wrapping `exec "$@"` in a function without passing the arguments:** inside a function `"$@"` is the function's arguments.
- **Moving `set -e` sensitive calls into `||` or `if` contexts in the entrypoint:** `set -e` is ignored inside a function called from `x || y` or `if x`. Call the `check_*` functions as plain statements.
- **`local x=$(cmd)` where `$?` is read afterwards:** `local` masks the status. Declare first, assign on the next line (H-00, H-06, H-10, H-11, H-12, H-13 read `$?` right after the assignment).
- **A new subfolder for libraries, or a `read` in `tests/host/*.sh`:** both break guard or selftest assumptions (above).
- **Adding `add_problem` or `stop_check` inside `$(...)` or a pipeline stage:** it runs in a subshell; the problem list or the `exit` is lost [VERIFIED: ran this session: after `x=$(add one)` the array length was still 0].
- **Dash as punctuation or planning IDs in the new comments and banners.**

## Common Pitfalls

### Pitfall 1: Eager expansion of the PASS text under `set -u`
**What goes wrong:** `report_check ID "fail text" "pass text with $var"` expands every argument before the call. If `$var` is unset on the failing path, the script aborts with `unbound variable` and prints no FAIL line.
**Why it happens:** the old code expanded the PASS text only on the pass path. H-02 sets `baseCount` only inside the `else` branch; with an empty base layer list it would abort. [VERIFIED: ran `set -u; f "x $unsetvar y"` in bash 5.3.9, shell exits `unbound variable` before calling `f`]
**How to avoid:** initialise every variable used in a PASS text (H-02 `baseCount=0`), or use `${var:-}`; command substitutions in PASS text run on the failing path too.
**Warning signs:** a transcript diff showing a missing FAIL line plus `unbound variable` on stderr.

### Pitfall 2: `$?` lost through `local`
**What goes wrong:** `local out=$(cmd)` returns 0 whatever `cmd` did, so a later `if [ "$?" -ne 0 ]` or `status=$?` is wrong. [VERIFIED: `local x=$(false); echo $?` printed 0, split form printed 1]
**How to avoid:** `local out` on one line, `out=$(cmd)` then `status=$?` immediately after, as `lib-bundle.sh` already does. Never put a command between the assignment and the `$?` read.

### Pitfall 3: Failure collection that disappears in a subshell
**What goes wrong:** `add_problem`, `report_check`, `stop_check` inside `$(...)` or on the right of a pipe run in a subshell; the list stays empty or the `exit` ends only the subshell. [VERIFIED: ran this session]
**How to avoid:** call them in the function body at top level; for loops over command output use `for x in $list` or a here-doc as `guard.sh` does, not `cmd | while read`.

### Pitfall 4: `set --` replaced inside a function, or positional parameters read in a function
**What goes wrong:** inside a function `$@` and `$#` are the function's. After conversion no check reads `$#`; do not reintroduce it. Manual helper H-09 reads script arguments in `parse_arguments`: pass `"$@"` explicitly.
[VERIFIED: ran `g(){ set -- a b; }`: outer `$#` stayed 0]

### Pitfall 5: Helper is not byte-equal to the inline code it replaces
**What goes wrong:** `printf '%s\n' "$x" | tr '\n' ' '` prints one separator even when `$x` is empty; a file-based `tr '\n' ';' <file` prints nothing for an empty file; `lib-bundle.sh` uses `printf '%s'` (no trailing newline, so no trailing separator). Swapping those sites changes FAIL text in edge cases.
**How to avoid:** `join_lines` and `first_lines` replace only sites that already use `printf '%s\n' "$x" | ...`; leave the two file-based sites in `coexistence.sh`, the `grep -Fl ... | tr` site in H-01, and the two `lib-bundle.sh` sites alone.

### Pitfall 6: A frozen test script needs a function from `lib.sh`
**What goes wrong:** inlining `claude_pin`/`expected_arch` into h12/h01 per D-08 makes five host-selftest cases FAIL ("lib: claude_pin equals the ARG in claude/Dockerfile", "lib: expected_arch maps ...").
**How to avoid:** keep them reachable from `lib.sh` (in `lib-docker.sh`, loaded by `lib.sh`); record in the plan that Phase 1.4 may inline them.

### Pitfall 7: Entrypoint `exec "$@"` and `set -e` semantics
See Anti-Patterns. Also `local` in `run_start_hooks` is fine under `set -eu`; `for hook in "$hookDir"/*` with no match yields the literal glob, which `[ ! -f ]` skips (verified for an empty directory).

### Pitfall 8: Guard scans comments
`no_installs_at_container_start` greps `base/sbx-entrypoint` for the words `npm npx bunx pip apt-get apt curl wget` including comments [VERIFIED: tests/guard.sh:134]; `sandbox_code_has_no_planning_ids` and `host_tests_have_no_planning_ids` scan comments for `D-NN`, `Phase N`, `CONTEXT.md`, `.planning`. Keep new comments clean.

### Pitfall 9: The two selftest numbers that look like counts
host-selftest asserts `19 PASS lines`, `Summary: 19 passed`, `Summary: 18 passed, 1 failed` [VERIFIED: tests/host-selftest.sh:639, 646, 677]. Do not add or drop a check script, a `PASS:` line or a `NOT RUN:` line. This is also why no new automated host check (an `h20`) is added for WR-04.

### Pitfall 10: bash 3.2 and BSD traps in new code
Assumed from the portability rule, not testable here: empty array under `set -u` is unbound in 3.2 (existing comment [CITED: tests/host/lib.sh:317]); `${var,,}`, `${var^^}`, `declare -A`, `mapfile`, `readarray`, `local -n`, `wait -n`, `&>>`, `|&`, `$BASHPID`, `;;&`, `declare -g`, fractional `read -t` are bash 4; `sed -i` without suffix, `grep -P`, `date -d`, `readlink -f`, `find -printf`, `stat -c` (outside `docker exec`) are GNU. `+=` array append and `printf '%q'` are already in use on the Mac. `[[ =~ ]]` with a quoted pattern changed meaning in 3.2: avoid regexes in `[[ ]]`. `layout-lint.sh` greps for the bash 4 list.

### `lib-report.sh` additions
```bash
# report_result ID FAIL_SUMMARY PASS_TEXT: prints FAIL with every problem collected, or PASS; clears the list; returns 1 or 0.
report_result() {
  local checkId=$1
  local failSummary=$2
  local passText=$3

  if [ "${#problemList[@]}" -gt 0 ]; then
    fail "$checkId" "$failSummary" "${problemList[@]}"
    problemList=()

    return 1
  fi

  pass "$checkId" "$passText"

  return 0
}

# report_check ID FAIL_SUMMARY PASS_TEXT: report_result, then exit 1 on FAIL or 0 on PASS.
report_check() {
  if report_result "$@"; then
    exit 0
  fi

  exit 1
}

# stop_check ID SUMMARY [DETAIL...]: prints one FAIL line with its details and exits 1.
stop_check() {
  fail "$@"
  exit 1
}

# pass_check ID TEXT: prints one PASS line and exits 0.
pass_check() {
  pass "$1" "$2"
  exit 0
}

# join_lines TEXT [SEPARATOR]: TEXT on one line, each line followed by SEPARATOR (default a space).
join_lines() {
  printf '%s\n' "$1" | tr '\n' "${2:- }"
}
```
