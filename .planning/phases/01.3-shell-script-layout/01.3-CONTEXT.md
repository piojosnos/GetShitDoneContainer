<decisions>
## Implementation Decisions

### Splitting scripts into functions
- **D-01:** Every script gets the layout: header comment, 80-column section banners, and a `Main / Entry Point` banner over the top-level flow.
- **D-02:** Split code into functions only where there are separate pieces that each get a clear name. A cohesive block stays whole, even in a short script; do not force a split where there are not two or more distinct things.
- **D-03:** When a piece also happens in other scripts, generalize it a little and move it to a library (see D-07 to D-09).

### Failure reporting in the checks
- **D-04:** Find the best, cleanest way for a check to collect and report its result, and use it in every host check (symmetry). The starting point is the pattern H-14 to H-18 use today: `add_problem` while checking, `report_check` at the end. Single-assertion checks that call `pass`/`fail` directly today move to the same pattern.
- **D-05:** No `set -- "$@"` failure collection is left in any check.
- **D-06:** PASS and FAIL lines, their order and exit codes stay exactly as today.

### Library organisation
- **D-07:** Split `tests/host/lib.sh` now into topic libraries. Each library file has one topic or purpose; its functions are cohesive with each other. From the file name a reader can infer what the functions do, and is never surprised to find a given function in a given library.
- **D-08:** A library is a set of reusable utilities. A function belongs in a library only when several scripts really use it; the more callers, the better. Do not move everything into libraries: hundreds of functions each used twice is a failure. One-script helpers stay in the script.
- **D-09:** Each library function has one well-defined behaviour and responsibility, and a short comment saying what it does. The goal is a small collection of libraries that make writing and reading the checks easier.

### Behaviour preservation
- **D-10:** The phase is a pure restructure except for D-11. Proof: `tests/host-selftest.sh`, `tests/bundle-selftest.sh` and `tests/guard.sh` give identical output before and after (temp names stripped), and `tests/host/run-all.sh` passes on the Mac.
- **D-11:** WR-04 fix in `base/sbx-entrypoint`: a regular file in `/etc/sbx/start.d` that is not executable stops the start with an `[sbx] ERROR` line and a non-zero exit, like a failing hook. Folders and dotfiles stay ignored. Covered by a test case.

### Claude's Discretion
- The exact library names and which function goes where, within D-07 to D-09.
- The exact shape of the reporting pattern (D-04), as long as it is the same everywhere and output is unchanged.
- Plan and wave split, and how each plan proves identical output.

</decisions>

## Existing Code Insights

### Reusable Assets
- `tests/host/lib.sh` (337 lines): run-folder setup (`host_init`, `resolve_run_dir`, `make_run_dir`), output (`pass`, `fail`, `info`), container and compose helpers (`in_container`, `compose_cmd`, `compose_up`, `compose_down`, `run_timeout`), test-sandbox guards (`assert_test_sandbox`, `require_test_sandbox`, `remove_leftover_test_container`), image helpers (`build_images`, `expected_arch`, `claude_pin`), old-layout snapshot, `print_next_block`, and the new `add_problem`, `report_check`, `first_lines`. These are the natural topic seams for the split.
- `tests/host/lib-bundle.sh`: already a topic library (bundle checks shared by H-15 to H-17).

### Established Patterns
- Ten older checks collect failures with `set -- "$@" ...` (H-01, H-02, H-03, H-05, H-06, H-09, H-11, H-12, H-13, Coexistence); the others call `pass`/`fail` directly.
- `tests/host-selftest.sh` runs every check against a fake docker and copies `tests/host/*.sh`, so new library files are picked up; check that any new library is sourced where the checks expect it.
- `tests/guard.sh` has rules over `tests/host/h[0-9][0-9]-*.sh` headers (`# Depends on:`), portability and never-delete; new library files must pass them.
- Manual helpers put the terminal check before sourcing the library, because `host_init` makes a docker call.

### Integration Points
- Every check sources `lib.sh` today; after the split each sources the libraries it uses (or `lib.sh` sources the core ones). Keep `run-all.sh` and the manual helpers working standalone.

</code_context>

<specifics>
## Specific Ideas

- The user's test for a split: can you give each piece a clear name? If yes, split; if the block is one cohesive thing, keep it.
- The user's test for a library: from its name you can guess its functions, and nothing in it is a surprise.

</specifics>
