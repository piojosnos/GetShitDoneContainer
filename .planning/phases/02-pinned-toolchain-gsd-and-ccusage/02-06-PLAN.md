## Phase Goal

ROADMAP.md Phase 2 goal (verbatim): "The sandbox has the full development toolchain plus Claude Code, GSD, and ccusage baked into the image at versions pinned in one `versions.env`. Rebuilding with changed pins delivers the new versions into the sandbox while login and history persist."

This plan delivers the rest of success criterion 4: after a GSD pin change and a rebuild, the start syncs the image's GSD and the login and session history are unchanged. The automated part plants a stale GSD; the attended helper does the real bump (research open question 4).

Planning notes:
- `compose up --wait` returns once the container runs, but the entrypoint runs the start hooks after that and the GSD sync writes about a thousand files (research Pitfall 3, A8). The bundle hook runs after GSD, so H-16's bundle checks would race too. compose_up therefore waits for the container's command: the entrypoint execs `sleep infinity` only after every hook, and `pgrep -x sleep` inside the container sees it. This is the research's option (a), polling in the host library, made general so it covers both hooks; the compose.yml healthcheck (option b) stays out because it touches Phase 1 files.
- Planning check run on 2026-10-08 with gsd-core 1.15.0: the installer removed a planted skills/gsd-h16-sample, backed up a hand-edited GSD skill and a stale VERSION to gsd-local-patches/, restored both, and kept a non-gsd user skill. H-16 is changed to match: no gsd-* user sample; a stale VERSION and an edited GSD skill must be restored.
- The settings key is planted by node inside the container (the host has no JSON tool the guard allows); the fake docker runs the same node command on the fixture.
- The helper never edits versions.env (the guard forbids host tests that change tracked files); the user does, then puts it back with `git checkout -- versions.env` and `./build.sh`.
- Reversibility: test code and docs; reversible.
