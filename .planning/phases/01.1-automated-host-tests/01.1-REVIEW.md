# Phase 01.1: Code Review Report

**Reviewed:** 2026-10-04
**Depth:** standard
**Files Reviewed:** 23
**Status:** issues_found

## Summary

The scripts are in good shape on the main safety question. Every Docker call is aimed at `sbx-hosttest` / project `sbx-hosttest`. `compose_down` is guarded by a label plus mount check. No script deletes anything. `guard.sh` and `host-selftest.sh` both pass on Linux (15/15 rules, all selftest cases). Bash 3.2 and BSD portability is clean; I found no bash 4 feature or GNU-only flag on the host side.

The defects are in the supporting machinery, not the happy path:

- The `run_timeout` helper does not bound anything when the command is a shell function. I reproduced this.
- Several checks can false-FAIL or false-PASS because of global state (volume list, git status, generic grep text).
- The guard rules pass vacuously in some situations.
- Two checklist claims are broader than what the scripts prove.

## Critical Issues

### CR-01: `run_timeout` does not stop a command that is a shell function (timeouts are ineffective)

**File:** `tests/host/lib.sh:132-158` (callers: `lib.sh:165`, `tests/host/h13-env-and-no-self-update.sh:12`)
**Issue:** `run_timeout` backgrounds `"$@"` and, on expiry, kills `$commandPid`. Both real callers pass a shell function (`compose_cmd`, `in_container`), not an external program. For a function, `$!` is the pid of the forked subshell. The `docker compose` or `docker exec` client is a child of that subshell and is not killed.

Effects:

- The `kill` hits the subshell only. The `docker` client keeps running as an orphan.
- Inside `$(...)` (H-13, line 12), the command substitution keeps reading the pipe until the orphan exits. The "60 s" limit therefore does not bound the wall time at all.
- For `compose_up` (120 s limit), an orphaned `docker compose up -d --wait` can finish later and race with the next step. The next step could be `compose_down`, a sentinel read, or the H-10 restart.

Reproduction on this machine: `run_timeout 2 slowcmd`, where `slowcmd` runs `sleep 7`, returned after 7 s, not 2 s. Only the H-10 call (`run_timeout 120 env ... docker ...`) works, because `env` execs docker and the pid is the real process.

**Fix:** Kill the process group or the child tree, or exec the real binary in the background. A minimal approach:
```bash
run_timeout() {
  local seconds=$1 commandPid watcherPid exitCode
  shift
  ( exec "$@" ) &   # still a function problem; see below
```
`exec` cannot run a function, so make the callers use external commands:

- Call `env SBX_NAME=hosttest SBX_DIR="$RUN" docker compose -f ... up -d --wait` directly, as H-10 already does.
- Call `docker exec "$CONTAINER" claude update` directly.

Alternatively, have the watcher kill the children too: `pkill -P "$commandPid"` (BSD `pkill -P` exists on macOS), then `kill "$commandPid"`.

## Warnings

### WR-01: `assert_test_sandbox` / `require_test_sandbox` do not tie the container to the current run folder

**File:** `tests/host/lib.sh:178-211`
**Issue:** The mount check is `case "$mountSource" in *sbx-hosttest-*)`, a substring match anywhere in the path. It never compares the mount to `$RUN`.

- A standalone check run with `SBXTEST_DIR` pointing at run folder A, against a container mounting run folder B, passes the guard.
- That mismatch makes `compose_up` in H-08, H-09, H-10 and H-11 recreate the container on A. It also makes the other checks read the wrong folder.
- Any real path containing `sbx-hosttest-` anywhere (a parent directory, say) would also be accepted as the test sandbox.

**Fix:** Compare the resolved last component, as H-09 already does:
```bash
case "$mountSource" in
  */"$(basename "$RUN")") return 0 ;;
esac
```
Fall back to the prefix check only when `RUN` is empty.

### WR-02: H-09 compares the host's entire volume list, so unrelated Docker activity causes a false FAIL

**File:** `tests/host/h09-rebuild-keeps-files-no-volumes.sh:18,45-50`
**Issue:** `docker volume ls -q` covers every volume on the daemon. Any other container, build or sandbox that creates or removes a volume during the rebuild (it takes minutes) fails H-09, even though this sandbox created none. This is the same "environmental false FAIL" the runner comments try to avoid for H-10.
**Fix:** Scope it to the test project and keep the mount-count check as the real proof:
```bash
docker volume ls -q --filter label=com.docker.compose.project=sbx-hosttest
```

### WR-03: H-03 does not test that `SBX_NAME` is required, although the checklist says it does

**File:** `tests/host/h03-variable-interpolation.sh:10-27`; `tests/host-checklist.md:42`
**Issue:** The checklist row reads "Name and folder variables are required". The script only checks that `SBX_NAME=hosttest` yields `name: sbx-hosttest`, and that a missing `SBX_DIR` is refused. It never runs `config` without `SBX_NAME`, and never tests that an uppercase name is rejected. SANDBOX.md also documents the uppercase rejection. The `SBX_DIR` half also depends on no `.env` file in the repo supplying `SBX_DIR`.
**Fix:** Add a third assertion with `env -u SBX_NAME SBX_DIR=... docker compose ... config` expecting "SBX_NAME is required" and a non-zero exit. Alternatively, narrow the checklist wording.

### WR-04: H-01's platform-warning grep is generic and misses the real BuildKit warning

**File:** `tests/host/h01-native-arch.sh:32-36`
**Issue:** It greps all of `$RUN/logs/*.log` for the bare text `does not match`.

- That text is the `docker run` warning ("requested image's platform ... does not match the detected host platform"). Build logs use BuildKit's `InvalidBaseImagePlatform` wording instead, so the build-time case is not caught here. The image `Architecture` inspect above does catch it.
- The text is too generic. Any apt, npm or Docker line containing "does not match" in a build log gives a false FAIL.

**Fix:** Match the specific phrases: `does not match the detected host platform|InvalidBaseImagePlatform`. Limit the glob to `build*.log` and `compose-up.log`.

### WR-05: Coexistence can false-FAIL on unrelated edits, miss committed changes, and pass when `docker ps` fails

**File:** `tests/host/coexistence.sh:21-37`; `tests/host/lib.sh:283-285`
**Issue:**

1. `git status --porcelain` flags any uncommitted edit under `ClaudeCode/` or `OpenCode/` that existed before the run, so the check fails regardless of what the test did. It also cannot see a committed change. `guard.sh` already covers that case with a diff against a commit.
2. `snapshot_old_containers` discards `docker ps` stderr and its exit status. If `docker ps` fails both times (daemon hiccup), both files are empty and equal, so the check reports "untouched".
3. A git error (not a repo, `safe.directory`) is merged into `gitOutput` through `2>&1` and reported as "changes".

**Fix:**

- Capture `git status --porcelain` in the run-all baseline too, and compare before and after.
- Have `snapshot_old_containers` return non-zero when `docker ps` fails, and treat an empty baseline from a failed command as "no baseline".
- Separate git's stderr from its stdout.

### WR-06: `guard.sh` rules pass vacuously, and the delete rule has gaps

**File:** `tests/guard.sh:30-37,42-66,137-138`
**Issue:**

- `nowhere_matches` and `host_code_lines` send grep errors to `/dev/null`. A mistyped file name, a missing file or an unmatched glob (`tests/host/*.sh` stays literal) yields empty hits, which PASSes. A rule that scans nothing looks identical to a rule that found nothing.
- `host_tests_never_delete` does not cover other ways to destroy data or state:
  - `docker compose rm`
  - `docker compose down --rmi`
  - `docker network rm`
  - `docker kill` and `docker stop`
  - `git clean`
  - `mv` over a path
  - `truncate`
  - redirects such as `: >file`
- Of these, `down --rmi` removes images (including the real `sbx-*:local` tags) and slips through.
- `host_tests_are_portable` omits a few macOS pitfalls: `sed -r`, `sort -V`, `xargs -r`, `realpath`, `date --date`, `mktemp --tmpdir`.

**Fix:**

- Fail a rule when a scanned file list is empty or a file is unreadable. Add `[ -e "$f" ] || { echo "missing: $f"; return 1; }` to the helpers.
- Extend the delete regex with `compose[[:space:]]+rm|--rmi|network[[:space:]]+rm|docker[[:space:]]+(kill|stop)|git[[:space:]]+clean`.
- Add the portability patterns above.

### WR-07: The environment scrub does not cover the Docker target or the Compose env files

**File:** `tests/host/lib.sh:18`
**Issue:** `host_init` unsets `COMPOSE_PROJECT_NAME`, `COMPOSE_FILE`, `COMPOSE_PROFILES`, `COMPOSE_PATH_SEPARATOR` and `SBX_DIR`. It leaves these alone:

- `DOCKER_HOST`, `DOCKER_CONTEXT`, `DOCKER_CONFIG`: a caller pointed at a remote or alternate daemon runs the whole suite, including `docker build` and `compose up` with local bind paths, there.
- `COMPOSE_ENV_FILES`, `COMPOSE_IGNORE_ORPHANS`, `COMPOSE_REMOVE_ORPHANS`.
- A `.env` file in the repo root: H-03's "missing `SBX_DIR`" assertion would then fail for an environmental reason.

The header says the caller's values "are never used", but this is only true for the variables listed.

**Fix:** Unset `COMPOSE_ENV_FILES COMPOSE_IGNORE_ORPHANS COMPOSE_REMOVE_ORPHANS`. Either unset `DOCKER_HOST DOCKER_CONTEXT`, or have run-all print `docker context show` as an `info` line so the target is visible. Pass `--env-file /dev/null` in `compose_cmd` and in the H-03 calls.

### WR-08: H-13 treats any `docker exec` failure as "the share folder exists"

**File:** `tests/host/h13-env-and-no-self-update.sh:13-14,28-30`
**Issue:** `test ! -e path` returns 1 when the path exists. But `docker exec` also exits 125, 126, 127 or 137 for daemon errors, a missing binary, or a killed process. `shareStatus -ne 0` reports all of them as "~/.local/share/claude exists in the container home", which misleads when diagnosing.
**Fix:** Test `shareStatus -eq 1` for "exists", and treat any other non-zero as "could not check (exit N)". It would also help to run `ls -d` and show the output.

## Info

### IN-01: The tests rebuild and retag the real `sbx-base:local` / `sbx-claude:local`

**File:** `tests/host/lib.sh:242-266`; `tests/host/h09-rebuild-keeps-files-no-volumes.sh:31`
**Issue:** This is documented and deliberate, but it means a test run replaces the user's working image tags, and `SBXTEST_NO_CACHE=1` forces a full rebuild of them. A bad working tree produces images that existing real sandboxes pick up on their next `up`. Failed builds do not retag, so the risk is limited to a build that succeeds but is subtly broken.
**Fix:** Consider test-only tags (for example `sbx-base:hosttest`) passed to the build through `BASE_IMAGE`. That needs a compose override, so it is a design change. At minimum, state the effect in the `run-all.sh` header, not only in the checklist.

### IN-02: Repeated standalone runs against the same `SBXTEST_DIR` can pass on stale files

**File:** `tests/host/h05-workspace-and-home.sh:11-17`; `tests/host/h06-git-and-identity.sh:41`
**Issue:** H-05 checks only that `x.txt` exists. H-06 checks only that `state/git/config` contains `name = T` (also true for `name = Tom`). With a reused run folder, a failing `touch` or `git config` in the container still passes. Nothing is deleted by design, so a fresh file name per run is the available fix.
**Fix:** Use a unique name (`x-$$.txt`) in H-05. In H-06 anchor the match: `grep -Eq '^[[:space:]]*name = T$'`.

### IN-03: H-02 passes if the Claude image is identical to the base image

**File:** `tests/host/h02-claude-on-base.sh:19-34`
**Issue:** The check proves the base layers are a prefix of the Claude layers. It does not require any additional layer. A `claude` image tagged from the base (or a Dockerfile with no install step) would still pass, and the pin check in H-12 would be the only backstop.
**Fix:** Also require `claudeCount > baseCount`.

### IN-04: Style deviations from the project conventions (blank lines around control flow)

**File:** `tests/host/run-all.sh:45-46`; `tests/host/lib.sh:105-106`; `tests/host/h08-history-survives-recreate.sh:17-19`; `tests/host/h09-rebuild-keeps-files-no-volumes.sh:25-27`
**Issue:** There are several instances where a `for` / `while` / `if` follows a statement with no blank line before it (for example `script=$1` immediately followed by `for item in ...`, and `shift 2` immediately followed by `while`). `code-conventions.md` requires a blank line before each control-flow construct. `guard.sh` has the same pattern in `nowhere_matches` (line 34 onward uses `[ -z ... ] && return 0` as a brace-less condition). Beyond the style point, these are low risk.
**Fix:** Add the blank lines, and convert `[ -z "$hits" ] && return 0` to a braced `if`.

### IN-05: The self-test fake docker mirrors the scripts' own assumptions, and its backgrounded shell outlives the run

**File:** `tests/host-selftest.sh:315-333`; `tests/host/h08-history-survives-recreate.sh:17`
**Issue:**

- The fake `docker` is built from the same assumptions the scripts make (template substrings, output wording), so the selftest proves parsing and control flow only. The header states this. Treat a green selftest as no evidence that real Docker output matches.
- H-08 starts a `sleep 25` pipeline that is never waited for. In the selftest each H-08 run leaves a `sleep 25` orphan. I saw five lingering after a selftest run. It is harmless, but it is another consequence of CR-01-style process handling.

**Fix:** In H-08, record the background pid and `kill` it after the fresh-shell step, or replace `sleep 25` with a `read`-based hold that ends when the container goes away.
