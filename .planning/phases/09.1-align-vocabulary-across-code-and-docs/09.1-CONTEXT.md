# Phase 09.1: Align vocabulary across code and docs - Context

**Gathered:** 2026-11-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Code, tests and docs use one agreed set of terms. The phase first builds a glossary (`GLOSSARY.md`), gets it agreed at a checkpoint, then applies it as deep as it goes: file names, function, check and step names, env vars, commands, messages, docs and the live planning docs. The user's rules and skills repo is called best-practices wherever "bundle" refers to it. The best-practices repo is cleaned of every sandbox detail in the same phase.

No behavior changes: a rename is a rename. New capabilities belong in other phases.

</domain>

<decisions>
## Implementation Decisions

### Glossary first, then the change
- **D-01:** The first plan builds the glossary and stops at a checkpoint for the user's review. Nothing is renamed before the glossary is agreed. Later plans apply it.
- **D-02:** The glossary lives in a standalone `GLOSSARY.md` at the repo root, linked from `README.md` and from `.claude/CLAUDE.md` so agents follow it. Match the existing docs' voice: short, schematic, a table.
- **D-03:** Each glossary entry records: the concept, the chosen term, the retired synonyms (with where they occur), and any term kept on purpose with its reason (for example "CA bundle: industry term").
- **D-04:** Two rules pick a term, so the review is not a set of separate debates: (1) an industry-standard term always wins; (2) otherwise the name users type or see (a command, check or step name) wins, and the prose follows it.
- **D-05:** Watch for real distinctions that only look like synonyms. Verify each candidate pair against the code before merging terms. Known example to check: "launcher" (64 uses) vs "agent wrapper" (6); `sbx-selfcheck`'s and `sbx-init`'s launchers may be a different thing from `sbx-claude` and `sbx-cursor`. Same care for "registry" vs "registration", "project folder" vs "sandbox folder" vs "host folder".

### What the sweep covers
- **D-06:** "bundle" changes only where it means the user's rules and skills repo. The CA certificate bundle (`base/selfcheck/checks/280_extra_ca.py`, the `extra-ca-system-bundle` check and its tests) keeps "bundle": it is the industry term.
- **D-07:** "the Mac" is not a project concept. The host machine is generic (macOS today, Windows or another Linux box tomorrow); use one universal term, "the host" unless the glossary review finds a better one. Mac-specific facts (Docker Desktop on macOS, BSD tools) stay named as such where they really are Mac-specific.
- **D-08:** Folder vs directory: one word for everything we own, prose and identifiers alike. Claude picks it in the glossary plan; the lean is "directory" (prose) with `dir` as its identifier abbreviation, because it is the universal term, it matches `mkdir`, and third-party env vars we cannot rename (`CLAUDE_CONFIG_DIR`, `GH_CONFIG_DIR`, `CURSOR_CONFIG_DIR`) already say `DIR`. The user may overrule at the checkpoint.
- **D-09:** Also normalized: leftover start-hook wording (`start.d`, "start hook"; Phase 9 removed start hooks), "self-check" vs `selfcheck`, "host check" vs "host test", "state folder" vs "state dir", "config folder" vs "config dir", and whatever else the glossary sweep finds.
- **D-10:** Fix as deep as possible once agreed: file and folder names (for example `base/selfcheck/bundle_links.py`, `270_no_bundle_copy.py`, `tests/host/lib-bundle.sh`, `tests/host/h27-bundle-clone-and-publish.sh`, `tests/host/support/bundle/`), identifiers, check and step names, user-facing commands (`sbx-bundle-clone`), env vars (`SBX_BUNDLE_DIR`), the `versions.env` key (`BUNDLE_REPO_URL`), messages, README sections, MIGRATION, tests docs. The bash host tests are included even though Phase 10 rewrites them, because they use the renamed commands and env vars and must keep passing.
- **D-11:** Renames are outright, with no old-name alias. A rebuild delivers the new names; MIGRATION.md gets a short note listing old to new for anything a user types. The exact new names come from the glossary review.
  **Reversibility:** costly: user-facing command and env var names reach the docs, both Dockerfiles, the host tests and the user's habits.
- **D-12:** `.planning/` history stays as written. Only the live parts follow the glossary: `PROJECT.md`, `REQUIREMENTS.md` (open requirements), and the `ROADMAP.md` text of future phases (for example Phase 10.1's "the bundle's rules").
- **D-13:** `.claude/CLAUDE.md` follows the glossary in its own branch and PR, separate from code and from `.planning/`.

### The best-practices repo knows nothing about the sandbox
- **D-14:** The dependency points one way: the sandbox depends on best-practices, never the reverse. In this phase, the best-practices repo (`/home/sandbox/workspace/best-practices`) is cleaned of every sandbox detail: `rules/best-practices.md` names `sbx-gh-login`, `sbx-bundle-clone` and the deleted `/etc/sbx/start.d/10-best-practices`, and those go. The rule says what to do in general terms (for example "if the clone is missing, say so"); the sandbox owns the how (the `sbx-init` FAIL line already prints the fix). It is a priority and should be a small change.
- **D-15:** That change is a separate PR against `main` of the best-practices repo, on its own branch, following its own git workflow. It is not a rename of "bundle" into "best-practices" inside that repo; it removes sandbox knowledge. Whether that repo calls itself the "bundle repo" in its own rules is its own vocabulary, and stays unless the user asks.
- **D-16:** `rules/shell.md`'s example `lib-bundle.sh` is an illustration, not sandbox knowledge; leave it.

### Checking the result
- **D-17:** grep finds candidates and serves as a final sweep, but it is not the validation. The validation is the agreed glossary applied by reading each hit in context (D-06 shows why: not every "bundle" is wrong).
- **D-18:** The existing gates still apply: the guard and selftests pass in the dev sandbox, and the host run (`./host-test.sh`) passes on the host, because renamed commands, env vars and check names touch the host tests.
- **D-19:** No guard rule enforces the glossary. `GLOSSARY.md` plus review is the enforcement, as with the dropped planning-ID guard rule.

- The exact wording of the general rule that replaces the sandbox details in `rules/best-practices.md`.

</decisions>
