## Phase Goal

ROADMAP.md Phase 3 goal (verbatim): "The user registers each sandbox once, then starts, stops, and upgrades it by name alone. One command rebuilds the images and recreates the sandbox, and login and history survive."

Not in user-story form; quoted verbatim as in earlier phases.

This plan adds the one command that upgrades a sandbox: `sbx-upgrade NAME` builds both images while the old container keeps running, then recreates that one sandbox on them. It leads with a tracer through the whole flow (registry, build.sh, recreate, wait) with a throwaway docker stand-in, then pins the refusals and the data rule, then prepares the Mac proof.

Planning notes:
- D-12, D-13, D-14 and D-18 are implemented here; D-15 to D-17 (the version line `sbx-upgrade` prints last) are plan 03, which appends one line to this script.
- Planner choices (Claude's discretion): extra arguments after the name go to `build.sh` unchanged (it forwards them to both builds, so `--no-cache` works); the running-sandbox line is printed before the build, worded "after the build, recreating it will close ...", so it is true whether or not the build succeeds and the user can still stop the run; `--force-recreate` because a cached build keeps the image id and a plain `up` would then keep the old container (research Pattern 3).
- The guard rule is the one research recommended for data safety: the old layout lost data through a volume removal, and a grep over `bin/*` is cheap. The second optional rule (bin/ sources only its libraries) is not added: the self-test case that plants `$(touch ...)` already fails when a reader sources the entry, proven by plan 01's mutant.
- Reversibility: reversible (one script and one guard rule).
