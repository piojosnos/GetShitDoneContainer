# Phase 05.2 Plan 01: Trust a company root certificate Summary

**Optional SBX_CA_CERT PEM file: build.sh validates and splits it, passes it to the base build as a BuildKit named context, base/Dockerfile trusts it in the system store, JDK, npm, pip, uv and Node, and an unset variable leaves the build byte for byte as before.**

## Performance

- **Duration:** about 12 min
- **Completed:** 2026-11-10T03:04:33Z
- **Tasks:** 3
- **Files modified:** 3 (127 insertions, 2 deletions)

## Accomplishments

- build.sh reads `SBX_CA_CERT`, keeps only the certificate blocks (one `sbx-extra-ca-N.crt` each) in a `mktemp` folder removed by an `EXIT` trap, and adds `--build-context cacert=DIR` to the base build only. Unset and empty runs print the same lines and the same two `docker build` commands as origin/main.
- base/Dockerfile has `FROM scratch AS cacert`, a step right after the apt RUN that installs the certificates with `update-ca-certificates` and writes the `/etc/sbx/extra-ca.pem` marker, and a step after Maven that imports each certificate into the JDK cacerts and writes the npm, pip, uv and Node settings. No ARG or ENV was added and no line was removed.
- Every bad input (relative path, missing or unreadable file, folder, no certificate, a block openssl rejects, openssl missing) prints a `build.sh: SBX_CA_CERT ...` line and exits 1 before any docker call.
- A starred banner names the file and each certificate's subject and SHA-256 fingerprint before the first build and after the last.
- The guard lets exactly the line `FROM scratch AS cacert` through `dockerfile_args_have_no_defaults`; the pin regex is unchanged.
