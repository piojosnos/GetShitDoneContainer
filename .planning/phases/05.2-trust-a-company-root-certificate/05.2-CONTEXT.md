# Phase 5.2: Trust a company root certificate - Context

**Gathered:** 2026-11-10
**Status:** Ready for planning

<domain>
## Phase Boundary

A sandbox builds and runs on a Mac behind a company HTTPS proxy (Zscaler) by trusting one optional root certificate file. The file is named by an environment variable; when it is not set, the images are unchanged. The image adds the cert to the system store before any download, and the runtime tools with their own store (Node, Java, Python, pip, uv) trust it too. The README explains setup and the trade-off. Proof is a manual run on the work Mac.

Out of scope: any new automated test, any doctor check, any change to the tool-versions line.

</domain>

<decisions>
## Implementation Decisions

### Where the cert comes from
- **D-01:** An environment variable on the Mac holds the path to the PEM file. `build.sh` passes the cert to the base build only when the variable is set; when it is unset or empty, both builds run exactly as today. The user chose this over a fixed file in the tools clone.
- **D-02:** Variable set but the file missing, unreadable or not a PEM certificate: `build.sh` stops with a clear error before any `docker build`. Never fall back silently to a build without the cert.
- **D-03:** Known cost, accepted: an `sbx-upgrade` run from a shell without the variable builds an image without the cert. On the work Mac that shows up as the same `curl: (60)` failure at the first download, so it is loud, not silent. The README tells the user to set the variable in their shell profile.
- **D-04:** The cert goes into `base/Dockerfile` right after the apt step, before any download (curl, git, gh, Node, Maven). `sbx-claude:local` inherits it from `sbx-base:local`; `claude/Dockerfile` needs no cert step of its own unless a runtime setting requires it.
- **D-05:** Runtime tools with their own trust store must trust the cert too: Node (`NODE_EXTRA_CA_CERTS` or equivalent, for Claude Code, npm, GSD), the Java `cacerts` (Maven), and Python, pip and uv (check each against the system store). Every such setting exists only when a cert was given; with no cert, no ENV or store changes.

### Visibility
- **D-06:** When a cert is used, `build.sh` prints a very visible banner framed by lines of `*` characters: it says the images will trust an extra root certificate, and names the file path and the cert subject (and fingerprint if cheap to get). Print it before the builds and again after they finish, so it does not scroll away under the Docker output. No banner without a cert.
- **D-07:** No marker on the tool-versions line (`/etc/sbx/tool-versions`); its regexes and host test h30 stay unchanged.
- **D-08:** README gets a section: why (Zscaler re-signs `release-assets.githubusercontent.com`; IT will not turn it off), how to export the cert from the Keychain (`security find-certificate -a -c "Zscaler Root CA" -p /Library/Keychains/System.keychain`), how to set the variable in the shell profile, and the trade-off: the image then trusts anything the proxy signs. Also update every doc spot that describes `build.sh` and `sbx-upgrade` (Build the images, Scripts table, Upgrade, Threat model, Troubleshooting).

### Verification
- **D-09:** No new shell test or host test (same ground rule as Phase 5 D-01). Proof is manual on the work Mac: the build passes, then `claude`, `npm`, `gh` and `mvn` reach the network from inside a sandbox (add Python/uv if cheap). Written as a short checklist in the README.
- **D-10:** On the home Mac (no proxy, variable unset), the existing `./host-test.sh` passes unchanged, which shows the image is unchanged without the cert.

### Claude's Discretion
- The variable name; follow the existing `SBX_*` naming (for example `SBX_CA_CERT`).
- How the cert enters the build given `.dockerignore` allows only `base`, `claude` and `versions.env` (named build context, build arg, or another mechanism), as long as D-01 holds and nothing is copied into the repo tree.
- The exact per-tool settings for D-05 and where they live (base ENV, conditional on the build input).
- Banner wording and layout within D-06.
- README structure and wording, matching the existing schematic style.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `build.sh` already collects `--build-arg` values into `buildArgList` and passes extra options to both builds; the cert input can join that list or the per-build options.
- `base/Dockerfile` already uses multi-stage `COPY --from=...`; a named build context fits the same shape.

### Established Patterns
- Every pinned `ARG` has no default and fails loudly when unset; the cert input is the one optional input and must not break that rule's guard (`tests/guard/supply-chain.sh`).
- Comment blocks framed with `# ----` above each step; short plain bash with `set -eu`; Mac commands BSD-portable.
- The last `RUN` of each image is a smoke test; the mount point must stay empty.

### Integration Points
- `/etc/ssl/certs/ca-certificates.crt` (system bundle, from `ca-certificates` in the apt step).
- `/opt/java/openjdk/lib/security/cacerts` (Temurin store copied from the jdk stage).
- Image ENV block in `base/Dockerfile` (docker exec shells get settings only from ENV).

</code_context>
