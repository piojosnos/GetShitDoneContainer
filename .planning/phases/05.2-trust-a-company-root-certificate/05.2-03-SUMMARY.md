## PR description draft

Title: `feat: trust an optional company root certificate in the image build`

```text
Behind a company HTTPS proxy (Zscaler), the base build stops at the gh
download with "curl: (60) SSL certificate problem": the Mac trusts the
proxy's root through the Keychain, the images do not. This adds one optional
input, SBX_CA_CERT, a PEM file on the Mac. Unset or empty, nothing changes.

What changed
- build.sh reads SBX_CA_CERT. A relative, missing, unreadable or non-PEM
  value is refused before Docker runs (exit 1, a "build.sh: SBX_CA_CERT"
  line). The file is split into one certificate per file in a temp folder,
  keeping only certificate blocks so a private key never reaches the build,
  and passed to the base build as the named context "cacert". A starred
  banner names the file, subjects and fingerprints before the first build
  and after the last.
- base/Dockerfile adds the certificates to the system store before any
  download, then, after the toolchains, to the JDK cacerts, npm, pip, uv and
  interactive Node. Settings are files, not ENV, so an image built without
  the variable is unchanged.
- The supply-chain guard lets the one empty "FROM scratch AS cacert" stage
  through; the pin rule is otherwise unchanged.
- README gains "Behind a company HTTPS proxy": setup steps, what trusts the
  root and how, the trade-off, a known limit and a manual checklist.

What you accept
- The images trust anything the proxy signs. Keep the file to the one root.
- A Node program run by a non-interactive "docker exec" does not get
  NODE_EXTRA_CA_CERTS; run it from sbx-shell.

How it was verified
- Linux: shell syntax of every script, the guard (shellcheck, hadolint and
  the supply-chain rules), the guard, entrypoint and sbx self-tests, and
  dry runs with a fake docker for unset, empty, valid and six bad values.
- Home Mac (no proxy): images built from the branch without a root equal the images built from main (same file listing, store hashes and ENV, no banner); ./host-test.sh ends "Summary: 32 passed, 0 failed, 0 not run"; a build with two throwaway roots (and a private key in the file) shows the banner twice, adds both roots to the system store, the JDK store, npm, pip, uv and interactive Node, and keeps the key out of the image; three bad values exit 1 before Docker runs.
- Work Mac (behind Zscaler): the images built with SBX_CA_CERT set to the exported root (no curl (60)), and the user then used the sandbox all day with everything working (user report, no logs).
```

PR #34 already exists and was merged before the work Mac run (see Deviations), so this draft is kept as the record of the description; it is not used for a new PR.

### Start failure on the work Mac (not caused by the certificate change)

After the image built, the sandbox failed to start. The 05-gsd start hook stopped with:

`EACCES, Permission denied '/home/sandbox/workspace/state/claude/gsd-core/commands/gsd'` (syscall `cp`)

It comes from Node `fs.cpSync` (the C++ `cpSyncCopyDir` path) inside GSD's `syncRuntimeSurfaceCorpus`.

- Cause: Docker Desktop's Virtual Machine Manager. The work Mac used the Apple Virtualization Framework; the home Mac uses Docker VMM. Under Docker VMM file sharing records modes in the `user.containers.override_stat` xattr; the work Mac files had no such xattr.
- `chmod -R u+w` and moving `gsd-core` aside did not help.
- Switching the work Mac to Docker VMM fixed it.
- The exact operation Apple Virtualization refuses was not probed.
- Docs: `ZSCALER.md` ("Set up a sandbox on a computer behind Zscaler") with the Docker VMM step and a failure table; it was merged through PR #35 and the README links to it.
