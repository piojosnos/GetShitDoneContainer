## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Where the cert comes from
- **D-01:** An environment variable on the Mac holds the path to the PEM file. `build.sh` passes the cert to the base build only when the variable is set; when it is unset or empty, both builds run exactly as today. The user chose this over a fixed file in the tools clone.
- **D-02:** Variable set but the file missing, unreadable or not a PEM certificate: `build.sh` stops with a clear error before any `docker build`. Never fall back silently to a build without the cert.
- **D-03:** Known cost, accepted: an `sbx-upgrade` run from a shell without the variable builds an image without the cert. On the work Mac that shows up as the same `curl: (60)` failure at the first download, so it is loud, not silent. The README tells the user to set the variable in their shell profile.
- **D-04:** The cert goes into `base/Dockerfile` right after the apt step, before any download (curl, git, gh, Node, Maven). `sbx-claude:local` inherits it from `sbx-base:local`; `claude/Dockerfile` needs no cert step of its own unless a runtime setting requires it.
- **D-05:** Runtime tools with their own trust store must trust the cert too: Node (`NODE_EXTRA_CA_CERTS` or equivalent, for Claude Code, npm, GSD), the Java `cacerts` (Maven), and Python, pip and uv (check each against the system store). Every such setting exists only when a cert was given; with no cert, no ENV or store changes.

#### Visibility
- **D-06:** When a cert is used, `build.sh` prints a very visible banner framed by lines of `*` characters: it says the images will trust an extra root certificate, and names the file path and the cert subject (and fingerprint if cheap to get). Print it before the builds and again after they finish, so it does not scroll away under the Docker output. No banner without a cert.
- **D-07:** No marker on the tool-versions line (`/etc/sbx/tool-versions`); its regexes and host test h30 stay unchanged.
- **D-08:** README gets a section: why (Zscaler re-signs `release-assets.githubusercontent.com`; IT will not turn it off), how to export the cert from the Keychain (`security find-certificate -a -c "Zscaler Root CA" -p /Library/Keychains/System.keychain`), how to set the variable in the shell profile, and the trade-off: the image then trusts anything the proxy signs. Also update every doc spot that describes `build.sh` and `sbx-upgrade` (Build the images, Scripts table, Upgrade, Threat model, Troubleshooting).

#### Verification
- **D-09:** No new shell test or host test (same ground rule as Phase 5 D-01). Proof is manual on the work Mac: the build passes, then `claude`, `npm`, `gh` and `mvn` reach the network from inside a sandbox (add Python/uv if cheap). Written as a short checklist in the README.
- **D-10:** On the home Mac (no proxy, variable unset), the existing `./host-test.sh` passes unchanged, which shows the image is unchanged without the cert.

## Summary

The cert can enter the base build with no change to `.dockerignore` and nothing copied into the repo tree: `build.sh` writes the certificates into a `mktemp -d` folder and passes it with `docker build --build-context cacert=<dir>`. The Dockerfile declares `FROM scratch AS cacert` so the name resolves when no context is given; Docker documents that a named context overrides a stage of that name. A `RUN --mount=type=bind,from=cacert` step right after the apt step installs the cert only when the folder holds `*.crt` files. The mount content is part of the cache key, unlike a BuildKit secret (a changed or newly added secret does not invalidate the cache, so a cached no-op step would silently survive). A build arg would force a new `ARG` that the guard forbids (every ARG must be a pin in `versions.env`) and carries PEM text through the command line.

ENV cannot be conditional in a Dockerfile, but almost nothing needs it. Run in this sandbox (same image as the project builds): Claude Code 2.1.285 is a native binary that loads the OS store by default, so the system store is enough. curl, git, gh (Go), Python `ssl`, and system pip (Debian de-vendored certifi, `certifi.where()` is `/etc/ssl/certs/ca-certificates.crt`) read the Ubuntu bundle. The tools that do NOT read it, each with a file-based fix that exists only when a cert was given: Java (import into `cacerts` with `keytool`; the JDK is a copied regular file, so the import must run after the `COPY --from=jdk`), npm (`cafile` in `/usr/local/etc/npmrc`, which also covers the `npm install -g` steps of `claude/Dockerfile`, so that file needs no change), **pip inside a venv** (the venv pip comes from `/usr/share/python-wheels/pip-24.0-py3-none-any.whl`, which vendors its own `certifi/cacert.pem`; fix with `/etc/pip.conf`), uv (bundled roots by default; `system-certs = true` in `/etc/uv/uv.toml`), and Node programs started from an interactive shell (`export NODE_EXTRA_CA_CERTS=/etc/sbx/extra-ca.pem` appended to `/etc/bash.bashrc`, the same place the tool-versions line already uses). The only residual gap versus a real `ENV`: a non-interactive `docker exec sandbox node ...` does not see the variable.

`update-ca-certificates` bundles a multi-cert `.crt` file but skips the hash link (`rehash: warning: skipping ... does not contain exactly one certificate or CRL`), and `keytool -importcert` imports only the first certificate of a multi-cert file. A Keychain export (`find-certificate -a`) can hold several. So `build.sh` splits the file into one `sbx-extra-ca-N.crt` per certificate with a portable `awk`, which also drops any non-certificate block (a private key in the same file never reaches the build).

**Primary recommendation:** Use a named build context (`--build-context cacert=<tmpdir>`) plus `FROM scratch AS cacert` and two conditional `RUN` steps in `base/Dockerfile` (system store after apt; Java, npm, pip, uv and the bashrc export after the JDK copy), keep `claude/Dockerfile` unchanged, add a one-line guard carve-out for `FROM scratch AS cacert`, and verify on the Mac.

### Alternatives Considered
| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Named context | BuildKit secret (`--secret id=cacert,src=...` with `required=false`) | Secret content is not part of the cache key: a changed cert, or a first-time cert on a machine that already has a cached no-op step, does not rerun the step. Needs `--no-cache` to recover. Rejected. |
| Named context | Build arg holding the PEM text | Needs `ARG` without a pin: guard `every_dockerfile_arg_is_pinned` fails; multi-line value on a command line; the value shows in `docker history`. Rejected. |
| Named context | Copy the file into `base/` | Violates "nothing may be copied into the repo tree". Rejected. |
| File-based settings plus bashrc | Unconditional `ENV NODE_EXTRA_CA_CERTS` or `NODE_USE_SYSTEM_CA=1` | Covers non-interactive `docker exec` too, but the no-cert image gains an ENV (violates D-05 as written). Node warns when the file is missing. Offered as the fallback if the user accepts the ENV. |
| File-based settings plus bashrc | Conditional ENV through a stage chosen by an ARG in `FROM` | Real conditional ENV, but needs a non-pin `ARG` (guard carve-out), restructures the Dockerfile into several stages. Not worth it. |
| Dockerfile splits the bundle | `build.sh` splits (recommended) | Mac-side split keeps non-certificate blocks (private keys) out of the build entirely, and validates each certificate where the error is readable. |

### Recommended Project Structure

### Pattern 1: Optional input through a named context with a scratch default
**What:** `FROM scratch AS cacert` in the Dockerfile; `--build-context cacert=<dir>` only when the cert exists. Docs: "The context overrides a stage called `name` when used as `FROM ... AS name`". [CITED: docs.docker.com/reference/cli/docker/buildx/build/] A bind mount from a named context is documented: `RUN --mount=from=docs,target=/app/docs`. [CITED: docs.docker.com/build/building/context/]
**When to use:** one optional file or folder that must not live in the repo.
**Cache behavior:** the mounted context content takes part in the step's cache key (the docs are silent; this is how BuildKit treats a mount source, and an unchanged folder gives a cache hit). [ASSUMED] The contrast with secrets is documented: "The contents of build secrets are not part of the build cache." [CITED: docs.docker.com/build/cache/invalidation, via search]
**Mount target:** use `/mnt`, which already exists in `ubuntu:24.04` (checked: `drwxr-xr-x 2 root root /mnt` in this sandbox), so no new empty directory is left in the layer. [ASSUMED that BuildKit would otherwise leave an empty mount-point directory; `/mnt` avoids the question]

### Pattern 2: Settings that exist only with a cert, without ENV
**What:** the second `RUN` is `if [ -f /etc/sbx/extra-ca.pem ]; then ...; fi`. The marker file written by step one is the single condition. In a no-cert build both `RUN` steps do nothing, so the filesystem and the ENV are the same as today.
**Side benefit:** `/etc/sbx/extra-ca.pem` is a stable marker for the deferred Phase 5.1 doctor ("does this image trust an extra root, and which"). It is not on the tool-versions line, so D-07 holds. [ASSUMED that the planner wants to mention it; it is free]

### Pattern 3: Validate and split on the Mac, one certificate per file
**What:** `awk` keeps only `BEGIN CERTIFICATE` to `END CERTIFICATE` blocks and writes `sbx-extra-ca-N.crt`; `openssl x509 -noout` validates each piece. Tested here with a file holding a leading "Bag Attributes" header, two certificates, text between them and a trailing private key: two clean files, zero `PRIVATE` lines. [VERIFIED: ran in this sandbox with mawk 1.3.4]
**Why one file each:** `update-ca-certificates` skips the hash link of a multi-cert file; `keytool` imports only the first. See pitfalls P1 and P2.

### Pattern 4: Guard carve-out, the BASE_IMAGE precedent
The guard rule `dockerfile_args_have_no_defaults` flags any `FROM` in `base/Dockerfile` that is not `FROM ${PIN}`. `FROM scratch AS cacert` trips it. The same rule already carves out `ARG BASE_IMAGE=sbx-base:local` with `grep -Fvx`. Add the same shape for the one stage. Verified in a scratch copy: with the carve-out `supply-chain.sh` passes all 9 rules; without it `dockerfile_args_have_no_defaults` fails with `FROM must take its image from a pin: FROM scratch AS cacert`. [VERIFIED: ran in a scratch copy of the repo]

Verbatim, the existing rule (`tests/guard/supply-chain.sh:120-122`):
```text
  grep -E '^ARG .*=' $BASE | report_lines "$BASE: an ARG with a default value: " || ok=1
  grep -E '^ARG .*=' $CLAUDE | grep -Fvx 'ARG BASE_IMAGE=sbx-base:local' | report_lines "$CLAUDE: an ARG with a default value: " || ok=1
  grep -E '^FROM ' $BASE | grep -Ev '^FROM \$\{[A-Z_]+\}( AS [a-z]+)?$' | report_lines "$BASE: FROM must take its image from a pin: " || ok=1
```
[VERIFIED: tests/guard/supply-chain.sh:120-122]

### Anti-Patterns to Avoid
- **A new `ARG` for the cert:** fails `every_dockerfile_arg_is_pinned` (every ARG without a default must be a `versions.env` pin) and the "no default" rule. Use the named context.
- **`ENV` for the settings:** present in every build, cert or not. Use files.
- **`exit` inside a new `build.sh` function:** the user's shell rule says the function reports and returns non-zero, and Main does `step || exit 1`. (The existing `check_versions_file` exits; new code should not copy that.)
- **An empty bash array expanded under `set -u`:** bash 3.2 (stock macOS) treats `"${emptyArray[@]}"` as unbound. Use an `if`/`else` around the base build, as in the example, and no new array.
- **Relative `SBX_CA_CERT`:** `build.sh` does `cd "$(dirname "$0")"` before it would read the path, so a relative path resolves against the repo folder. Require an absolute path.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| System trust store and bundle | Appending to `ca-certificates.crt` | `update-ca-certificates` | Also creates the hash links OpenSSL capath users need |
| Splitting a PEM bundle | `csplit` or `sed` ranges on the Mac | The `awk` in the example | `csplit` keeps junk between blocks (keys, headers); it is also not portable between GNU and BSD |
| Java store | Replacing `cacerts` with a copy | `keytool -importcert -cacerts` | Keeps the 120 shipped roots |
| Making ENV conditional | Stage selection by ARG in `FROM` | Config files plus the bashrc line | Avoids a non-pin ARG and a restructure |
| Printing subject and fingerprint | Parsing certificates in shell | `openssl x509 -noout -subject -fingerprint -sha256` | Output is only displayed, never parsed, so LibreSSL versus OpenSSL 3 formatting does not matter |

## Common Pitfalls

### P1: Multi-cert `.crt` file in `/usr/local/share/ca-certificates`
**What goes wrong:** `update-ca-certificates` adds the file to the bundle but prints `rehash: warning: skipping sbx-extra-ca.pem,it does not contain exactly one certificate or CRL` and creates no hash link. Tools that use only the hash directory miss the certs.
**Why:** `openssl rehash` handles one certificate per file. [VERIFIED: ran `update-ca-certificates --localcertsdir ... --etccertsdir ...` against a scratch folder as non-root; bundle grew by 2, no link created]
**How to avoid:** one certificate per file (`sbx-extra-ca-N.crt`), split in `build.sh`.
**Warning signs:** the warning above in the build log.

### P2: `keytool` imports only the first certificate of a file
**How to avoid:** the per-certificate loop; use `|| exit 1` inside the loop, because `set -e` does not stop a failure inside an `&&` list.
**Warning signs:** one `sbx-extra-*` alias in `keytool -list -cacerts`.

### P3: Relative path after `cd`
`build.sh` changes directory to its own folder before the rest runs, and `sbx-upgrade` runs it with `bash "$repoDir/build.sh"` from the user's cwd. A relative `SBX_CA_CERT` would be read from the wrong folder. Reject non-absolute values with a clear error (tested). The README example uses an absolute path.

### P4: The variable is set but not exported
`SBX_CA_CERT=... ` in `~/.zshrc` without `export` is invisible to `build.sh`, and `sbx-upgrade` then builds without the cert (D-03: loud `curl: (60)`). The README line must read `export SBX_CA_CERT="$HOME/..."`.

### P5: `--build-context` and the first run on a new machine
`docker build` runs through Buildx by default unless Docker Engine is in Windows container mode or `DOCKER_BUILDKIT=0`. [CITED: docs.docker.com/reference/cli/docker/image/build/] The flag is a Buildx flag. That `docker build --build-context` is accepted on the user's Docker Desktop is not tested here. [ASSUMED] Check once on each Mac: `docker buildx version` and `docker build --help | grep build-context`.
**Contingency if `--mount=from=<scratch stage>` fails with no context given:** have `build.sh` always pass `--build-context cacert=<empty dir>` and drop `FROM scratch AS cacert` (and the guard carve-out). That departs from D-01's "exactly as today", so use it only if the home Mac proves the scratch default fails. [ASSUMED: scratch-stage bind mount works]

### P6: The venv pip trap
Python and system pip trust the system bundle, so a quick check from `python3` or `pip3` passes, while `python3 -m venv v && v/bin/pip install x` still fails. Test with a venv. The fix is `/etc/pip.conf`.

### P7: A BuildKit secret hides a cert change
Rejected above; do not "simplify" to `--secret` later. A changed cert would not rebuild the cached step.

### P8: The first build with a cert rebuilds everything after apt
The `RUN` step sits before Node, gh, Maven and the rest, and its cache key now holds the cert. Adding, removing or changing the cert rebuilds all later layers once. Expected; mention in the README so the user is not surprised.

### P9: The closing banner is skipped when a build fails
With `set -eu` the script stops at the failed build, so the second banner is not printed. The first banner is above the Docker output. If the planner wants the second banner on failure too, call it from an `EXIT` trap instead of the end of Main. Not required by D-06 ("again after they finish").

### P10: Non-interactive `docker exec` does not see `NODE_EXTRA_CA_CERTS`
`/etc/bash.bashrc` is read by interactive shells (`sbx-shell` runs `docker exec -it ... bash`), and Claude and its child processes inherit the variable from that shell. `docker exec sandbox node ...` without a terminal does not. State it as a known limit in the README. The existing tool-versions line has the same reach. [VERIFIED: `bin/sbx-shell` uses `exec docker exec -it -w ... bash`, and the tool-versions line is appended to `/etc/bash.bashrc` in `base/Dockerfile`]

### P11: Keychain export can hold more than one certificate, or expired ones
`security find-certificate -a -c "Zscaler Root CA" -p ...` prints every match. All of them are split and trusted. An expired root is trusted by the store only until a verifier checks dates, so it is harmless; the banner lists each subject so the user can see the count. Optional: show `openssl x509 -noout -enddate` per certificate. [ASSUMED: the command and flags; widely used, and quoted by D-08]

### P12: `host-test.sh` inherits the variable
`host-test.sh` calls `bash "$REPO_DIR/build.sh"`, so with the variable exported it builds with the cert and prints the banner into the test log. That is correct on the work Mac. On the home Mac the variable must be unset for D-10.

## Code Examples

These were run in a scratch copy of the repo here (shellcheck and hadolint clean with the repo's configs; `build.sh` exercised with a fake `docker` on PATH). The planner turns them into tasks; paths and names are the recommendation.

### base/Dockerfile: the stage and step one (right after the apt step)
```dockerfile
FROM ${HADOLINT_IMAGE} AS hadolint
FROM scratch AS cacert
FROM ${UBUNTU_IMAGE}
```
```dockerfile
# ------------------------------------------------------------------------------
# Optional extra root certificate: the system store, before any download
# ------------------------------------------------------------------------------
# build.sh mounts a folder of one-certificate .crt files as the cacert context
# when SBX_CA_CERT is set; without it the empty stage above is mounted and this
# step changes nothing.
# ------------------------------------------------------------------------------
RUN --mount=type=bind,from=cacert,target=/mnt \
    if compgen -G '/mnt/*.crt' >/dev/null; then \
      install -m 644 /mnt/*.crt /usr/local/share/ca-certificates/ \
      && update-ca-certificates \
      && mkdir -p /etc/sbx \
      && cat /mnt/*.crt > /etc/sbx/extra-ca.pem \
      && chmod 644 /etc/sbx/extra-ca.pem; \
    fi
```
Notes: the base `SHELL` is bash, so `compgen -G` works. `install -m 644` gives root-owned files whatever the Mac uid of the mounted folder. `hadolint` accepts the `--mount` flag. The step must stay below the apt step (`update-ca-certificates` comes from `ca-certificates`) and above `ARG NODE_VERSION`.

### base/Dockerfile: step two (after Maven, before the uv copy)
```dockerfile
# ------------------------------------------------------------------------------
# Optional extra root certificate: the tools that keep their own store
# ------------------------------------------------------------------------------
# Only when step one found a certificate. Java: cacerts. npm: cafile. pip and uv:
# their own config files. Node programs: the variable, for interactive shells.
# ------------------------------------------------------------------------------
RUN if [ -f /etc/sbx/extra-ca.pem ]; then \
      for certFile in /usr/local/share/ca-certificates/sbx-extra-ca-*.crt; do \
        keytool -importcert -noprompt -cacerts -storepass changeit -alias "$(basename "$certFile" .crt)" -file "$certFile" || exit 1; \
      done \
      && mkdir -p /usr/local/etc /etc/uv \
      && echo 'cafile=/etc/ssl/certs/ca-certificates.crt' >> /usr/local/etc/npmrc \
      && printf '[global]\ncert = /etc/ssl/certs/ca-certificates.crt\n' > /etc/pip.conf \
      && echo 'system-certs = true' > /etc/uv/uv.toml \
      && echo 'export NODE_EXTRA_CA_CERTS=/etc/sbx/extra-ca.pem' >> /etc/bash.bashrc; \
    fi
```
The step runs as root (the Dockerfile switches to `USER sandbox` only near the end). It must come after `COPY --from=jdk` (the JDK is not there earlier) and after the Node tarball (npm). `claude/Dockerfile` needs no edit: its `npm install -g` steps read `/usr/local/etc/npmrc`.

### build.sh: validation, split and banner
```bash
# ------------------------------------------------------------------------------
# prepare_extra_cert: with SBX_CA_CERT set, checks it and fills extraCertDir
# ------------------------------------------------------------------------------
# extraCertDir holds one .crt file per certificate; only certificate blocks are
# kept, so a key in the same file never reaches the build. Empty when unset.
# ------------------------------------------------------------------------------
prepare_extra_cert() {
  local certPath

  extraCertDir=""

  if [ -z "${SBX_CA_CERT:-}" ]; then
    return 0
  fi

  case "$SBX_CA_CERT" in
    /*) ;;
    *)
      echo "build.sh: SBX_CA_CERT must be an absolute path: $SBX_CA_CERT" >&2
      return 1
      ;;
  esac

  if [ ! -f "$SBX_CA_CERT" ] || [ ! -r "$SBX_CA_CERT" ]; then
    echo "build.sh: SBX_CA_CERT is not a readable file: $SBX_CA_CERT" >&2
    return 1
  fi

  if ! command -v openssl >/dev/null 2>&1; then
    echo "build.sh: SBX_CA_CERT is set, but openssl is not installed to check it" >&2
    return 1
  fi

  extraCertDir=$(mktemp -d "${TMPDIR:-/tmp}/sbx-cacert.XXXXXX")
  trap 'rm -rf "$extraCertDir"' EXIT

  if ! awk -v dir="$extraCertDir" '/-----BEGIN CERTIFICATE-----/ { count++; out = sprintf("%s/sbx-extra-ca-%d.crt", dir, count); inCert = 1 } inCert { print > out } /-----END CERTIFICATE-----/ { inCert = 0; close(out) } END { if (count == 0) { exit 1 } }' "$SBX_CA_CERT"; then
    echo "build.sh: SBX_CA_CERT holds no PEM certificate: $SBX_CA_CERT" >&2
    return 1
  fi

  for certPath in "$extraCertDir"/*.crt; do
    if ! openssl x509 -noout -in "$certPath" >/dev/null 2>&1; then
      echo "build.sh: SBX_CA_CERT holds a block that is not a valid certificate: $SBX_CA_CERT" >&2
      return 1
    fi
  done
}

# ------------------------------------------------------------------------------
# print_cert_banner: prints a starred banner naming the extra root, if any
# ------------------------------------------------------------------------------
print_cert_banner() {
  local certPath
  local starLine="**********************************************************************"

  if [ -z "$extraCertDir" ]; then
    return 0
  fi

  echo "$starLine"
  echo "* build.sh: the images trust an EXTRA ROOT CERTIFICATE"
  echo "* file: $SBX_CA_CERT"

  for certPath in "$extraCertDir"/*.crt; do
    openssl x509 -noout -subject -fingerprint -sha256 -in "$certPath" | sed 's/^/* /'
  done

  echo "* Anything the proxy signs is trusted inside the sandbox. See README."
  echo "$starLine"
}
```
Main, replacing the two build lines (an `if`/`else` instead of an array, for bash 3.2):
```bash
collect_build_args
prepare_extra_cert || exit 1
print_cert_banner

if [ -n "$extraCertDir" ]; then
  build_image base/Dockerfile sbx-base:local --build-context "cacert=$extraCertDir" "$@"
else
  build_image base/Dockerfile sbx-base:local "$@"
fi

build_image claude/Dockerfile sbx-claude:local "$@"
print_cert_banner
```
Behavior run with a fake `docker`: unset and empty give exactly today's two command lines (no `--build-context`); relative, missing, not-a-PEM and bad-block paths print one error and exit 1 before any `docker` call; a file with a header, two certificates, junk and a private key gives two `ctx:` files and a banner with two subject and fingerprint pairs, before and after the builds; the temp folder is gone afterwards. [VERIFIED: ran with a fake `docker` on PATH]

Portability notes: only POSIX `awk` features (`-v`, `sprintf`, `print > var`, `close`), `mktemp -d "${TMPDIR:-/tmp}/..."` (precedent in `host-test.sh`), `openssl x509 -noout -subject -fingerprint -sha256`. The last is in LibreSSL and OpenSSL 3; output differs (`subject=CN = X` versus `subject= /CN=X`), and it is only displayed. [ASSUMED: LibreSSL accepts these flags; not runnable here]

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Copy the cert into the build context | Named build context (`--build-context`) | Dockerfile frontend 1.4, Buildx | The cert never enters the repo tree |
| `NODE_EXTRA_CA_CERTS` for every Node tool | Native tools read the OS store (`NODE_USE_SYSTEM_CA`, Claude Code default `bundled,system`) | Node 22.15 and 23.8 for the flag; Claude Code docs now state the default | Claude Code needs no setting once the system store has the cert |
| `uv --native-tls` | `system-certs` setting and `UV_SYSTEM_CERTS` | uv 0.12 line (the `--help` of 0.12.21 shows `--system-certs`) | Use the new name in `uv.toml` |

**Deprecated or not applicable:** Temurin's `USE_SYSTEM_CA_CERTS` entrypoint feature (the project copies the JDK and does not use that image's entrypoint); `ca-certificates-java` (not installed, adds a JRE).

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Private key in the exported PEM reaches the build context and the image | Information disclosure | `awk` keeps only `CERTIFICATE` blocks; the key never leaves the Mac (tested) |
| Trusting a root lets the proxy read prompts, code and tokens, and tamper with downloads | Information disclosure, Tampering | Explicit opt-in per Mac, a starred banner on every build, README threat model row; do not trust more than the supplied file |
| Fallback to a cert-less build hides a misconfiguration | Repudiation | D-02: any bad input stops the build; D-03: a missing variable fails loudly at the first download |
| Option injection or path trick through `SBX_CA_CERT` | Tampering | Absolute path required, always quoted, `-f` and `-r` checked, never evaluated |
| Temp folder left behind | Information disclosure (low: the files are public certificates) | `mktemp -d` (mode 0700) and an `EXIT` trap |
| Weakening the other guards | Tampering | One literal carve-out (`FROM scratch AS cacert`, `grep -Fvx`), no regex loosening, no new ARG |
