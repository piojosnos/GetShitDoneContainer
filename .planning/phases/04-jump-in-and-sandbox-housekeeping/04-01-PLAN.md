## Phase Goal

ROADMAP.md Phase 4 goal (verbatim): "The user gets into any registered sandbox with one command, and can see and clean up their sandboxes without risking code, login, or history."

The roadmap marks this phase `mvp`, but the goal line is not in user-story form; it is quoted verbatim as in earlier phases (run `/gsd-mvp-phase 4` if a story is wanted).

This plan is the phase tracer: `sbx-shell NAME` gets the user into a sandbox with one command. One path runs end to end through every layer the phase touches, proven here without Docker by a throwaway stand-in that records the calls: the registry read, the start steps now shared in the library, the scoped Compose call, the start-hook wait and the interactive `docker exec`. Plan 02 adds `sbx-list` on the same library, plan 03 `sbx-rm` with the guard rule it needs, plan 04 the docs, plan 05 the gate and the Mac run.

Planning notes (each a choice the user can object to at review):
- D-04 lets the start steps be shared either as a library function or by calling `sbx-start`. This plan moves them into `bring_up_sandbox NAME` in `bin/sbx-lib.sh`. Calling `sbx-start` would print its two lines and its hint inside every jump-in, and its older-image warning could fire for a sandbox the jump-in would not recreate anyway.
- Research open question 1, adopted: `sbx-shell` always runs `check_name` and `read_registry_entry`, also for a running sandbox. Both are cheap and need no Docker, and they make sure only a registered sandbox is entered and a bad name never reaches `-w` or the container name. Folder check, image check, compose and the wait run only when the sandbox is not running (D-01).
- Research open question 5, adopted: entering a running sandbox does not wait for its start hooks. `sbx-start` and `sbx-shell` always wait for the hooks of a sandbox they start, so only a sandbox started with the raw `docker compose up` can still be inside its hooks; the start-readiness phase fixes that for everyone. Plan 04 writes one sentence about it in SANDBOX.md.
- Research open question 2, adopted: H-31 drives `sbx-shell` through BSD `script` (a pty) and the attended helper `tests/host/manual/h31-jump-in.sh` proves the real terminal and the `sbx-claude` login. H-31 sends the shell its input only once the shell runs in the container, and keeps the input open until the shell has written its file, so neither an input flush when Docker switches the terminal to raw mode nor a `script` that ends with its input can lose the commands. Whether BSD `script` gives `sbx-shell` a terminal with piped input is a Mac assumption (plan 05); if it does not, H-31's FAIL line says so and names the helper.
- One host check per command (H-31 `sbx-shell`, H-32 `sbx-list`, H-33 `sbx-rm`) instead of research's combined H-31 for shell and list: each plan then proves its own command, and a failure points at one script. The cost is one more take-down and restore of the test sandbox on the Mac.
- No terminal test in `sbx-shell`: the self-test closes stdin for every run, so a `[ -t 0 ]` check would make the start path untestable; Docker's own refusal is the message. `sbx-shell` prints nothing of its own, so a running sandbox gets the `docker exec` only.
- Reversibility: every decision here is reversible (scripts and a library function behind stable names; nothing is stored).

## Conventions carried into every edit

- Comment shape: a banner is a rule line of `# ` plus 78 dashes (80 columns), a title line, a rule line, then at most two "why" lines and a closing rule; with no why, the title sits between two rules. No comment line over 80 columns: shorten a title in this plan if it does not fit, keeping its meaning. The knob table in the `make_scripted_docker` banner is the one existing longer block; it gains the new knobs.
- Shell: `set -eu` in the bin scripts, `set -u` in tests; libraries set no options and run nothing; functions plus a `# Main / Entry Point` banner over a short list of calls; braces always; a blank line before and after every `if`/`for`/`while`/`case` block (an `else` stays cuddled); full camelCase variable names; list variables end in `List`.
- Stock bash 3.2 and BSD tools (the scripts run on the Mac): no `mapfile`, `readarray`, `declare -A`, `${var,,}`, `&>>`, `|&`, `[[ -v ]]`, `local -n`, `sed -i`, `readlink -f`, `realpath`, `stat -c`; split `local name` from `name=$(command)` when the status matters; never expand a possibly empty array under `set -u`; keep `case` blocks out of `$( ... )`.
- Quote every expansion; host paths may hold spaces.
- Every docker call reads `</dev/null`, except the one interactive `docker exec -it` in `bin/sbx-shell`, whose stdin is the terminal.
- The text of every `bin/` file (code, comments and messages) never contains the words rm, rmdir, prune, kill, down or eval, nor the option --volumes, nor the text sbx-rm (the word rm matches inside it): the guard rule `host_scripts_keep_sandbox_data` refuses them. Plan 03 narrows that rule for `bin/sbx-rm` alone.
- ASCII only. No em or en dash, no ` -- ` or spaced ` - ` used as a dash, in comments, messages or docs; punctuation after a closing quote.
- No planning IDs in committed source, tests, fixtures, comments or commit messages: no D-xx, SCR-xx, T-04-xx, phase numbers, assumption IDs, CONTEXT.md or .planning references. Host check IDs such as H-31 are product IDs and are fine.
