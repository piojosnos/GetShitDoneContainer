## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Image layers
- **D-01:** Two layers stay: `sbx-base` then one thin image per agent. No third "agent common" layer and no single image holding both agents.
- **D-02:** What both agents share moves into `sbx-base`: the GSD package (`@opengsd/gsd-core` at `GSD_CORE_VERSION`), `sbx-gh-login` and `sbx-bundle-clone`. GSD goes late in the base Dockerfile, so a GSD bump rebuilds only the last base layers. The GSD pin moves to the `sbx-base` section of `versions.env`. Reversibility: costly, moving them back touches both agent Dockerfiles, the base Dockerfile and the guard rules that name which image holds what.
- **D-03:** `claude/` keeps only what is Claude's: Claude Code, ccusage, `sbx-claude`, the managed settings and the Claude start hooks. `cursor/` holds only the Cursor CLI, its env and its start hooks.
- **D-04:** The general tools (JDK, Maven, Python, Node, gh, uv) stay exactly as they are in `sbx-base`; neither agent image adds or changes one.

#### Cursor CLI install
- **D-05:** The Cursor CLI version is pinned as `CURSOR_AGENT_VERSION` in `versions.env` and its package for that version is downloaded directly in `cursor/Dockerfile`, never through a pipe to a shell. A build-time smoke test checks the installed version equals the pin, as `claude/Dockerfile` does for Claude.
- **D-06:** Cursor's self-update is turned off, the Cursor counterpart of `DISABLE_UPDATES`.
- **D-07:** Fallback only if research finds no versioned linux/arm64 download: download the install script, keep it in the build, then run it; the version is then unpinned and the plan says so.

#### GSD and the bundle in Cursor
- **D-08:** A Cursor start hook mirrors `claude/start.d/05-gsd`: it runs `gsd-core --cursor --global` into the Cursor config folder at every start and checks the synced version against the image's.
- **D-09:** The best-practices bundle is used from Cursor: the bundle clone is linked into Cursor's config the same way `10-best-practices` links it into Claude's, at the paths where the Cursor CLI reads global rules and skills.
- **D-10:** Rules or skills that do not work in Cursor (for example `pr-reply` or `merged`, or rule text naming `~/.claude/...` paths) are listed in the phase output, not rewritten in this phase.

#### Agent choice and the shell
- **D-11:** `sbx-add NAME HOST_PATH [claude|cursor]`: an optional third argument, `claude` when omitted. The registry entry keeps its `SBX_AGENT=` line; `read_registry_entry` accepts `claude` and `cursor`.
- **D-12:** No command switches the agent of an existing sandbox. The user edits the registry line, or runs `sbx-rm` then `sbx-add`, which keeps the files.
- **D-13:** Compose starts the image that matches the entry's agent. `build.sh` and `sbx-upgrade` always build both agent images.
- **D-14:** `sbx-shell` opens bash for both agents; the user starts `claude` or `cursor-agent` from that shell. No `sbx-cursor` launcher. `sbx-claude` stays as it is (Phase 9 keeps it as the warning wrapper); that asymmetry is accepted.

#### Cursor state
- **D-15:** One folder `state/cursor/` holds Cursor's login and settings. `~/.cursor` and `~/.config/cursor` (or wherever research finds Cursor keeps its auth and config) link into it, as `~/.claude` links to `state/claude`. `cursor` is appended to `SBX_STATE_DIRS` in the Cursor image.

#### Tests
- **D-16:** No new host checks: the test harness is rewritten in Phase 10, so tests written now would be thrown away. Phase 10 gets a criterion that the host tests are one shared harness run for each agent, with only small agent-specific checks.
- **D-17:** The static guard rules that cover `claude/Dockerfile` (one `FROM`, nothing piped to a shell, and the like) also cover `cursor/Dockerfile`. This extends the files the guard lists; it adds no new rule.
- **D-18:** The Mac gate: `./host-test.sh` passes (Claude sandboxes work as before), then by hand a Cursor sandbox is added, logs in, answers one prompt in its workspace, and the login survives an `sbx-upgrade`.

## Summary

The Cursor CLI ships as a versioned tarball at a stable URL, per architecture, with a published `.sha256` file next to it. The version string is `YYYY.MM.DD-<7 hex>` (today's: `2026.11.11-b912975`), and `cursor-agent --version` prints exactly that string, so D-05 (pin, download, version smoke test) works as decided and the D-07 fallback is not needed. The package is a self-contained Node app (own `node`, own `rg`, 528 MB unpacked, 175 MB packed) behind a small bash wrapper; it runs from a root-owned read-only folder through a symlink in `/usr/local/bin`. I ran it in this sandbox (linux arm64) and read its source.

Login needs no keyring on Linux: the credential store falls back to a plain file, `~/.config/cursor/auth.json` (not under `CURSOR_CONFIG_DIR`). Config, rules, skills and chats live under `~/.cursor`. So D-15's two symlinks (`~/.cursor` and `~/.config/cursor`, both into `state/cursor`) are exactly right, and one folder holds everything. The login prints a URL and polls; no browser, port or keyring is needed in the container. Self-update is turned off by the documented config key `"channel": "static"` in `cli-config.json`, which needs a small start hook because that file lives under the mounted `state/`. `gsd-core --cursor --global --config-dir DIR` works, writes the same `gsd-core/VERSION` file the Claude hook checks, and installs 72 skills and 64 agents into `DIR`.

Four things the decisions did not foresee, in order of risk. (1) The Phase 6 code is not on this branch, so the phase base branch needs a decision. (2) `cursor-agent --version` writes `~/.cursor/cli-config.json`, and through a dangling `~/.cursor` link at build time it would create files under the mount point and fail the image's empty-mount check; the smoke test must use a throwaway `HOME`. (3) Cursor global rules are read only from `*.mdc` files, and every bundle rule is `*.md`, so linking the rules folder (D-09) is inert. (4) The version string breaks the guard rule `pins_are_exact` (it demands `x.y.z`).

**Primary recommendation:** Build `cursor/Dockerfile` from the tarball URL pattern with its `.sha256`, link `state/cursor` twice, add a small `02-no-self-update` hook plus mirrored `05-gsd` and `10-best-practices` hooks, key compose on `${SBX_AGENT:-claude}` with `run_compose` always passing the entry's agent, and extend the guard file lists. Branch the phase code from the Phase 6 code branch.

### Pattern 1: Cursor install RUN (download, verify, extract, link)
**What:** pinned URL, per-arch mapping like the Node RUN, checksum from the publisher, extract to a root-owned folder, symlink into `/usr/local/bin`.
**When:** `cursor/Dockerfile`, as root, before `USER sandbox`.
**Facts behind it:**
- URL: `https://downloads.cursor.com/lab/<VERSION>/linux/<x64|arm64>/agent-cli-package.tar.gz`, checksum at the same URL plus `.sha256`, content `<hash>  agent-cli-package.tar.gz` [VERIFIED: install script lines `DOWNLOAD_URL=...`; HEAD 200 for both archs; downloaded arm64 and `sha256sum` matched `f068af64ed91b5304605976586f690579679f740a41f388091a6b3a2e776987c`; x64 checksum file `be01f42ad334f81d05a9992fcf060a52cc746f52cc451e849eb652146a6e3c91` and x64 listing read]
- Layout: one top folder `dist-package/`, so `tar --strip-components=1`. It holds the wrapper `cursor-agent` (bash, resolves symlinks with `realpath`), `node`, `rg`, `index.js` and native `.node` files [VERIFIED: tar listing, wrapper source]
- It runs from a read-only copy reached through a symlink in another PATH folder, as a non-root user [VERIFIED: ran `chmod -R a-w` copy via symlink: `--version`, `about`, `status` all worked]
- Arch names in the URL are `x64` and `arm64`; map from `dpkg --print-architecture` (`amd64`, `arm64`) exactly like the Node RUN in `base/Dockerfile:56-58`.

### Pattern 2: One state folder, two links
**What:** `ENV CURSOR_CONFIG_DIR=/home/sandbox/workspace/state/cursor`, plus image-layer symlinks `~/.cursor` and `~/.config/cursor` to the same folder, created as root and `chown -h sandbox`, as `claude/Dockerfile:22-23` does for `~/.claude`.
**Why both links and the variable:**
- Config dir resolution is `CURSOR_CONFIG_DIR`, else `$XDG_CONFIG_HOME/cursor`, else `~/.cursor` [VERIFIED: source of `cursor-config/dist/paths.js` in the package]
- Rules, skills and chat data are read from `homedir()/.cursor/...`, not from `CURSOR_CONFIG_DIR` [VERIFIED: source, `Vo(this.userHomeDirectory,...)` joins `homedir` with `.cursor/skills`; `CURSOR_DATA_DIR` default is `~/.cursor`]. Without the `~/.cursor` link, GSD skills installed under `state/cursor/skills` would not be seen.
- The login file is `${XDG_CONFIG_HOME:-$HOME/.config}/cursor/auth.json` on Linux, mode 600, never under `CURSOR_CONFIG_DIR` [VERIFIED: source of `cli-credentials`: Linux branch of `getAuthFilePath`; `h(t)` returns the file store for every non-darwin platform, so no keyring or libsecret is involved]
- Nothing else needs to persist for login. The `~/.cache/cursor-compile-cache` folder is a throwaway cache in the container layer [VERIFIED: created on first run; wrapper sets `NODE_COMPILE_CACHE`].
- The CLI does `chmod 700` on the folder holding `auth.json` (so `state/cursor` becomes 700); harmless [VERIFIED: source `ensureDirectoryExists`].

### Pattern 3: Per-agent start hooks, same names
Keep hook names identical in both images (`05-gsd`, `10-best-practices`) so base `sbx-bundle-clone`, which ends with a call to `/etc/sbx/start.d/10-best-practices`, works unchanged for both agents. [VERIFIED: claude/bin/sbx-bundle-clone:27 `/etc/sbx/start.d/10-best-practices`] Copy the two hooks into `cursor/start.d/`, changing only the env variable (`CURSOR_CONFIG_DIR`) and the installer flag (`--cursor`). Two copies is the tolerated duplicate count, and Phase 9 deletes the hooks.

### Pattern 4: Agent in the registry, image from the agent
Set one global `agentImage` next to `entryDir` in `read_registry_entry`, and have `require_images`, `runs_older_image` and `run_compose` read `entryAgent` and `agentImage`. Every caller already reads the entry first. [VERIFIED: bin/sbx-start:21, sbx-stop:31, sbx-shell:30, sbx-upgrade:73 call `read_registry_entry` before `run_compose` or `bring_up_sandbox`; sbx-list:103 reads each entry before `runs_older_image` at :110]

### Anti-Patterns to Avoid
- **Running `cursor-agent` at build time with the image's `HOME` and `CURSOR_CONFIG_DIR`:** it writes `cli-config.json` through the dangling link into the (writable, empty) mount point and the last RUN's empty-mount check fails. Use a throwaway `HOME` and `env -u CURSOR_CONFIG_DIR` in the smoke test. [VERIFIED: reproduced; with `~/.cursor` linked to `ws5/state/cursor` in a writable folder, `--version` created `ws5/state/cursor/cli-config.json`]
- **Downloading with `curl -O` after base's `WORKDIR /home/sandbox/workspace`:** the tarball would land on the mount point. Write to `/tmp` or set `WORKDIR /tmp` and restore it. [VERIFIED: base/Dockerfile:227 `WORKDIR /home/sandbox/workspace`]
- **Piping a download into `tar` or the script into `bash`:** the guard greps for the second; keep download, verify, extract as separate commands so the checksum runs before extraction.
- **Rewording `warn_sessions_close`:** the text `will close its open shells and Claude sessions` is asserted by host checks H-29 and H-33 and by the sbx self-test. [VERIFIED: tests/selftest/sbx/start.sh:37, tests/host/h29-sbx-upgrade.sh:81,163,236, tests/host/h33-sbx-rm.sh:260] Leave it as is, even for a Cursor sandbox.
- **The words `rm`, `rmdir`, `prune`, `kill`, `down` or `--volumes` in any `bin/` script other than `sbx-rm`:** the guard rule `host_scripts_keep_sandbox_data` greps for them. Do not mention `sbx-rm` in `sbx-add` messages. [VERIFIED: tests/guard/isolation.sh:47 `nowhere_matches '\b(rm|rmdir|prune|kill|down)\b|--volumes' $otherFileList`]

## Don't Hand-Roll

| Problem | Don't build | Use instead | Why |
|---------|-------------|-------------|-----|
| Merge one key into `cli-config.json` | sed or printf splicing | `jq '.channel = "static"'` (jq is in base) | JSON edit with atomic `mv`; a corrupt file fails the start instead of being overwritten |
| Cursor install | A reimplementation of the install script's atomic version folders and symlink dance | Plain extract to one fixed folder plus one symlink | Version switching is off (static channel); the image is the version |
| GSD for Cursor | A copy of GSD files | `gsd-core --cursor --global --config-dir "$CURSOR_CONFIG_DIR"` | It writes skills, agents, hooks and `gsd-core/VERSION` itself |
| Agent list check | Two separate lists of `claude cursor` in `sbx-add` and `sbx-lib.sh` | One `knownAgentList` variable and one `is_known_agent` function in `sbx-lib.sh` | One edit point when a third agent arrives |
| Checksum verification | A custom hash compare | `sha256sum -c` on the publisher file, with the file name the checksum file names | Same pattern as the Node and gh RUNs |

**Key insight:** every piece already has a Claude twin in this repo; the work is moving shared pieces down a layer and mirroring the rest, not inventing mechanisms.

### Pitfall 2: The version string fails `pins_are_exact`
**What goes wrong:** the guard demands `_VERSION=` values match `^[0-9]+\.[0-9]+\.[0-9]+$` [VERIFIED: tests/guard/supply-chain.sh:106 on `chore/test-diet`]. `2026.11.11-b912975` does not.
**How to avoid:** loosen that one regex to also accept `^[0-9]{4}\.[0-9]{2}\.[0-9]{2}-[0-9a-f]{7,40}$` and say so in the PR: it is the one place D-17 ("no new rule") is not literally true, a loosening rather than a new rule. **Warning signs:** `pins_are_exact` FAIL naming `CURSOR_AGENT_VERSION`.

### Pitfall 3: `.dockerignore` hides `cursor/`
**What goes wrong:** `COPY cursor/start.d/` fails: `.dockerignore` is `*` with `!base`, `!claude`, `!versions.env` [VERIFIED: .dockerignore lines 2-5].

### Pitfall 4: Globs that match nothing fail the guard
**What goes wrong:** `nowhere_matches` fails when `grep` cannot read a file (exit status above 1), and `shellcheck` fails on a literal unexpanded glob. ### Pitfall 5: hadolint DL4006 on the new Dockerfile
**What goes wrong:** hadolint reads each Dockerfile alone; a `|` in a RUN with no `SHELL ... pipefail` in that file raises DL4006 at warning level, and `.hadolint.yaml` fails at `warning` [VERIFIED: .hadolint.yaml `failure-threshold: warning`, ignores only DL3008 and DL3066].
**How to avoid:** write the Cursor RUN without a pipe (download both files, `sha256sum -c`, `tar`), or declare `SHELL ["/bin/bash", "-o", "pipefail", "-c"]` in `cursor/Dockerfile`.

### Pitfall 6: The tool-versions line and host check H-30
**What goes wrong:** `claude/Dockerfile:82-85` builds `claude X | gsd Y | ccusage Z | <base fields>` and greps that exact shape; H-30 hard-codes the same order [VERIFIED: claude/Dockerfile:82-85; tests/host/h30-version-line.sh:26 on `chore/test-diet`]. GSD moves to base, so base owns the `gsd` field, and the Claude Dockerfile can no longer put `ccusage` after it by prefixing alone.
**How to avoid:** recommended shape: base writes `gsd G | node ... | python ...` (its own grep updated, `base/Dockerfile:199`); Claude puts `claude C | ccusage U | ` in front; Cursor puts `cursor-agent V | ` in front. That reorders the Claude line (`ccusage` before `gsd`), so edit the one `expectedLine=` in H-30 and the Claude grep. The alternative that keeps the Claude line byte-identical is a `sed` in the Claude RUN that inserts `ccusage` after `gsd`; it is shorter to read as a reorder. Either way, do not change the other fields.

### Pitfall 7: Compose and the direct-compose host checks
**What goes wrong:** host checks call `docker compose` with only `SBX_NAME` and `SBX_DIR` (H-03, H-10, H-20, `compose_cmd` in `tests/host/lib-sandbox.sh:33`, the cleanup hint in `tests/host/run-all.sh:149`). A strict `${SBX_AGENT:?...}` would break all of them. [VERIFIED: grep of tests/host/*.sh on `chore/test-diet`]
**How to avoid:** `image: "sbx-${SBX_AGENT:-claude}:local"`. The default is safe because `run_compose` is the only path from the registry and always sets `SBX_AGENT`. The host-test sandbox is a Claude sandbox.

### Pitfall 8: An invalid third argument must stay a usage error
The self-test "three arguments print the usage and exit 2" runs `sbx-add demo "$WORK/u3" extra`, expecting exit 2 and the text `Usage: sbx-add NAME HOST_PATH` [VERIFIED: tests/selftest/sbx/add.sh:79,89-90]. `has_text` is a fixed-substring match [VERIFIED: tests/selftest/lib-expect.sh:37 `grep -Fq`], so a new usage line `Usage: sbx-add NAME HOST_PATH [claude|cursor]` still contains it. If an unknown agent is reported through `sbx_usage` (exit 2), that case passes unchanged.

### Pitfall 9: Stale bundle rule link would be inert and could clobber user rules
See Open Questions 2. `10-best-practices` begins with `rm -rf "$configDir/rules"` [VERIFIED: claude/start.d/10-best-practices:33]. Copied unchanged into the Cursor hook, it would delete a real `~/.cursor/rules` folder the user created.

### Pitfall 10: GSD bump now rebuilds both agent images
GSD sits in `sbx-base`, so a GSD pin bump changes the base image and invalidates every later layer of both agent images (the Claude Code install, the 175 MB Cursor download). That is the cost of D-02 (decided); say it in the README bump note.
