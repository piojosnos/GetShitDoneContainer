## Summary

The phase moves GSD, `sbx-gh-login` and `sbx-bundle-clone` into `sbx-base`, adds `cursor/Dockerfile` with three start hooks, and makes the agent a registry value that picks the compose image. I ran the guard rules and both selftest suites in the dev sandbox; all pass. I traced the Claude path against the old hook: `sbx-link-bundle rules` links the same rules link and the same skill links as the old `10-best-practices`, and the Claude image keeps the same files, ENV and tool-versions fields (only the field order changes, and H-30 follows it). Bash 3.2 portability holds in `bin/` (`${var// /|}` and plain `for ... in $list` only). No dashes as punctuation, no non-ASCII and no planning IDs in the changed source files.

No blocker was found. The two warnings are a design coupling in the shared linker and an unprotected wiring point that decides which image a sandbox runs. The rest are small.

## Warnings

### WR-01: `sbx-link-bundle` in no-rules mode links nothing when the clone has no `rules/` folder

**File:** `base/bin/sbx-link-bundle:118-125`
**Issue:** The main block gates the whole link step on `[ -d "$bundleDir/rules" ]`. That test made sense when the only caller linked rules. In `no-rules` mode (the Cursor image) rules are never used, yet a clone that holds `skills/` but no `rules/` folder gets no skill links, and the message says `no best-practices clone at ...; run sbx-bundle-clone`, which is wrong advice for an existing clone. The check `check_links_reach_clone` is skipped for the same reason.
**Fix:** Gate on the folder the mode needs:
```bash
if [ "$linkMode" = rules ]; then
  needDir=$bundleDir/rules
else
  needDir=$bundleDir/skills
fi

if [ -d "$needDir" ]; then
  check_links_reach_clone || exit 1
  link_bundle
  ...
```
Add a selftest case: a clone with `skills/` only, `no-rules` mode, expects the skill links.

### WR-02: Nothing checks that a Cursor sandbox is started on the Cursor image

**File:** `bin/sbx-lib.sh:207`, `compose.yml:13`
**Issue:** The one thing that makes a Cursor sandbox a Cursor sandbox is `SBX_AGENT="$entryAgent"` in `run_compose` plus `image: "sbx-${SBX_AGENT:-claude}:local"`. The default `:-claude` means that if either side is lost or renamed, every Cursor sandbox silently starts the Claude image: no error, no failing guard rule, no selftest, and per D-16 no host check. `entry.sh` only tests `read_registry_entry`; the Mac gate is a manual step. `require_images` and `runs_older_image` also pass for the wrong image because they read the same `agentImage`.
**Fix:** Add one cheap static guard rule (no new harness needed), for example in `tests/guard/isolation.sh` or `supply-chain.sh`:
```bash
compose_image_follows_the_agent() {
  grep -Fq 'image: "sbx-${SBX_AGENT:-claude}:local"' compose.yml \
    && grep -Fq 'SBX_AGENT="$entryAgent"' bin/sbx-lib.sh
}
```

## Info

### IN-01: Session warnings still say "Claude sessions" for every agent

**File:** `bin/sbx-lib.sh:250` (`warn_sessions_close`), `bin/sbx-list:~122` (older image note), `README.md` (Start/Upgrade sections)
**Issue:** `sbx-shell`'s header comment was reworded for both agents, but the runtime message "will close its open shells and Claude sessions" and the `sbx-list` note still name Claude, so a Cursor sandbox gets a misleading warning. The selftest group "the shared warning" pins the current text.
**Fix:** Say "agent sessions" in the three places and update the pinned text in `tests/selftest/sbx/`.

### IN-02: `02-no-self-update` replaces `cli-config.json` with default permissions

**File:** `cursor/start.d/02-no-self-update:51-57`
**Issue:** `jq ... >"$configFile.tmp"` then `mv` gives the new file the umask default mode (644), whatever mode the CLI gave the original. The file holds settings, not the token (that is `auth.json`), so the exposure is small, and the Mac mount does not enforce modes. It is still a silent mode change at every start.
**Fix:** Copy the mode first, for example `chmod --reference` is GNU only, so inside the Linux image it is fine: `chmod --reference="$configFile" "$configFile.tmp"` before the `mv`.

### IN-03: The Cursor package checksum comes from the same host as the package

**File:** `cursor/Dockerfile:22-28`
**Issue:** `sha256sum -c` against a `.sha256` fetched from `downloads.cursor.com` catches a corrupt download, not a swapped version (an attacker who replaces the tarball replaces the checksum file too). This matches how Node and gh are handled and the research accepted it, but the agent is the one tool in the image that holds a login token and runs with open network. A per-arch digest pin in `versions.env` would close it, at the cost of two more pins per bump and a looser `pins_are_exact` rule.
**Fix:** Optional. If kept, say in the Dockerfile comment (and README bump steps) that the checksum guards against corruption only.

### IN-04: `sbx-add NAME PATH ""` registers `claude` silently

**File:** `bin/sbx-add:281`
**Issue:** `agentName=${3:-claude}` treats an empty third argument like a missing one. A script that passes an empty `$AGENT` gets a Claude sandbox with no error.
**Fix:** `if [ "$#" -eq 3 ]; then agentName=$3; else agentName=claude; fi`.

### IN-05: Cursor skill links are documented as working, but not proven

**File:** `README.md` ("In a Cursor sandbox" list), `cursor/start.d/10-best-practices`
**Issue:** `06.1-CURSOR-GAPS.md` says it is unproven that Cursor follows a symlinked skill folder. The README states the skills are linked "the same way" without that caveat, and `h14` does not probe the new root-owned `sbx-link-bundle` (it probes `sbx-gh-login` and `sbx-bundle-clone` only).
**Fix:** Add one README line that the skill links are checked by hand on the Mac, and add `/usr/local/bin/sbx-link-bundle 755` to the H-14 probe list the next time that file changes.
