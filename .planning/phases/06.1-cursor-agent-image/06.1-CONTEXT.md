# Phase 06.1: Cursor agent image - Context

**Gathered:** 2026-11-13
**Status:** Ready for planning

<domain>
## Phase Boundary

A sandbox can run Cursor instead of Claude, from its own image `sbx-cursor:local`. The Cursor sandbox works like a Claude sandbox: the same base tools, GSD, the gh login helper and the best-practices bundle, with only the agent CLI and its config folder different. The sandbox's agent is picked once, by `sbx-add`. Scrappy: no new host checks; a Cursor login and one prompt on the Mac are the gate. Success criteria in `.planning/ROADMAP.md` Phase 06.1 (criteria 1 and 2 reworded by this discussion).

</domain>

<decisions>
## Implementation Decisions

### Image layers
- **D-01:** Two layers stay: `sbx-base` then one thin image per agent. No third "agent common" layer and no single image holding both agents.
- **D-02:** What both agents share moves into `sbx-base`: the GSD package (`@opengsd/gsd-core` at `GSD_CORE_VERSION`), `sbx-gh-login` and `sbx-bundle-clone`. GSD goes late in the base Dockerfile, so a GSD bump rebuilds only the last base layers. The GSD pin moves to the `sbx-base` section of `versions.env`. — **Reversibility:** costly — moving them back touches both agent Dockerfiles, the base Dockerfile and the guard rules that name which image holds what.
- **D-03:** `claude/` keeps only what is Claude's: Claude Code, ccusage, `sbx-claude`, the managed settings and the Claude start hooks. `cursor/` holds only the Cursor CLI, its env and its start hooks.
- **D-04:** The general tools (JDK, Maven, Python, Node, gh, uv) stay exactly as they are in `sbx-base`; neither agent image adds or changes one.

### Cursor CLI install
- **D-05:** The Cursor CLI version is pinned as `CURSOR_AGENT_VERSION` in `versions.env` and its package for that version is downloaded directly in `cursor/Dockerfile`, never through a pipe to a shell. A build-time smoke test checks the installed version equals the pin, as `claude/Dockerfile` does for Claude.
- **D-06:** Cursor's self-update is turned off, the Cursor counterpart of `DISABLE_UPDATES`.
- **D-07:** Fallback only if research finds no versioned linux/arm64 download: download the install script, keep it in the build, then run it; the version is then unpinned and the plan says so.

### GSD and the bundle in Cursor
- **D-08:** A Cursor start hook mirrors `claude/start.d/05-gsd`: it runs `gsd-core --cursor --global` into the Cursor config folder at every start and checks the synced version against the image's.
- **D-09:** The best-practices bundle is used from Cursor: the bundle clone is linked into Cursor's config the same way `10-best-practices` links it into Claude's, at the paths where the Cursor CLI reads global rules and skills.
- **D-10:** Rules or skills that do not work in Cursor (for example `pr-reply` or `merged`, or rule text naming `~/.claude/...` paths) are listed in the phase output, not rewritten in this phase.

### Agent choice and the shell
- **D-11:** `sbx-add NAME HOST_PATH [claude|cursor]`: an optional third argument, `claude` when omitted. The registry entry keeps its `SBX_AGENT=` line; `read_registry_entry` accepts `claude` and `cursor`.
- **D-12:** No command switches the agent of an existing sandbox. The user edits the registry line, or runs `sbx-rm` then `sbx-add`, which keeps the files.
- **D-13:** Compose starts the image that matches the entry's agent. `build.sh` and `sbx-upgrade` always build both agent images.
- **D-14:** `sbx-shell` opens bash for both agents; the user starts `claude` or `cursor-agent` from that shell. No `sbx-cursor` launcher. `sbx-claude` stays as it is (Phase 9 keeps it as the warning wrapper); that asymmetry is accepted.

### Cursor state
- **D-15:** One folder `state/cursor/` holds Cursor's login and settings. `~/.cursor` and `~/.config/cursor` (or wherever research finds Cursor keeps its auth and config) link into it, as `~/.claude` links to `state/claude`. `cursor` is appended to `SBX_STATE_DIRS` in the Cursor image.

### Tests
- **D-16:** No new host checks: the test harness is rewritten in Phase 10, so tests written now would be thrown away. Phase 10 gets a criterion that the host tests are one shared harness run for each agent, with only small agent-specific checks.
- **D-17:** The static guard rules that cover `claude/Dockerfile` (one `FROM`, nothing piped to a shell, and the like) also cover `cursor/Dockerfile`. This extends the files the guard lists; it adds no new rule.
- **D-18:** The Mac gate: `./host-test.sh` passes (Claude sandboxes work as before), then by hand a Cursor sandbox is added, logs in, answers one prompt in its workspace, and the login survives an `sbx-upgrade`.

### Claude's Discretion
- How compose picks the image (for example `image: sbx-${SBX_AGENT}:local` with the variable passed by `run_compose`) and how `require_images` and `runs_older_image` name the agent's image.
- How the bundle hook is shared or mirrored between the two agent images, and whether `sbx-bundle-clone` links per agent or the start hook does.
- The Cursor tool-versions line in `/etc/sbx/tool-versions`.
- Doc updates in `README.md` for the third `sbx-add` argument, the Cursor image and the moved helpers.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- The registry entry already has `SBX_AGENT=claude`, and `read_registry_entry` already parses it into `entryAgent`; only the accepted values change.
- `05-gsd` already takes the config folder from an env var; a Cursor copy differs in the env var and `--cursor`.
- `build.sh` passes every `versions.env` pin as a build arg, so a new pin needs no `build.sh` change beyond building the third image.

### Established Patterns
- Tools install as root into `/usr/local`, never under `/home/sandbox/workspace` (the mount hides it); the last RUN checks the mount point is empty.
- Every pin is a required ARG with no default, checked with `: "${X:?...}"`.
- Config folders the agent writes live under `state/` and are linked from `$HOME`.

### Integration Points
- `compose.yml` image line, `run_compose` env, `require_images`, `runs_older_image`, the `sbx-add` success message.

</code_context>
