### Locked Decisions

#### Bootstrap: shell first, three wrapper scripts
- **D-01:** The sandbox start never launches Claude; the user gets a shell (as today: `sleep infinity` plus `docker exec`). Three small wrapper scripts, baked into the Claude image on `PATH`, run inside that shell in this order:

  | Script | Does |
  |---|---|
  | `sbx-gh-login` | `gh auth login`, then `gh auth setup-git` so git over HTTPS uses that login. The login persists in `state/gh` |
  | `sbx-bundle-clone` | `git clone "$BUNDLE_REPO_URL"` into the clone folder (D-05), then links it into Claude (D-07) |
  | `sbx-claude` | Runs `claude` (passes its arguments through) |

  They are mere wrappers: a few plain lines each, same banner layout as every other script.
- **D-02:** The repo URL lives in one place: `BUNDLE_REPO_URL` in `versions.env`. `build.sh` already passes every name in that file as a build arg; the Claude Dockerfile turns it into image ENV, so changing the repo means editing that line and rebuilding. The `versions.env` header comment is adjusted, since this one line is a setting, not a version.
- **D-03:** The design works for a public or a private repo (the clone runs after gh login). The repo is created **private**.
- **D-04:** `sbx-claude` with no clone yet still runs Claude, after a warning the user cannot miss: a clearly marked multi-line message naming `sbx-bundle-clone`, then a pause of a few seconds before Claude takes over the screen.

#### Clone location and live updates
- **D-05:** The clone sits at `<sandbox>/best-practices` on the Mac, which is `/home/sandbox/workspace/best-practices` in the container: a plain subfolder of the one mount, next to `<name>/` and `state/`. No compose change. Git works on it from the Mac even with the container down. **Reversibility:** costly. Why: every sandbox's clone, the links and the docs assume this path.
- **D-06:** No automatic pull, ever. The start hook does not fetch or pull. Updating the clone is the user's lifecycle: `git pull` on the Mac, in the sandbox shell, or by asking Claude. A fresh `sbx-bundle-clone` gets the latest version. This amends roadmap success criterion 4 and BP-05 (done in this discussion).
- **D-07:** Claude reads the clone through relative symlinks, not copies: `state/claude/rules` points to the clone's `rules/`, and each bundle skill in `state/claude/skills/` points to the clone's skill folder. Relative so the links resolve both in the container and on the Mac. A pull or an edit takes effect without a resync. **Research must verify** that Claude Code at the pinned version follows these symlinks for rules (always-on and `paths:` scoped) and skills. If it does not, fall back to copies plus a git `post-merge` hook in the clone that reruns the copy.
- **D-08:** The start hook `10-best-practices` keeps the Phase 1.2 ownership model (rules is fully owned; bundle skills tracked by the manifest list, GSD and user skills never touched; bundle wins a name clash) but now (re)creates links from the clone instead of copying from the image. When the clone is missing, the start succeeds with no bundle and prints one line saying so; it does not fail. `sbx-bundle-clone` reuses the same linking code, so a fresh clone is live without a restart.
- **D-09:** The image no longer carries the bundle: no `COPY best-practices`, no `/opt/sbx/best-practices`, and `best-practices/` leaves this repo (roadmap criterion 1, one source of truth).

#### Claude reads, amends and publishes the practices
- **D-10:** Claude must be able to answer questions about the practices, amend them on request, and open a PR for them. So:
  - The generated-file header in every rule and skill goes away (there are no generated copies anymore).
  - The bundle gets one short always-on rule saying where the practices live (`/home/sandbox/workspace/best-practices`) and how to change them: edit in the clone, branch, commit, push only with the user's go, open a PR against the bundle repo, the user merges. It points at the existing git workflow rule instead of repeating it.
  - The managed Edit deny rules must not block edits in the clone. **Research must verify** whether Claude can edit the clone, which is outside the project folder it starts in (likely needs an allowed directory in the managed settings), and how deny rules match a path reached through a symlink.

#### Creating the bundle repo
- **D-11:** Claude creates `piojosnos/claude-best-practices` (private) with `gh repo create` during execution, seeded with the history of `best-practices/` (`git subtree split`), then the header removal and the new rule (D-10) land there as a PR. Creating the repo and every push are outward-facing: the plan has a human checkpoint at each, and the user merges every PR.

## Summary

Both flagged Claude Code behaviours are settled by running the pinned binary. The dev sandbox's `claude` reports `2.1.285 (Claude Code)`, the same as the pin, so there is no version gap. With a scratch config folder whose `rules` is a relative symlink to a clone's `rules/` and whose bundle skills are relative symlinks to the clone's skill folders, Claude loads the always-on rules, loads the `paths:` scoped rule only after a matching file is read, and lists the symlinked skills. The copies-plus-post-merge-hook fallback is not needed. One side effect matters for the tests: Claude reports the **resolved** path of a symlinked rule (`.../best-practices/rules/x.md`), not `state/claude/rules/x.md`.

Editing the clone from a project folder elsewhere works under `bypassPermissions` with no setting at all, but under `default`, `acceptEdits` (and, by the docs, the auto mode that is the interactive default from 2.1.283) it needs `permissions.additionalDirectories` pointing at the clone. The current managed deny `Edit(//home/sandbox/workspace/state/claude/rules/**)` **blocks the real clone path too**, because Claude applies a deny written through a symlinked directory at the directory's real location. That entry must go. `Edit(.../skills/**)` can stay: it denies the symlink path under `state/claude/skills/` (protecting GSD's skills) but not the clone's real path, so skill edits in the clone are allowed.

The rest is wiring. The image drops the bundle and gains three wrapper scripts, one ARG/ENV for `BUNDLE_REPO_URL` and one for the clone path. The start hook becomes a link maker (prototype validated: idempotent, upgrades the old copy layout, clone-less start succeeds, dangling links are harmless to Claude). `gh auth setup-git` writes into `GIT_CONFIG_GLOBAL` (verified), so the git credential helper persists in `state/git/config`. `git subtree split` on `main` yields 10 commits with a deterministic hash; 3 commit subjects carry phase IDs, which is a decision for the user at the seed checkpoint. The host tests need a fixture bundle (the real one leaves the repo) and a local bare repo with `--initial-branch=main`.

**Primary recommendation:** Link, do not copy. Use relative symlinks created by the rewritten `10-best-practices` hook (rm then `ln -s`, never `ln -s` over an existing link), put `additionalDirectories` for the clone in managed settings, delete the `rules/**` deny and keep `skills/**` and the manifest deny, define `SBX_BUNDLE_DIR` and `BUNDLE_REPO_URL` once as image ENV, and let `sbx-bundle-clone` call the hook so there is one piece of linking code.

### Pattern 1: Relative links made by remove-then-link
**What:** The hook removes what it owns (`rules`, the skills listed in the manifest), then creates relative links. `rm -rf` on a symlink removes only the link; it never touches the clone.
**When to use:** Every start and from `sbx-bundle-clone`.
**Why not `ln -sf`:** `ln -s TARGET LINK` where LINK is an existing symlink to a directory creates the new link **inside the target directory**, i.e. inside the clone. Remove first. `[VERIFIED: rerun of the hook left 0 symlinks inside the clone]`
**Example (validated in a scratch workspace; the derived-path variant was run, the `SBX_BUNDLE_DIR` variant differs only in the first lines):**
```bash
#!/usr/bin/env bash
# ------------------------------------------------------------------------------
# Links the best-practices clone into the Claude config at every start
# ------------------------------------------------------------------------------
# Other skills (GSD, your own) are never touched. A start with no clone goes on.
# ------------------------------------------------------------------------------
set -eu

configDir=${CLAUDE_CONFIG_DIR:-}
bundleDir=${SBX_BUNDLE_DIR:-}
skillList=$configDir/.best-practices-skills

# ------------------------------------------------------------------------------
# check_inputs: stops the start when either folder variable is empty
# ------------------------------------------------------------------------------
check_inputs() {
  if [ -z "$configDir" ] || [ -z "$bundleDir" ]; then
    echo "[sbx] ERROR: CLAUDE_CONFIG_DIR or SBX_BUNDLE_DIR is not set." >&2
    exit 1
  fi
}

# ------------------------------------------------------------------------------
# remove_old_links: removes rules/ and the skills the last start listed
# ------------------------------------------------------------------------------
# rm -rf on a link removes the link, never the clone. It also clears the real
# copies an older start left.
# ------------------------------------------------------------------------------
remove_old_links() {
  local oldName

  rm -rf "$configDir/rules"

  if [ ! -f "$skillList" ]; then
    return
  fi

  while IFS= read -r oldName; do
    case "$oldName" in
      ""|*/*|.*) continue ;;
    esac

    rm -rf "$configDir/skills/$oldName"
  done <"$skillList"

  rm -f "$skillList"
}

# ------------------------------------------------------------------------------
# link_bundle: links rules/ and each skill folder with relative targets
# ------------------------------------------------------------------------------
# Relative, so the links resolve in the container and on the Mac alike. The
# final test fails the start when the clone is not where the links expect it.
# ------------------------------------------------------------------------------
link_bundle() {
  local skillDir skillName

  ln -s ../../best-practices/rules "$configDir/rules"
  : >"$skillList"

  for skillDir in "$bundleDir"/skills/*/; do
    if [ ! -d "$skillDir" ]; then
      continue
    fi

    skillName=$(basename "$skillDir")
    echo "$skillName" >>"$skillList"
    rm -rf "$configDir/skills/$skillName"
    ln -s "../../../best-practices/skills/$skillName" "$configDir/skills/$skillName"
  done

  if [ ! -d "$configDir/rules" ]; then
    echo "[sbx] ERROR: the rules link does not resolve to $bundleDir/rules" >&2
    exit 1
  fi
}

# ------------------------------------------------------------------------------
# Main / Entry Point
# ------------------------------------------------------------------------------
check_inputs
mkdir -p "$configDir/skills"
remove_old_links

if [ -d "$bundleDir/rules" ]; then
  link_bundle
  echo "[sbx] best-practices linked from $bundleDir"
else
  echo "[sbx] no best-practices clone at $bundleDir; run sbx-bundle-clone"
fi
```
Scenarios run against the derived-path prototype, all passing: no clone (exit 0, one line); upgrade from the Phase 1.2 copy layout (real `rules/` dir and real skill copy replaced by links, user skill and `gsd-*` skill untouched); rerun is idempotent; a skill dropped from the clone loses its link and manifest entry at the next run; clone removed (links removed, exit 0); bad config dir (exit 1). `[VERIFIED: scratch runs this session]`

### Pattern 2: Wrappers are a few plain lines
`sbx-bundle-clone` calls the hook instead of duplicating the link code (discretion item; recommended). Skeletons (clone wrapper validated with a local bare repo and a stand-in hook folder):
```bash
#!/usr/bin/env bash
# ------------------------------------------------------------------------------
# Clones the best-practices repo into the sandbox folder and links it into Claude
# ------------------------------------------------------------------------------
# Usage: sbx-bundle-clone (run sbx-gh-login first when the repo is private)
# Never overwrites: an existing folder stops the script.
# ------------------------------------------------------------------------------
set -eu

: "${BUNDLE_REPO_URL:?BUNDLE_REPO_URL is not set}"
: "${SBX_BUNDLE_DIR:?SBX_BUNDLE_DIR is not set}"

# ------------------------------------------------------------------------------
# Main / Entry Point
# ------------------------------------------------------------------------------
if [ -e "$SBX_BUNDLE_DIR" ]; then
  echo "[sbx] ERROR: $SBX_BUNDLE_DIR already exists; nothing was changed." >&2
  echo "[sbx]        To update it: git -C $SBX_BUNDLE_DIR pull" >&2
  exit 1
fi

if ! GIT_TERMINAL_PROMPT=0 git clone "$BUNDLE_REPO_URL" "$SBX_BUNDLE_DIR"; then
  echo "[sbx] ERROR: cannot clone $BUNDLE_REPO_URL. A private repo needs sbx-gh-login first." >&2
  exit 1
fi

/etc/sbx/start.d/10-best-practices
```
`GIT_TERMINAL_PROMPT=0` makes a missing login fail fast: `fatal: could not read Username for 'https://github.com': terminal prompts disabled` (exit 128) `[VERIFIED: ran without credentials]`. Without it git would wait on a prompt.

### Anti-Patterns to Avoid
- **`ln -sf` or `ln -s` over an existing link or directory:** nests a link inside the clone (see Pattern 1).
- **Keeping `Edit(.../rules/**)` in managed deny:** it blocks the clone's `rules/` by real path (run D).
- **Reading the resolved memory path as `state/claude/rules/...`:** Claude lists `/home/sandbox/workspace/best-practices/rules/<file>` (see below); H-15's string match must change.
- **Putting `git pull` or `git fetch` in the hook:** locked out by D-06; H-17's `--network none` start would also fail.
- **Linking `skills/` as a whole directory:** `state/claude/skills/` also holds GSD's real skill folders, so links are per skill.

## Common Pitfalls

### Pitfall 1: The real-path deny
**What goes wrong:** Leaving `Edit(.../state/claude/rules/**)` in the managed deny makes every edit of the clone's `rules/` fail, by symlink path and by real path.
**Why it happens:** Claude applies a deny written through a symlinked directory at the directory's real location.
**How to avoid:** Delete that entry; test in H-18 that a clone rule edit succeeds.
**Warning signs:** "File is in a directory that is denied by your permission settings" on `best-practices/rules/...`.

### Pitfall 2: Memory path in `/context` changes
**What goes wrong:** H-15 looks for `/home/sandbox/workspace/state/claude/rules/<file>` and fails, although the rules loaded.
**Why:** Claude lists the resolved path (`.../best-practices/rules/<file>`). `[VERIFIED: /context output in scratch listed .../exp1/ws/best-practices/rules/communication.md]`
**How to avoid:** Match the clone path. Scoped rules: assert they are absent from `/context` at start.

### Pitfall 3: `ln -s` over an existing link
**What goes wrong:** A link is created inside the clone (`best-practices/rules/rules`), polluting a git repo.
**How to avoid:** Remove first; the self-test asserts the clone holds zero symlinks after two runs.

### Pitfall 4: Guard globs on a deleted folder
**What goes wrong:** `no_compromised_gsd_package` FAILs the moment `best-practices/` is gone.
**How to avoid:** Edit the file list in the same commit that deletes the folder.

### Pitfall 5: `BUNDLE_REPO_URL` vs `pins_are_exact`
**What goes wrong:** The first guard run after adding the line prints "the name must end in _VERSION or _IMAGE".
**How to avoid:** Extend the rule (allow `_URL`, require `https://`) and add a self-test case in the same plan.

### Pitfall 6: A bare repo whose HEAD is `master`
**What goes wrong:** Cloning a fixture `git init --bare` repo that received `main` prints `warning: remote HEAD refers to nonexistent ref, unable to checkout` and gives an empty working tree. The hook then says "no best-practices clone", which looks like a hook bug. `[VERIFIED: hit it in the prototype]`
**How to avoid:** `git init --bare --initial-branch=main`.

### Pitfall 7: New or removed skills after a pull
**What goes wrong:** Rules are one directory link, so a pull that adds a rule is live. Skills are per-skill links made at start or clone time, so a pull that **adds** a skill shows nothing until the hook runs, and one that **removes** a skill leaves a dangling link (harmless to Claude, verified).
**How to avoid:** Document: after a pull that adds or removes a skill, restart the sandbox or run `/etc/sbx/start.d/10-best-practices`. Rejected alternative: a `post-merge` hook in the clone (runs with the Mac's shell on a Mac pull).

### Pitfall 8: Clone created on the Mac while the container runs
**What goes wrong:** Links exist only after a start or a hook run; `sbx-bundle-clone` refuses an existing folder.
**How to avoid:** Same documentation line as Pitfall 7. Optionally `sbx-claude` could run the hook first; that breaks "mere wrapper" and is not recommended.

### Pitfall 9: Sandbox named `best-practices`
**What goes wrong:** `$ws/$SBX_NAME` and the clone folder are the same path; the name passes the current pattern.
**How to avoid:** Reserve the name in `check_sandbox_name` (see change map).

### Pitfall 10: Host tests that touch the user's git identity or real repo
**What goes wrong:** Fixture commits pick up the Mac user's `user.name`; a test pushes or pulls the real private repo.
**How to avoid:** `git -c user.name=... -c user.email=...` for every fixture commit; the automated checks never name the real URL; the container-side clone test passes `-e BUNDLE_REPO_URL=<local bare path>` via `docker exec`.

### Pitfall 11: Interactive default permission mode
**What goes wrong:** From 2.1.283 interactive terminal sessions start in auto mode `[CITED: code.claude.com/docs/en/permission-modes]`. Edits outside the working directory are classifier-reviewed there; `additionalDirectories` is what makes the clone count as a working directory. Auto mode could not be exercised here (needs a real account).
**How to avoid:** Keep `additionalDirectories` (covers every mode); put one observation of "ask Claude to amend a rule" in the manual H-19 helper.

### Pitfall 12: Deleting `.best-practices-skills` entries vs real user skills
**What goes wrong:** "bundle wins a name clash" means `rm -rf` of a same-named real user skill folder. This is the existing Phase 1.2 behaviour, unchanged, but the hook now also deletes real copies from the old layout. Intended.

In the image gh is at `/usr/local/bin/gh` `[VERIFIED: base/Dockerfile:60 extracts gh into /usr/local/bin]`, so the stored helper path is `/usr/local/bin/gh`. `GIT_CONFIG_GLOBAL` is image ENV for every shell `[VERIFIED: base/Dockerfile:125 "GIT_CONFIG_GLOBAL=/home/sandbox/workspace/state/git/config"]`, so `git config --global` and `gh auth setup-git` both land in `state/git/config`, and the helper survives recreate and rebuild. ## Open Questions

1. **Constant path versus `SBX_BUNDLE_DIR` ENV.**
   - What we know: the approved Phase 2.1 re-scan cut R-19 removes the hook's old `SBX_BUNDLE_DIR` override, quoting "Use the constant path" `[VERIFIED: .planning/phases/02.1-shell-diet/02.1-RESCAN.md:29]`. That cut is part of the pending second shell-diet PR, which may or may not land before this phase's code.
   - What's unclear: R-19's reason was that nothing set the variable; now three scripts and the self-test would.
   - Recommendation: define `SBX_BUNDLE_DIR` once as image ENV (a constant in the Dockerfile, like `GH_CONFIG_DIR`) and read it everywhere. Alternative with no new variable: derive the clone as `${CLAUDE_CONFIG_DIR%/state/claude}/best-practices` (this was the variant I ran), at the cost of that line in three scripts (the third copy should be consolidated per the code conventions). Tell the planner to coordinate with the pending diet PR so the two edits of `10-best-practices` do not conflict.

2. **Reword the 3 seeded commit subjects?**
   - What we know: see Seeding. No AI attribution in the history.
   - What's unclear: whether the "no internal IDs" rule extends to commit subjects.
   - Recommendation: ask at Checkpoint 2; default to rewording (cheap, one-way door once pushed).

3. **Token scope and branch protection.** `gh auth login` (default scopes include `repo`) gives the in-container agent push rights to **all** the user's repos, and "push only with the user's go" is rule text, not enforcement. A fine-grained token limited to the bundle repo would cap that, but gh's own help warns that fine-grained tokens "may cause confusing behaviour"; branch protection may not exist on a private Free repo (A6). Recommendation: keep the default login (it matches what SANDBOX.md already documents), note the risk in the SANDBOX.md section, and offer the fine-grained token as an optional hardening for the user to decide. DOC-03 (Phase 5) owns the threat-model write-up.

4. **Should `sbx-bundle-clone` accept an existing git clone and just relink?** Context says refuse. A relink-only path already exists (run the hook). Recommendation: refuse, and print the two commands (`git pull`, run the hook) in the message.

5. **Pause length.** Recommendation 5 seconds (the host check waits that long once).
