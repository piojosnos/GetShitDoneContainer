# Phase 2.2: Best-practices from git, editable from any sandbox - Context

**Gathered:** 2026-10-16
**Status:** Ready for planning

<domain>
## Phase Boundary

The best-practices bundle (`rules/`, `skills/`) leaves this repo and becomes its own GitHub repo, `piojosnos/claude-best-practices`. Each sandbox keeps its own clone in its sandbox folder on the Mac. Claude reads the practices straight from that clone, so an edit or a `git pull` reaches the running sandbox at once. From inside the sandbox the user (or Claude, when asked) can read, amend and publish the practices as a PR. A change reaches other sandboxes only after the PR is merged and that sandbox pulls.

Out of this phase: host-side `sbx-*` lifecycle scripts (Phases 3 and 4), CI (Phase 6).

</domain>

<decisions>
## Implementation Decisions

### Bootstrap: shell first, three wrapper scripts
- **D-01:** The sandbox start never launches Claude; the user gets a shell (as today: `sleep infinity` plus `docker exec`). Three small wrapper scripts, baked into the Claude image on `PATH`, run inside that shell in this order:

  | Script | Does |
  |---|---|
  | `sbx-gh-login` | `gh auth login`, then `gh auth setup-git` so git over HTTPS uses that login. The login persists in `state/gh` |
  | `sbx-bundle-clone` | `git clone "$BUNDLE_REPO_URL"` into the clone folder (D-05), then links it into Claude (D-07) |
  | `sbx-claude` | Runs `claude` (passes its arguments through) |

  They are mere wrappers: a few plain lines each, same banner layout as every other script.
- **D-02:** The repo URL lives in one place: `BUNDLE_REPO_URL` in `versions.env`. `build.sh` already passes every name in that file as a build arg; the Claude Dockerfile turns it into image ENV, so changing the repo means editing that line and rebuilding. The `versions.env` header comment is adjusted, since this one line is a setting, not a version.
- **D-03:** The design works for a public or a private repo (the clone runs after gh login). The repo is created **private**.
- **D-04:** `sbx-claude` with no clone yet still runs Claude, after a warning the user cannot miss: a clearly marked multi-line message naming `sbx-bundle-clone`, then a pause of a few seconds before Claude takes over the screen.

### Clone location and live updates
- **D-05:** The clone sits at `<sandbox>/best-practices` on the Mac, which is `/home/sandbox/workspace/best-practices` in the container: a plain subfolder of the one mount, next to `<name>/` and `state/`. No compose change. Git works on it from the Mac even with the container down. **Reversibility:** costly. Why: every sandbox's clone, the links and the docs assume this path.
- **D-06:** No automatic pull, ever. The start hook does not fetch or pull. Updating the clone is the user's lifecycle: `git pull` on the Mac, in the sandbox shell, or by asking Claude. A fresh `sbx-bundle-clone` gets the latest version. This amends roadmap success criterion 4 and BP-05 (done in this discussion).
- **D-07:** Claude reads the clone through relative symlinks, not copies: `state/claude/rules` points to the clone's `rules/`, and each bundle skill in `state/claude/skills/` points to the clone's skill folder. Relative so the links resolve both in the container and on the Mac. A pull or an edit takes effect without a resync. **Research must verify** that Claude Code at the pinned version follows these symlinks for rules (always-on and `paths:` scoped) and skills. If it does not, fall back to copies plus a git `post-merge` hook in the clone that reruns the copy.
- **D-08:** The start hook `10-best-practices` keeps the Phase 1.2 ownership model (rules is fully owned; bundle skills tracked by the manifest list, GSD and user skills never touched; bundle wins a name clash) but now (re)creates links from the clone instead of copying from the image. When the clone is missing, the start succeeds with no bundle and prints one line saying so; it does not fail. `sbx-bundle-clone` reuses the same linking code, so a fresh clone is live without a restart.
- **D-09:** The image no longer carries the bundle: no `COPY best-practices`, no `/opt/sbx/best-practices`, and `best-practices/` leaves this repo (roadmap criterion 1, one source of truth).

### Claude reads, amends and publishes the practices
- **D-10:** Claude must be able to answer questions about the practices, amend them on request, and open a PR for them. So:
  - The generated-file header in every rule and skill goes away (there are no generated copies anymore).
  - The bundle gets one short always-on rule saying where the practices live (`/home/sandbox/workspace/best-practices`) and how to change them: edit in the clone, branch, commit, push only with the user's go, open a PR against the bundle repo, the user merges. It points at the existing git workflow rule instead of repeating it.
  - The managed Edit deny rules must not block edits in the clone. **Research must verify** whether Claude can edit the clone, which is outside the project folder it starts in (likely needs an allowed directory in the managed settings), and how deny rules match a path reached through a symlink.

### Creating the bundle repo
- **D-11:** Claude creates `piojosnos/claude-best-practices` (private) with `gh repo create` during execution, seeded with the history of `best-practices/` (`git subtree split`), then the header removal and the new rule (D-10) land there as a PR. Creating the repo and every push are outward-facing: the plan has a human checkpoint at each, and the user merges every PR.

### Claude's Discretion
- Exact wording and length of the D-04 warning and the pause length (a few seconds).
- Whether the manifest file keeps its name `.best-practices-skills` and where the linking code lives (shared helper sourced by the hook and `sbx-bundle-clone`, or the clone script calls the hook).
- What `sbx-bundle-clone` does when the folder already exists (refuse with a clear message is the expected default; never overwrite).
- Which managed deny rules stay (for example `skills/**` still protects GSD's skills), as long as edits in the clone are allowed.
- How the host tests change: h14 to h19 and `lib-bundle.sh` rewritten for the clone and links, the `.dockerignore` and guard references updated, `prompts/consolidate-memories.md` and `SANDBOX.md` pointed at the bundle repo. The interactive steps (gh login, clone of a private repo) go in the manual pass; the automated checks can use a local bare repo as `BUNDLE_REPO_URL` or a pre-made clone folder.

</decisions>

## Existing Code Insights

### Reusable Assets
- `claude/start.d/10-best-practices`: `check_inputs`, `remove_listed_skills`, `copy_bundle_skills` become the link version almost line for line (`cp -R` becomes `ln -s`).
- `build.sh` passes every `versions.env` name as a build arg, so `BUNDLE_REPO_URL` needs no build script change.
- `gh` is already in the base image and `state/gh` persists its login.

### Established Patterns
- Start hooks in `/etc/sbx/start.d/`, run in name order, fail closed; error lines use `[sbx] ERROR: ...`.
- Agent state lives under `state/`; code under `<name>/`; everything on the one bind mount.
- Every pinned ARG fails the build when unset (`${X:?X is not set; build with ./build.sh}`); the same form fits `BUNDLE_REPO_URL`.

### Integration Points
- `claude/Dockerfile`: drop the bundle COPY, add the ENV and the three scripts.
- `state/claude/rules` and `state/claude/skills/<bundle skill>`: become links into `workspace/best-practices`.
- Managed settings: allowed directory for the clone (if research confirms it is needed), deny list adjusted.

</code_context>

<specifics>
## Specific Ideas

- The user wants the bootstrap as three tiny, obvious scripts run by hand in order (login, clone, claude), not automation hidden in the start.
- The `sbx-claude` warning must stay on screen long enough to read: a sleep before Claude starts.
- The clone must be usable from the Mac with the container down: pull, push and any git command.
- The user wants to be able to say to Claude: "what do the practices say about X", "amend the practices", "open a PR for the practices".

</specifics>
