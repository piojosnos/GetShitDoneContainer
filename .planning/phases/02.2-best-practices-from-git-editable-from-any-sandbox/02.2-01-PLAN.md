## Phase Goal

ROADMAP.md Phase 2.2 goal (verbatim): "The best-practices bundle lives in its own GitHub repo. Every sandbox keeps its own clone in its sandbox folder, starts with the latest version, and can send improvements back as PRs. Updates survive restarts and rebuilds, and reach other sandboxes only after the user reviews and merges them."

The roadmap marks this phase `mvp`, but the goal line is not in user-story form; it is quoted verbatim as in earlier phases (run `/gsd-mvp-phase 2.2` if a story is wanted).

This plan is the phase tracer: a clone in the sandbox folder is what Claude reads. One path runs end to end and is proven here, without Docker: a pin line in versions.env, the image ENV that names the clone folder, the rewritten start hook that links the clone into `state/claude`, and the pinned Claude listing the clone's rule and skill. Everything later builds out from this slice: the wrappers and settings (plan 03), the bundle repo (plans 02 and 04), the Mac checks (plans 05 and 06), the docs and the removal of the in-repo copy (plan 07).

Planning notes:
- **Open Question 1, decided: `SBX_BUNDLE_DIR` is one image ENV, set in claude/Dockerfile to `/home/sandbox/workspace/best-practices`, and read with no default.** Why: the approved Phase 2.1 re-scan cut R-19 ("use the constant path") answered a variable nothing set and that could redirect what was copied into `~/.claude`. Both reasons are gone: the image now sets it, the hook, two wrappers and the self-test read it, and it matches `GH_CONFIG_DIR`, `CLAUDE_CONFIG_DIR` and `HISTFILE`. The redirect risk is closed differently: the links use two fixed relative targets, and the hook's last test stops the start when they do not reach `$SBX_BUNDLE_DIR`, so the variable can only make a start fail, never load other content. Deriving the path from `CLAUDE_CONFIG_DIR` in each script was rejected: three copies of the same line. Plan 08 records in the pending shell-diet todo that R-19 is superseded.
- Research verified on Claude Code 2.1.285 (the pin) that symlinked rules (always-on and `paths:` scoped) and symlinked skill folders load; the copies plus post-merge fallback of D-07 is not needed. The planner re-ran the `/context` probe and the hook prototype this session; the tracer verify below is that probe.
- `ln -s` over an existing link to a folder creates the new link inside the clone (research pitfall 3, hit while prototyping). The hook removes before it links; the self-test asserts zero links inside the clone after a rerun, and Task 2 proves the case fails on a mutant hook that skips the removal.
- The `ARG BUNDLE_REPO_URL` check goes after the ccusage install, so a bare `docker build` still stops first on `CLAUDE_CODE_VERSION`, which host check H-25 expects.
- Reversibility: D-05 (the clone path) is rated costly by the discussion: every clone, both link targets and the docs assume `<sandbox>/best-practices`. Flagged on Task 1, not gated (already decided by the user).
- Size: the entrypoint self-test is 512 lines today (Phase 2.1 target 520). The new group adds about 110, because it is now the only automated cover of the hook (the bundle self-test was retired in 2.1). The total is recorded in the SUMMARY and shown to the user at the gate; the pending second shell-diet PR deletes a 51-line group of the same suite.

## Conventions carried into every edit

- Comment shape (Phase 2.1): a banner is a rule line of `# ` plus 78 dashes (80 columns), a title line, a rule line, then at most two "why" lines and a closing rule; with no why, the title sits between two rules. No comment line over 80 columns; never three plain comment lines in a row.
- Shell: `set -eu` in shipped scripts, `set -u` in tests; functions plus a `# Main / Entry Point` banner over a short list of calls; braces always; a blank line before and after every `if`/`for`/`while` (an `else` stays cuddled); full variable names; list variables end in `List`.
- ASCII only. No em or en dash, no ` -- ` or spaced ` - ` used as a dash, in comments, messages or docs; punctuation after a closing quote.
- No planning IDs in committed source, fixtures, comments or commit messages.
- The hook's text (code and comments) never uses the words git, fetch or pull, and none of the words the guard rule `no_installs_at_container_start` refuses (npm, npx, bunx, pip, apt, apt-get, curl, wget).
