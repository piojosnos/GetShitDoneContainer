# Phase 10.1: Code Review Report

**Reviewed:** 2026-11-24
**Depth:** standard
**Files Reviewed:** 38
**Status:** issues_found

## Summary

The generator is small and mostly careful: symlinks are refused, the masters are read fail-closed, Jinja never evaluates master text, and `generated/` is wiped only after its path is verified. The suite passes (88 tests) and `practices.check` reports no drift on the committed tree. No critical issue was found.

The defects are in the edges the tests do not reach. I confirmed four by running them against a copy of the fixture repo: `practices.check` passes when `generated` is a symlink; a YAML date such as `2026-13-45` in frontmatter raises an uncaught `ValueError` traceback; a quoted numeric skill name is emitted unquoted and changes type; a glob containing a newline injects an extra `alwaysApply` line into the Cursor frontmatter. The write path is not atomic, and two tests are fragile or too weak on macOS and on drift enforcement. The project also has no linter, which `python.md` and `coding-general.md` require.

## Warnings

### WR-01: `practices.check` passes when `generated` is a symlink (drift detection gap)

**File:** `practices/output.py:61-66` (also `practices/check.py:31-50`)
**Issue:** `write_output` refuses a symlinked `generated`, but `read_output_tree` only checks entries inside it. `generated_dir.is_dir()` follows the link and `rglob` walks the target. I reproduced it: after moving `generated/` to `real_gen/` and linking `generated -> real_gen`, `check.main([])` returned 0 with "matches the masters". A tracked symlink holds no generated content in git, so the check passes while the committed tree lacks every generated file. `generate` and `check` also disagree about what a valid `generated/` is.
**Fix:**
```python
def read_output_tree(repo_dir: Path) -> dict[str, OutputFile]:
    generated_dir = repo_dir / GENERATED_FOLDER

    if generated_dir.is_symlink():
        raise PracticesError(f"{GENERATED_FOLDER} is a link; {GENERATED_FOLDER}/ must be a plain folder")
    ...
```
Reuse `_check_generated_dir` or a shared helper so both paths apply the same rule, and add a test in `tests/test_check.py` next to `test_check_refuses_a_link_under_generated`.

### WR-02: Invalid YAML scalar raises an uncaught `ValueError` (traceback instead of a refusal)

**File:** `practices/reader.py:322-326`
**Issue:** Only `yaml.YAMLError` is caught. `yaml.safe_load` raises a plain `ValueError` for an implicit timestamp that matches the date pattern but is not a real date (`foo: 2026-13-45`), so `run_command` does not catch it and `generate` and `check` print a traceback. `cli.py` documents "neither shows a traceback". I confirmed `ValueError month must be in 1..12` escapes `generate.main`.
**Fix:**
```python
    except (yaml.YAMLError, ValueError) as e:
        raise PracticesError(f"{master_path}: the frontmatter is not valid YAML") from e
```
Add a `BROKEN_RULE_MASTER_LIST` case with `foo: 2026-13-45`.

### WR-03: `write_output` is not atomic; a failed write leaves `generated/` empty or half-written

**File:** `practices/output.py:29-38`
**Issue:** The module deletes `generated/` with `rmtree` and then writes each file. A disk-full error, a permission error, a Ctrl-C (`run_command` turns it into exit 130) or a crash partway leaves `generated/` partly or wholly gone. The `generate.py` comment says a broken master stops the run before anything is touched, which holds only for render errors, not write errors. The committed copy is recoverable from git, but only if the user notices and nothing else was uncommitted in `generated/`.
**Fix:** Write into a sibling temp folder (`repo_dir / ".generated.tmp"`, created with `tempfile.mkdtemp(dir=repo_dir)`), then `shutil.rmtree(generated_dir)` and `os.replace(tmp_dir, generated_dir)`. Remove the temp folder in a `finally`.

### WR-04: Skill `name` is emitted as a bare YAML scalar and can change type

**File:** `templates/claude/skill.md.j2:2`, `templates/cursor/skill.md.j2:2`
**Issue:** `name: {{ skill.name }}` is not quoted, while `description` goes through `yaml_str`. A master with `name: "123"` in `skills/123/` passes `_check_name` (the parsed value is the string "123") and renders `name: 123`, which a YAML reader parses as an integer. The same holds for `"true"`, `"null"` and `"no"`. I confirmed the output line `name: 123`. The reverse case (an unquoted `name: 123` master) is rejected with the misleading message "name must equal the folder name".
**Fix:** `name: {{ skill.name | yaml_str }}` in both templates, and update the exact-bytes expectations in `tests/test_skill_output.py` (the fixture name `a` would then render as `"a"`).

### WR-05: `paths` globs are not checked for newlines or surrounding whitespace; the Cursor template can inject frontmatter keys

**File:** `practices/reader.py:126-139`, `templates/cursor/rule.mdc.j2:3`
**Issue:** `check_path_list` rejects empty, non-string and comma-bearing globs only. A glob such as `"a\nalwaysApply: true"` is valid for the Claude output (JSON-quoted) but the Cursor template writes it raw, producing `globs: a`, `alwaysApply: true`, `alwaysApply: false`. I confirmed this output. The master files are trusted, but the reader is documented as the strict dialect gate, and the Cursor line is plain text with no escaping. A glob with leading or trailing space, or one that starts with a character YAML treats specially, also produces a different meaning per agent.
**Fix:** In `check_path_list`, reject any glob where `glob != glob.strip()` or where any character is a control character (`not glob.isprintable()`), with the same "write one glob per entry" style of message. Add cases to `BROKEN_RULE_MASTER_LIST`.

### WR-06: The "find the clone" instruction resolves the wrong repository when run from a project

**File:** `rules/best-practices.md:3`, `skills/update-practice/SKILL.md:15-17`
**Issue:** Both texts say to resolve the file's link with `realpath` and "take the repository root with `git rev-parse --show-toplevel`". `git rev-parse --show-toplevel` answers for the current working directory, which in normal use is the user's project, not the best-practices clone. An agent following the text literally edits branches in the wrong repository. `test_masters_neutral` asserts the strings `realpath` and `git rev-parse --show-toplevel` are present, so the wording is pinned and the gap is untested.
**Fix:** Name the directory: take the folder that holds the resolved file and run `git -C <that folder> rev-parse --show-toplevel`. Update the expected strings in `tests/test_masters_neutral.py`.

### WR-07: `test_masters_neutral` crashes on hidden or binary files that the reader deliberately skips

**File:** `tests/test_masters_neutral.py:67-75` and `:36`
**Issue:** `_master_file_list` uses `rglob("*")` with no hidden-file filter and reads every file as UTF-8. The reader skips hidden entries and tolerates a `.DS_Store` (see `test_hidden_entries_in_rules_are_skipped`). On the user's macOS host a Finder-created `rules/.DS_Store` or `skills/.../.DS_Store` makes this test fail with `UnicodeDecodeError`, and a binary skill extra file does the same. The test also checks files the generator never renders.
**Fix:** Build the list from `read_masters(REPO_DIR)` (rule `master_path`, skill `master_path`, and text-decodable extra files), or skip any path with a hidden part and catch `UnicodeDecodeError`.

### WR-08: Committed-output tests do not prove every generated file is tracked

**File:** `tests/test_committed_output.py:21-29`
**Issue:** `test_generated_output_is_tracked_and_not_ignored` asserts only that `git ls-files -- generated` is non-empty, then checks ignore rules. A newly rendered file that the author forgot to `git add` is not detected: `find_drift` reads the working tree, so check and the suite pass locally and the PR ships without it. No CI workflow exists in the repo to run the suite on the PR. The test also fails on a checkout that is not a git repository (tarball, `git archive`).
**Fix:** Compare the set `git ls-files -- generated` (stripped of the `generated/` prefix) with `render_all(REPO_DIR)` keys, and assert equality. Optionally add a CI job running `practices.check` and `pytest`.

### WR-09: No linter configured for the Python code

**File:** `pyproject.toml:1-19`
**Issue:** `rules/python.md` ("Linting") and `rules/coding-general.md` ("Linters") require a linter that runs in the normal test command so a finding fails like a test. `pyproject.toml` has no linter dependency or config, and no test gate script runs one. Style items the user cares about (unused imports, import order) go unchecked.
**Fix:** Add `ruff==<pinned>` to the dev group, a `[tool.ruff]` section matching the code (line length near 120, exclude `generated`), and run `uv run --locked ruff check` from the gate that runs `pytest`. Document it in the README command list.

## Info

### IN-01: `_rendered_header_file_list` ignores nested rules and the name says "rendered"

**File:** `tests/test_committed_output.py:92-98`
**Issue:** The reader supports rules in subfolders (`rules/sub1/d1.md`), but this helper uses a non-recursive `iterdir()`. A nested rule would yield a directory entry, `read_text` would raise `IsADirectoryError`, and `rule_file.stem` would drop the folder. The helper also walks `generated/` rather than the rendered map.
**Fix:** Iterate `render_all(REPO_DIR)` keys and derive the master path from the model (`Rule.master_path`, `Skill.master_path`), or use `rglob` plus the relative path.

### IN-02: `_yaml_str` can emit characters that YAML reads differently or rejects

**File:** `practices/render.py:47-48`
**Issue:** `json.dumps(..., ensure_ascii=False)` leaves U+0085 and U+007F raw. I confirmed that `yaml.safe_load` of a string holding U+0085 gives a different value (YAML folds it as a line break) and one holding U+007F raises `ReaderError`. A master can reach this by a double-quoted `"\x85"` escape in its description.
**Fix:** Use `ensure_ascii=True` (JSON escapes are valid YAML double-quoted escapes), or reject non-printable characters in `_check_description`.

### IN-03: Members public but used only inside their own module

**File:** `practices/reader.py:81,126,179,306`, `practices/render.py:33`, `practices/cli.py:42`, `practices/reader.py:23-26`
**Issue:** `read_rule`, `check_path_list`, `read_skill`, `split_frontmatter`, `build_environment`, `print_notice` and the `ALLOWED_*`/`MAX_*` constants have no caller outside their module. `coding-general.md` says to keep every member as private as it can be.
**Fix:** Prefix them with `_` (and update the one test import if any); keep public only what another module or test imports.

### IN-04: Duplicated constants and key literals

**File:** `practices/reader.py:23,28,32`, `practices/output.py:22`, `tests/test_committed_output.py:13`
**Issue:** `_OWNER_EXEC_BIT = 0o100` is defined in both `reader.py` and `output.py`; `GENERATED_FOLDER` is redefined in `test_committed_output.py` instead of imported from `practices.output`; `ALLOWED_RULE_KEY_SET = {"paths"}` and `ALLOWED_SKILL_KEY_SET` repeat the strings behind `_PATHS_KEY`, `_NAME_KEY`, `_DESCRIPTION_KEY` and `_DISABLE_MODEL_INVOCATION_KEY`. Two copies is tolerable by the user's rule, but these will drift, and the exec-bit read (`stat().st_mode & bit`) is the same logic in both.
**Fix:** Import `GENERATED_FOLDER` in the test; build the allowed sets from the key constants; move the exec-bit read to one helper (for example `is_executable(path)` in `model.py` or a small shared module).

### IN-05: Frontmatter edge cases are accepted or mis-parsed silently

**File:** `practices/reader.py:306-319`, `:324`
**Issue:** The fence match is exact (`"---"`), so a file with a UTF-8 BOM, or a fence with trailing whitespace (`--- `), is treated as having no frontmatter and its YAML lines become body text. PyYAML silently keeps the last of duplicate keys (two `paths:` blocks, two `description:` lines), so a duplicated key is not reported even though unknown keys are. YAML 1.1 booleans also make `disable-model-invocation: yes` pass as `true`.
**Fix:** Strip a leading BOM before the fence test (`text.removeprefix("\\ufeff")`), compare `line.rstrip() == "---"`, and use a `SafeLoader` subclass that raises on duplicate keys.

### IN-06: `merged` skill uses `$FEATURE_BRANCH` it never sets, and a bare `gsd-tools` command

**File:** `skills/merged/SKILL.md:60-72`, `:83`
**Issue:** Step 4 says the feature branch is `headRefName` from Step 1 but the shell snippets use `$FEATURE_BRANCH` and `git branch -D "$FEATURE_BRANCH"` without ever assigning it, so a literal run deletes nothing or runs `git branch -D ""`. The edited Step 5 now calls `gsd-tools query progress`, which assumes that binary is on `PATH` for every agent; the `2>/dev/null` plus the stated fallback makes it fail soft, but the skill does not say how to detect it.
**Fix:** Add `FEATURE_BRANCH=<headRefName>` to Step 1 (and to the `--arg` path, take the current branch before switching). Say in Step 5 to use the roadmap file when the command is not found.
