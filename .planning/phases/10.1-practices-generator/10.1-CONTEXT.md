# Phase 10.1: Practices generator - Context

**Gathered:** 2026-11-21
**Status:** Ready for planning (research first: D-03 comes back to the user before planning)

<domain>
## Phase Boundary

The best-practices repo gains agent-neutral masters, a small Python generator and one Jinja template set per agent. The generator reads the masters (`rules/`, `skills/`) into a typed model and renders it into committed output under `generated/claude/` and `generated/cursor/`. A drift check proves the output matches the masters. An `update-practice` skill and a rewritten `rules/best-practices.md` make an agent edit the masters and regenerate, never the output.

All work happens in the best-practices repo (`/home/sandbox/workspace/best-practices`). No sandbox changes in this phase: linking the output into the agents' config directories is Phase 10.1.1. OpenCode templates are Phase 10.2.

</domain>

<decisions>
## Implementation Decisions

### The pattern: masters, model, templates per agent
- **D-01:** Agents read rules in different formats (Claude: `.md` with `paths:`; Cursor: `.mdc` with `globs:` and `alwaysApply:`; OpenCode, per Phase 10.2: likely `AGENTS.md` or an `instructions` list). Skills share one format (`SKILL.md` with `name` and `description`) but still go through the same pipeline. So the best-practices repo has masters plus scope metadata, and renders them per agent.
- **D-02:** The pipeline is: a reader parses every master into a typed model (for example `Rule(name, scope, description, body)` and `Skill(name, description, body, extra files)`); a small per-agent profile says where each output goes and how it is named (extension, folder, one file per rule or one combined file); one Jinja template per agent and kind (for example `templates/cursor/rule.mdc.j2`) renders the model. Differences between agents live in the templates, not in Python string building. Jinja is pinned with uv in the best-practices repo (a new `pyproject.toml`). **Reversibility:** costly: the templates and the reader are the whole mechanism.
- **D-03:** The master format is picked on merit, not because Claude's format works today. Research compares Claude `.md` + `paths:`, Cursor `.mdc`, an `AGENTS.md` style and plain `.md` with a separate manifest, against these criteria, and brings the pick back to the user before planning:
  1. Expresses every scope we use: "always" and "only for these file globs". Cursor's "agent picks it by description" mode is not required.
  2. Renders to every target (Claude, Cursor, OpenCode, the next agent) without loss.
  3. Plain and readable: normal Markdown, renders on GitHub, easy to edit from any agent's sandbox.
  4. Stable: a documented format likely to last, or an emerging cross-agent standard.
  5. Tie-breaker only: at least one agent can use it as is.

  No invented format for its own sake; leaning towards plain `.md` with a small frontmatter block. If the pick is not the current Claude format, converting the 13 rule masters is part of this phase. **Reversibility:** costly: every master and every template follow the format.
- **D-04:** No Jinja inside master bodies, at least at first. Masters stay plain Markdown; only the templates wrap them. Placeholders such as `{{ config_dir }}` in rule text are rejected for now: they turn masters into templates and break code samples that contain `{{`. Revisit only if agent-neutral wording proves insufficient.
- **D-05:** The generator walks the two shallow master folders with a plain sorted `rglob`. No visitor-pattern traverser: `base/selfcheck/tree_walk.py` lives in the sandbox repo's image and cannot be imported here, and copying it would make a second copy to maintain. Adopt the visitor pattern (as in the user's `util-file-traverser`) only if the generator grows several different walks.

### Output layout
- **D-06:** Layout of the best-practices repo:
  ```
  best-practices/
    rules/              masters (paths unchanged, so history stays)
    skills/             masters
    templates/<agent>/  Jinja templates per agent
    generated/          never edited by hand
      claude/
        rules/
        skills/<name>/
      cursor/
        rules/
        skills/<name>/
    generator, drift check, pyproject.toml
  ```
  The output folder is called `generated/` (not `out/` or `dist/`) so its name tells an agent not to edit it. **Reversibility:** costly: Phase 10.1.1 links these paths.
- **D-07:** Everything is generated, skills included, even where Claude's output equals the master. One plain rule for agents and humans: agents only ever see `generated/`.
- **D-08:** Each `generated/<agent>/` mirrors that agent's config directory (`generated/cursor/` has the shape of `~/.cursor/`), so the Phase 10.1.1 linker stays agent-neutral.
- **D-09:** The generated output is committed (the "commit generated code the build needs" rule), so a sandbox only links it and never runs the generator.

### Keeping edits on the masters
- **D-10:** `rules/best-practices.md` (always loaded by every agent) is rewritten: masters live in `rules/` and `skills/`, `generated/` is never edited, a change goes through the `update-practice` skill, and masters are agent-neutral (no agent's paths, tools or command syntax).
- **D-11:** A new `update-practice` skill holds the steps: branch from the updated `main`, edit the master, run the generator, run the drift check, commit masters and output together, ask for the push go, open the PR. The user only says what to change.
- **D-12:** Every generated file starts with a comment naming its master, for example `<!-- GENERATED from rules/java.md; edit that file and regenerate -->`. An agent that reaches a rule through its config link lands in the generated file first; the header sends it to the master.
- **D-13:** The drift check is a script (regenerate and compare; fails on any difference, so a hand edit of an output fails it). It is run by the skill and by hand. No git hook and no CI in this phase (see Deferred).

### Agent-neutral wording in the masters
- **D-14:** In the best-practices repo PR of this phase:
  - `skills/merged`: `node "$HOME/.claude/gsd-core/bin/gsd-tools.cjs"` becomes `gsd-tools` (on PATH in every image).
  - `rules/git-workflow.md` and `skills/merged`: GSD steps are named as skills (for example "the `gsd-execute-phase` skill"), not slash commands.
  - `skills/pr-reply`: "the repo's agent instructions file (`CLAUDE.md`, `AGENTS.md`)" instead of `CLAUDE.md` only.
  - `rules/communication.md`: the `AskUserQuestion` line becomes "a multiple-choice picker, if the agent has one".
  - `rules/best-practices.md`: rewritten per D-10.

### Proof in this phase
- **D-15:** pytest tests in the best-practices repo for the reader and for each agent's templates, plus the drift check passing on the committed output.

### Phase split and order
- **D-16:** The original Phase 10.1 ("full skills and best-practices support in Cursor") is split: 10.1 is this generator (best-practices repo); 10.1.1 links the generated practices into the sandboxes (this repo); the shared agent checks moved to 10.1.2; OpenCode stays 10.2. Linking goes before the shared checks so Cursor gets its practices one phase sooner; the extra churn is small because the link logic already lives in shared base modules and the per-agent files are 20-line wrappers.

### Carried to Phase 10.1.1 (decided here, implemented there)
- **D-17:** The linker becomes agent-neutral: it links what `generated/<agent>/` holds into the agent's config directory. The rules folder is linked whole (`~/.cursor/rules` -> `generated/cursor/rules`); skills get one link each, because `skills/` also holds GSD's skills and user skills.
- **D-18:** Existing sandboxes fix themselves: the linker already treats any link into the clone as its own and replaces it, so the next `sbx-init` moves Claude's links from `rules/` to `generated/claude/rules/`.
- **D-19:** Proof there: the selfcheck checks the links point into `generated/<agent>/` and resolve; the integration scenario asserts the same for both agents through `AgentSpec`; an attended Mac step asks Cursor to list its rules and skills. That step settles whether Cursor's CLI reads `~/.cursor/rules` and follows linked skill folders; if not, the fallbacks (copy instead of link, or `AGENTS.md`) come back to the user as a decision.
- **D-20:** GLOSSARY.md gains the new terms (master, generated practices) when this repo's code first uses them.

### Claude's Discretion
- File and module names of the generator, the drift check script and the profiles.
- The exact header wording of generated files (D-12), within the comment syntax each output format allows.
- How the model represents skill extra files (copy as is, or through a template).

</decisions>
