<objective>
Fix the last two open findings of the incremental review of Phase 8:

1. `run_check` guards only the call to `check.function()`. `run_selfcheck` then reads `result.passed` and `outcome_lines` reads `result.detail` and `result.hint`, both outside any `try`. A check that returns `None` (a forgotten `return`, the commonest slip when a check is added), a bool or a tuple ends the whole run with `AttributeError` and no PASS or FAIL line. The previous plan closed this hole for a malformed `CHECK_LIST`; this is the same hole one level down, and the README promise that a broken checks file shows up as a FAIL line still has this gap.
2. In `scan_owned_state` the entry stat handler catches every `OSError`, names the whole folder `(unreadable)` and breaks out of the entry loop. That is right for a folder that cannot be searched, but any other error on one entry (an I/O error, a too long name) mislabels the folder and leaves the entries after it unexamined, so a root-owned sibling can drop out of the report. The relative folder path is also computed in two places.

Purpose: the self-check is the sandbox doctor (D-04). A check that returns the wrong thing gets a named FAIL with a fix, and an unusual entry error is reported as what it is instead of as an unreadable folder.
Output: a result check inside `run_check`, a narrowed handler in `scan_owned_state`, a test written first for each, and the review ledger with both findings fixed.

No Mac checkpoint. The changes are Python covered by pytest, Docker is not available in the dev sandbox, and the Mac run of the earlier plan already passed. A healthy sandbox takes the same path through both functions as before, so its lines and the check counts do not change; the next `./host-test.sh` run picks the new code up through the image build.

## Design (Claude's discretion under D-03, D-04 and D-12)

- WR-03 validates the result inside `run_check`, as the review suggests. That function is where a check's exceptions already become FAIL lines, so a wrong return is one more way a check fails to produce a result, and `run_selfcheck`, `outcome_lines` and `collect_checks` stay untouched. The detail names the returned type, so a forgotten `return` reads `NoneType`. The fix text is the one the `raised` branch uses; two copies of that short prefix are tolerable.
- IN-09 narrows the entry stat handler to `PermissionError` and keeps the `break`. Why, of the two options the review offers:
  - An entry `lstat` needs only search permission on its folder, so a `PermissionError` there means the folder cannot be searched and every other entry would fail the same way. Naming the folder once and ending its loop is exact.
  - Any other error on one entry is a different fact. Calling it "folder unreadable" is wrong, and `OSError` with `continue` would leave that entry unclassified: a root-owned entry could pass unseen and the check could print a false PASS, the worst outcome for a doctor. It would also need a duplicate guard in the helper, since the helper would append the folder once per failing entry. Letting the error surface gives the runner's existing named `raised OSError` FAIL, loud and visible.
- Honest asymmetry, kept on purpose: the listing branch stays `except OSError`, because a listing that fails for any reason is a whole-folder fact, unlike a single entry's stat.
- The folder's relative path is computed once, right after the folder is popped at the top of each pass, because the listing branch needs it before the review's suggested spot (after the `scandir` block). Both helper calls use it.
- No README change: its troubleshooting rows already describe both outcomes.
